# 1. 澄清需求

在估算任何规模之前，先弄清楚面试官问的到底是哪个阶段。LLM 系统设计里最常见的
错误，就是把每个问题都当成预训练问题（从零开始、几万亿 token 的训练，产出一个
原始基座模型的那种）。而它几乎从来不是。

下面是一段典型的对话。注意每一个问题要么直接把某个阶段划出范围，要么从根本上
改变了设计。

---

**候选人：** 公司今天用现成的 API 拿不到什么能力？值得自己持有权重的那个缺口是什么？

**面试官：** 主要是数据驻留。公司处理的是敏感的法律文书，不能送出本地环境。另外
他们需要领域术语和引用格式，这两样前沿模型总是弄错。

---

**候选人：** 有没有可以起步的开源权重？还是必须从零预训练？

**面试官：** 用开源基座没问题。预算是实打实的，但不是实验室级别，没有几亿美元。

---

**候选人：** 领域语料长什么样？多少 token，有多干净，变化多快？

**面试官：** 大约 500 亿 token 的判例和合同，已经清洗过了。每季度更新一次。

---

**候选人：** 服务目标是什么？延迟、吞吐、单次查询成本？

**面试官：** 交互式的：p95 首 token 延迟 2 秒以内，峰值大概 500 个并发用户。成本要管，
这不是离线批处理任务。

---

**候选人：** 安全和评估的门槛在哪里？输出错了谁会受伤？

**面试官：** 用户是受过训练的律师，他们会审核建议。引用错了很糟糕，但有人复核。我们
需要的是引用准确率和指令遵循，不是消费级的安全加固。

---

把问题总结一下。我们要拿一个能力过硬的开源权重基座模型，让它适应法律领域的文本和
词汇（中期训练，也就是在 500 亿领域 token 上继续预训练），把它变成一个能正确引用
来源的指令遵循模型（后训练，也就是 SFT 加偏好调优，让基座模型学会听指令的那个
阶段），然后在中等并发、交互式延迟的要求下把它服务起来，同时管住成本。

**两个结论马上就能推出来：**

- **这几乎肯定是一个中期训练加后训练的问题，不是预训练。** 从零预训练一个大到有
  意义的模型要花几亿美元和几周的算力。这个团队的杠杆在于拿一个开源基座（Llama 3、
  Qwen3、OLMo），在 500 亿领域 token 上做适应，然后跑 SFT（在指令-回复对上做监督
  微调）和偏好优化。基座模型的通用语言能力是白送的，我们只为增量付钱。

- **服务约束直接排除了全精度的最大号模型。** 500 个并发用户、p95 首 token 延迟 2 秒，
  意味着模型必须小到能在预算内服务，这就需要量化（把权重存成低精度整数以缩小显存
  占用，至少 INT8），而每个用户的 KV cache（为过去的 token 保存的 key 和 value）大小
  决定了每张 GPU 能塞下多少并发请求。服务设计不是细节，它决定了哪个模型规模才是
  可行的。

## 四种情况的速查

| 面试官说 | 实际问的是哪个阶段 | 典型回答 |
|---|---|---|
| "给我们的领域做一个 LLM" | 在开源基座上做中期训练 | 在 Llama / Qwen3 / OLMo 基座上继续预训练，再做后训练 |
| "让它遵守我们的风格指南，并拒绝有害请求" | 后训练 | 在基座输出上做 SFT 加 DPO；不做预训练 |
| "我们的法律文书需要 200K 上下文" | 中期训练（上下文扩展） | 从现有基座出发，做 RoPE 缩放并在长文档上继续训练 |
| "我们需要一个面向新语言的新基础模型" | 预训练 | 在大规模多语言语料上从零预训练；只有实验室级别的规模才说得通 |

先说清问题属于哪个阶段，再去估算任何规模。明明中期训练就够用，却一开口就是
"我们要预训练"，是这场面试最快的挂法。
