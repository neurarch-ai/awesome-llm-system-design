# 5. 可靠性

## 流式系统特有的故障模式

流式对话系统出故障的方式和无状态请求系统不一样。一个请求要么成功要么失败。而一条流可以成功了一半然后死掉，
给客户端留下半条回复。这种"半截"状态带来三个非流式系统里不存在的问题：

1. **部分输出。** 用户收到了回复的前一半，连接断了，session 存储可能记了也可能没记这次生成到一半的内容作为助手的这一轮。

2. **重复生成。** 客户端没看到回复，重试请求，服务端又生成了一次。如果第一次生成已经记进了 session 存储，
   重试就会追加第二条一模一样的回复。如果没记，客户端看到的就是前后不一致的视图。

3. **无主的槽位。** 客户端掉线了，服务端没检测到，继续生成，白白烧掉一个槽位好几分钟。

每一个都有具体的修法。

## 重连与 session 恢复

围绕两条不变式来设计重连：

**不变式 1：session 存储是唯一的真相来源。** 网关只在生成结束（或到达一个安全的检查点）之后，才把一条完整的助手轮次
写进 session 存储。它不写部分输出。

**不变式 2：客户端记住它收到的最后一个事件序号。** 每个 SSE 事件在 `id:` 字段里带一个单调递增的序号
（这是 SSE 的标准行为；浏览器的 `EventSource` 重连时会发 `Last-Event-ID` 头）。网关用它在 token 流里找到正确的位置续传。

重连时：

- 如果生成还在同一个副本上进行，网关从 `Last-Event-ID + 1` 处继续推流。
- 如果生成已经完成，网关从 session 存储读出回复，从相应的偏移处开始推。
- 如果生成已经成了无主的（客户端掉线，槽位已释放），客户端收到一个"生成已取消"的信号，可以重新提交。

这样设计的意义在于，短暂的网络抖动不会逼着客户端完整重试。用户得到一次平滑的重连，生成不会重复，
而且无论哪种情况槽位都会被及时释放。

## 幂等

当客户端确实需要重试（生成真的丢了）的时候，重试必须是幂等的。机制是客户端生成一个请求 id，每次尝试都带上。
网关按这个 id 去重：如果这个请求 id 对应的生成已经记在 session 存储里，就返回存好的结果，不再生成一次。

这和支付 API 里的幂等 key 是同一个模式。窗口只需要覆盖重试窗口（通常几秒到几分钟）。去重存储上加一个短的 TTL
（time-to-live）就够了。

## Session 存储里的部分输出怎么处理

关于部分输出有两个流派：

**按句子边界打检查点。** 网关每检测到一个句子边界（句号、换行）就把部分回复写进 session 存储。连接断了，
session 存储里有截止到最后一个完整句子的内容。重连时客户端得到一条到那个位置为止的干净回复。

**只在完成时写。** 网关只在生成结束时写 session 存储。中途断掉意味着这次生成丢了，客户端重试。实现和推理都更简单；
风险在于一次很长的生成（好几段、一个代码块）如果在快结束时断掉，可能整个丢掉。

对大多数聊天产品来说，只在完成时写是正确的默认。生成够短，重试的代价很低，换来的简单性值得。
按句子边界打检查点适合长文本生成类产品，那里一条回复可能要跑几十秒。

## 故障模式汇总

| 故障模式 | 原因 | 检测 | 修法 |
|---|---|---|---|
| 无主的生成 | 客户端掉线且没有显式取消 | 下一个 token 写失败；心跳超时 | 中止生成，释放槽位 |
| 送出了部分输出 | 生成中途连接断掉 | 重连时的 `Last-Event-ID` | 从最后看到的事件 id 续传 |
| 重试时重复生成 | 客户端重试时没有幂等 | 没有去重 key | 客户端请求 id，网关去重 |
| session 存储里留下过期的半截内容 | 网关在中断时写了部分内容 | 没有完成标记 | 只在干净完成时写存储 |
| 重连时 cache miss | 换了一个副本处理重试 | 冷 prefill（性能问题，不是正确性问题） | 接受冷 prefill 作为兜底；优先选同一个副本 |
