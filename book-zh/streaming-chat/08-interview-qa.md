# 8. 面试问答

面试官在实时流式对话这块真正会问的问题，按用途分组。
"常被答错的"那一节，才是面试拉开差距的地方。

## 常考的

**问：为什么要流式吐 token，而不是等全部生成完一次性返回？**

答：为了感知延迟。模型是一个一个 token 解码出来的，prefill 一结束第一个 token 几乎马上就有了，
而最后一个 token 可能要好几秒之后才到。流式输出把每个 token 一产出就送走，用户能看着回复实时长出来。
用户真正感受得到的指标是首 token 延迟（TTFT），总生成时间是次要的。
一条五秒的回复，如果 300ms 就开始出字，比一条两秒但生成完之前什么都不显示的回复感觉更快。

**问：SSE 还是 WebSocket？你选哪个？**

答：纯文本聊天选 SSE。token 的投递是单向的（服务端到客户端），而 SSE 就是为这件事造的：
普通 HTTP，不需要升级握手，能穿过标准代理，好调试。WebSocket 多出来的全双工能力，基础聊天用不上。
什么时候选 WebSocket：产品需要在流的中途做客户端到服务端的信令（实时打断、音频、一条连接上多路并发请求）。
语音则要上基于 UDP 的 WebRTC，因为 TCP 的有序投递会在丢包时把音频卡住。

**问：为什么第五轮比第一轮贵？**

答：每一轮都要对整份对话记录做一次 prefill。每过一轮，记录大致就多出一条用户消息加一条助手回复，
到第五轮时模型要读五轮的历史。prefill 的成本随上下文长度增长。
前缀缓存能缓解这件事，它复用对话里那段稳定开头的 KV cache，
但前提是后续这一轮落在同一个副本上（粘性路由）。没有缓存也没有粘性，
每一轮都要为越来越长的记录付出完整的 prefill 成本。

**问：用户在生成到一半时点了停止，说说会发生什么。**

答：客户端发一个取消信号（或者直接关掉 SSE 连接）。网关检测到取消，向推理引擎发取消信号，
引擎中止 decode 并释放推理槽位。这一轮网关不往 session 存储里写任何东西（半截的回复丢掉）。
槽位立刻还回池子。这里最要命的错误是没把取消传递到推理引擎：模型继续解码没人会看的 token，
白白烧着一个本可以服务另一个用户的槽位。

**问：用户在生成中途关掉了浏览器标签页，你怎么处理？**

答：网关在尝试推下一个 token 时会遇到写错误（TCP 连接已经没了）。它中止生成、释放槽位、丢掉半截回复。
在 SSE 通道上加心跳（定期发一行注释）能保证即使操作系统没有报告一次干净的关闭，网关也能发现连接已死。
客户端重连时会带上 `Last-Event-ID`（这是 SSE 的标准行为）：如果生成还在进行中，网关从那个位置续传；
如果已经生成完了，就从 session 存储里把完整回复取出来给它。

## 有坑的（拉开差距的追问）

**问：你说前缀缓存能降低多轮延迟。现在流量突增，你得加新的推理副本，你的缓存会怎么样？**

答：新副本上的缓存是冷的。因为一致性哈希重新平衡而落到新副本上的 session，
下一轮要付出一次完整 prefill 的 cache miss。正确的态度是把缓存当成尽力而为的优化：
正确性不受影响（对话记录在 session 存储里），下一轮在新副本上就把缓存捂热了。
你要监控缓存命中率，并在它持续下滑时告警（那说明是路由有 bug，而不是一次重新平衡）。
**为什么"持续"才是关键的判据：** 重新平衡带来的 miss 是自愈的，因为 miss 的这一轮本身就把新副本捂热了，
所以命中率只会掉一下，一两轮之内就恢复；而路由 bug 会让同一个 session 每一轮都跑到不同的副本上，
于是每轮都 miss，命中率一直低着。区分这两种原因，看的是这条曲线随时间的形状。

**问：你有 1 万条并发流。其中一个用户已经聊到第 200 轮，上下文极大，所以他的生成很慢。这会影响其他用户吗？**

答：在连续批处理下，调度器把所有在途流的 decode 步骤交错着跑，所以单独一条慢流不会饿死别人。
这条慢流自己的问题是 prefill 很贵（上下文长），这会拖慢它每一轮的 TTFT。另外 9999 条流不会被阻塞。
**这种隔离为什么成立：** 每一个 decode 步骤都会重新组一次 batch，所以没有哪条流会在整次生成期间独占 GPU；
唯一的风险点是那一大段 prefill 的突发，现代引擎的做法是把大 prefill 切成 chunk，
和其他人的 decode 步骤交错着跑，于是巨大的上下文拖慢的是这个用户自己的首 token，
而不是把整个集群的 token 间延迟都抬上去。对这个慢用户的缓解手段是服务端摘要，把他的上下文长度框住，
或者给单个 session 显式限流，防止一个人在每一轮里都占掉不成比例的 GPU 时间。

**问：为什么不把整段对话缓存在客户端，每轮都发上来？这样就不需要粘性路由了。**

答：这是个成立的设计，一些简单的部署就是这么做的。代价是：每次请求的负载大小随历史增长，
服务端做不了服务端摘要或者上下文管理，而且一份很大的对话记录在每一轮都会带来可观的序列化和网络开销。
更大的问题是信任：如果历史由客户端发上来，服务端每次请求都得校验它（客户端可能截断它，也可能篡改它）。
对于会话很长、需要可恢复、或者有安全约束的产品，状态放在服务端才是对的选择。
**为什么篡改不只是"多花点钱"这么简单：** 对话记录是模型这一轮全部的依据，
所以一个能改历史的客户端可以伪造助手早先做过的承诺（"你已经答应免掉这笔费用了"），
或者夹带进审核层在任何一轮真实对话里都没见过的指令；一旦信任客户端持有的历史，
过去的每一条消息就都成了未经认证的输入。

**问：你的语音产品端到端延迟是 600ms，你从哪儿砍？**

答：先把流水线的和拆开：STT 加轮次检测，加 LLM 首 token，加 TTS 首字节，加网络。每一段都测。
常见的高收益砍法：（a）抢跑式轮次检测（拿中等置信度的转写就先发 LLM，用户如果又接着说就取消），
能从轮次检测的等待里省下 200 到 400ms；（b）流式 TTS，整句还没合成完就开始播；
（c）如果可以放弃那份能看的中间转写，就换成融合式的 speech-to-speech 模型。
砍网络就是多区域部署，把流量路由到最近的区域。
**为什么抢跑式轮次检测是单项收益最大的：** 轮次检测器只有等过一段静音阈值才能确认用户说完了，
而这段等待是纯粹的死时间，每一轮都要付一次；投机性地先发 LLM 就把这段死时间和有用的计算重叠起来了，
而且这个赌注很便宜，因为猜错了也是在任何话被播回给用户之前就取消掉。

**问：首 token 延迟和 token 间延迟都在衡量流式的快慢，这个区别到底什么时候才真的重要？**

答：两者的表现都是"这条流感觉很慢"，仪表盘也经常把它们糊成一个延迟数字。
但它们是由不同的阶段产生的，瓶颈也不一样。TTFT 主要由排队加 prefill 决定：它随上下文长度和准入延迟增长，
能改善它的是前缀缓存、粘性路由和分块 prefill。token 间延迟由 decode 吞吐决定：
它随 batch 大小和模型大小增长，能改善它的是批处理策略和硬件选择。
只要你开始调任何一个旋钮，这个区别立刻就重要了：把 batch 上限调高会改善单 token 成本，
同时让 ITL 变差，而 TTFT 基本不动；前缀缓存会改善 TTFT，对 ITL 毫无帮助。
一个混在一起的延迟指标会掩盖该拧哪个旋钮，而针对一个阶段的修法，往往会让另一个阶段稍微变差。

**问：用户的网络在流传到一半时抖了一下，SSE 连接断了。这个标准怎么帮你续传，而不用把整个回答重播一遍？**

答：Server-Sent Events（W3C/WHATWG）自带重连：连接断掉时浏览器的 `EventSource` 会自动重连，
而且如果服务端给每个事件都打了 `id:` 字段，客户端重连时会在 `Last-Event-ID` 请求头里带上它看到的最后一个 id。
只要服务端按 stream id 缓冲了在途的这次生成，它就能从那个 id 之后的 token 接着推，而不是从头开始
（session 存储里的对话记录是那份持久副本）。如果服务端没有缓冲，重连照样会触发，但没有东西可以续传，
于是客户端要么从头重放，要么等那条持久化的最终消息。这就是为什么生产环境的流式输出都会给每个事件分配 id，
哪怕顺利的时候从来没人回头去读它们。

## 常被答错的

**问：语音是不是该用 WebSocket，好拿到比 SSE 更低的延迟？**

答：不是。语音的传输选择是基于 UDP 的 WebRTC，不是 WebSocket。
WebSocket 跑在 TCP 上，而 TCP 靠重传丢失的包来保证有序投递。
对文本 token 来说，一次重传只是稍微晚一点；对音频帧来说，一次 200ms 的重传卡顿会毁掉对话的流畅感（队头阻塞）。
WebRTC 用 UDP：丢掉一个 20ms 的音频帧几乎听不出来。WebRTC 还自带抖动缓冲、回声消除、拥塞控制和 NAT 穿透。
在这类面试里，拿 WebSocket 做语音是最常见的传输选型错误。

**问：为了应对过载，我会把多出来的请求全排队，等槽位空出来再服务。**

答：无上限的排队比丢负载更糟，因为队列一长，排在后面的请求真被服务到的时候已经在那儿等了好几分钟。
正确的过载应对是：排队，但把等待时间老实显示出来；超过阈值就丢，并给一个明确的重试信号
（HTTP 429 带 `Retry-After` 头）；再加上尖峰时降级到更小的模型来抬高槽位容量。
无声无息地无限排队，在用户看来就是卡死，而且会因为重试把负载放大。
**这个放大是怎么来的：** 用户和客户端库会超时重试，于是每一个被默默排进队列的请求都会派生出副本，
排在自己后面进同一个队列；到达速率正好在有效容量已经耗尽的时候往上冲，
而队列最终服务的那些请求里，有很大一部分属于早就放弃的用户，这是纯粹浪费掉的 GPU 时间。
早点丢负载，才能让系统干的活和还在等着的用户对得上。

**问：我会往 session 存储里多存点上下文，每次 prompt 都带上，好让模型在长对话里更聪明。**

答：让存下来的上下文无上限地涨，这本身就是故障模式，不是修法。多存的每一个 token，
下一轮 prefill 都要再读一遍。正确的设计是用摘要或者滑动窗口把上下文的增长框住，
再在前缀缓存加粘性路由上投入，让那段稳定开头的重读成本保持在低位。
不设上限地往里加上下文，最后得到的就是一个聊到一半撞上上下文上限然后报错的产品。
**更多上下文甚至换不来它承诺的质量：** 旧的轮次会和当前这个问题争抢模型的注意力，
而随着对话记录在某个相关细节周围越堆越多，把它检索出来的效果反而在退化；
一份有边界、被摘要过的上下文常常答得更好，而不只是更便宜，
因为模型需要的那点信号不再被埋在一堆早就不重要的轮次里。

**问：我会在负载均衡器上开 session 亲和，让前缀缓存生效。**

答：粘性负载均衡是一种机制，但光靠它不够。如果用户开了两个标签页，或者断线后重连，
或者负载均衡器把他重新路由了（节点重启，或者粘性 session 过期），这个 session 就会落到一个冷副本上。
正确的设计把粘性当成尽力而为：尽量路由到热副本，但接受 cache miss 一定会发生，
并确保走冷缓存那条路是正确的、只是慢一点，而不是坏的。
**为什么冷路径必须是一等公民：** session 到副本的映射存在负载均衡器里，并不持久，
而那些会打断它的事件（重启、扩容、故障切换）恰好扎堆出现在压力最大的时刻；
所以一个只在热路径上正确的设计，偏偏会在故障期间失效。正确性必须放在 session 存储里，
缓存只负责改变延迟。

**问：流式输出能缩短生成答案的总时间，对吧？**

答：不对。流式不改变模型产出最后一个 token 需要多久；无论流不流式，decode 吞吐都是一样的。
它改变的是感知延迟：prefill 一结束就把第一个 token 送出去（TTFT），而不是攥着所有 token 等整段生成完，
于是用户可以边生成边读。到最后一个 token 的时间，以及总成本，都没有变。
把首 token 时间和末 token 时间搞混，会让人许下一个流式根本给不了的吞吐承诺；
它的收益全在响应感上，这也正是为什么真正重要的指标是 TTFT 和 token 间延迟，而不是一个端到端的总数字。
