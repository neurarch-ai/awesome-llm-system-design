# 8. 面试问答

真正会被问到的关于"给模型做 benchmark"的问题，按用途分组。最后那批坑是这场面试通常丢分的地方，因为每一个都有一个听起来很对、其实是错的答案。

## 常见问题

**问：把整条流水线讲一遍。你怎么在 benchmark 上评估一个模型？**

答：八个阶段，有意思的内容集中在中间三个。

1. **先想清楚这个数字要干什么。**是选模型、训练过程的遥测、发布门禁，还是对外的宣称。这决定了需要多严谨，以及给谁看。
2. **选的是组合，不是一个 benchmark。**能力项对着负载来挑，每一项都要有提升空间，另外至少配一个私有的内部题集，它污染不了，而且确实对得上构念。
3. **钉住题目。**benchmark 版本、题量、发布日期、许可证。
4. **固定协议。**chat 模板、system prompt、few-shot 的数量和顺序、答案格式指令、打分模式、解码参数、输出 token 预算、每题样本数、seed。已发表数字之间的方差大多来自这里，所以它是写下来并做哈希的，不是靠默认假设。
5. **跑，并且什么都留着。**按题分片、按完整协议哈希做缓存、代码和 agent 放沙箱里、每次运行的 token 和美元都记账，每一条渲染后的 prompt 和原始输出都存下来。
6. **打分。**任务允许就用可执行检查，短的自由答案用答案匹配，开放式用认证过的评分器做 rubric 评分，代码用单元测试，agent 用任务成功率加成本加可靠性。解析失败率、截断率和拒答率都当成一等输出来跟踪。
7. **像分析实验一样分析。**逐题配对比较、区间、seed 方差、题目成组时用聚簇误差、在你实际跑过的那张表格上做多重比较控制。
8. **报告一张卡片，不是一个数字。**分数、区间、样本数和 seed 数、每题成本、协议哈希、污染证据，以及每一组比较的结论，而且允许结论是"区分不出来"。

然后说出那句给整个回答定调的话：这条流水线的任务不是产出一个高分，而是产出一个能扛住别人来复现的数字。

**问：你怎么决定跑哪些 benchmark？**

答：从决策倒推。列出产品依赖的能力项（比如重检索的推理、代码编辑、工具调用、长输入、两种语言），每项挑一个还有提升空间的 benchmark，凡是所有候选都已经在 90 分以上的直接砍掉，因为剩下的差距落在标签噪声里。再加一个 live 或者做了时间切分的 benchmark 当污染核查，加一个私有的内部题集作为正式的决策依据。采用一个 benchmark 之前，先验证它能分开两个你已经知道差距大于它自身置信区间的模型；如果分不开，它也分不开你真正要比的那两个。

**问：你的数字和厂商公布的不一样。发生了什么？**

答：先验是协议出问题，不是模型。我按这个顺序查，因为这大致就是各项效应的量级排序：chat 模板和 system prompt、few-shot 的数量和顺序、打分模式（对数似然排序还是生成加解析器）、输出 token 预算和截断率、解码参数和样本数，最后才是 benchmark 版本和题目子集。LM Evaluation Harness 的维护者记录过这样的案例：在同一批题上，光是 prompt 格式就能让一个模型在"接近随机"和"挺能干"之间来回移动，这个幅度比我要争论的任何一代模型之间的差距都大。解法不是去调和两个数字，而是在我自己控制的一套协议下，把每个候选（包括基线）全部重跑一遍。

**问：你怎么知道 3 分的差距是真的？**

答：配对着算。两个模型答的是同一批题，所以答案一致的题相互抵消，只有不一致的那些携带信息：设 A 赢了 $b$ 题、B 赢了 $c$ 题，差值就是 $(b-c)/n$，标准误约为 $\sqrt{b+c}/n$。在一个 200 题的 benchmark 上，每个分数不配对的区间大约 7 分，所以单次运行得到的 3 分差距分辨不出来，但配对之后有可能。如果区间仍然包含零，答案就是"在这个样本量下区分不出来"，再加上能定论所需要的题量，在 2 分的目标和常见的不一致率下，这个量级是几千题。seed 方差也要报：在小型推理 benchmark 上，运行之间的摆动超过大家在宣称的那个效果。

**问：思考预算可变的模型怎么评估？**

答：把预算当成候选的一部分，而不是模型的一部分。同一个模型的低算力档和高算力档是两个候选，质量是一条随开销变化的曲线，所以我会在两三个算力档上报告分数对平均输出 token 和成本的关系。两个操作要点：输出 token 上限要根据观测到的长度分布来定，并且报告截断率，因为一段被截断的推导会因为和能力无关的原因被判成错答案；解码策略要么对所有候选用同一套，要么用各家推荐的设置并说明是哪种，混着来会悄悄偏袒那个拿到了自己偏好配置的模型。

**问：污染怎么处理？**

答：我能控训练的地方靠预防，控不了的地方靠检测。训练这一侧，去污染是数据流水线的活：把 benchmark 题目及其改写做 n-gram 和近重复去除，但要说清它抓不住从一个被污染的教师模型蒸馏过来的情况。评估这一侧，因为我通常看不到别人的语料，只能靠黑盒证据：把 cutoff 之后的题目和难度匹配的 cutoff 之前的题目对比打分，跑 LiveBench 这类做了时间切分的 benchmark 或者 LiveCodeBench 的发布日期窗口，能拿到 token 概率的时候，就用 Min-K% 这类成员推断统计量，对照一份模型不可能见过的文本的参考分布。单看最强的一项核查是函数式孪生题：按同一份规范用新题重建一个 benchmark，在孪生题上大幅掉分就是污染的特征。另外我会留一个私有的内部题集，那是唯一一个"没泄漏"能被证明、而不只是被论证的题集。

**问：评估 agent 有什么不一样？**

答：三点不同。环境成了测量的一部分，所以容器要按 digest 钉住、网络策略要写明、重试次数要记（一个有 5% 题目需要重试的套件，报的是基础设施，不是能力）。结果验证必须强到能拒掉错误的解，对广泛使用的 agent benchmark 做的审计发现，有的测试套件弱到能接受错误的补丁，有的成功标准会把"什么都没做"判成成功，所以我在发布任何东西之前，会人工抽查一批判为通过的轨迹。指标也变了：单一成功率把成本和方差都藏起来，所以我会报任务成功率加步数加美元，可靠性用 pass^k，也就是 $k$ 次独立尝试全部成功的概率，而不是 pass@k，后者测的是允许重试时的覆盖率。

## 有坑的问题（追问是拉开差距的地方）

**问：我们的微调模型在目标 benchmark 上涨了 6 分，用户却说变差了。怎么回事？**

答：大概率是三种里的一种，而且它们可以区分开。**格式过拟合**：微调学到的是这个 benchmark 的答案形状，而不是能力，表现为一旦把同一个构念改成自由生成而不是多选来问，涨幅就消失了。**选择性泄漏**：这个 benchmark 被用来挑 checkpoint 和超参，所以报出来的数字是多次窥视之后的最大值，而不是无偏估计；判断的线索是开发过程中这个题集被查询了多少次。**局部涨、整体退**：benchmark 动了，别的地方悄悄掉了，所以要有一个回归组合（包含指令遵循、拒答行为和内部题集）在每个 checkpoint 上都跑一遍。确认实验很便宜：用另一种格式重建同一个构念，在一个从未被查询过的留出切片上评估，然后 diff 整个组合，而不是只看头条数字。

**更深一层：**这三种的修法不同，而且只有一种是模型的问题。格式过拟合在数据配比里修，选择性泄漏靠流程修（一个带查询预算的密封切片），整体回归靠训练修。在提出方案之前先诊断出你碰到的是哪一种，这才是价值的大头。

**问：我们在用模型给一个开放式 benchmark 打分。怎么让这个数字可信？**

答：先认证，再校正，第二步别跳过。认证是一个 meta-eval 集，几百对专家标注、在决策边界附近多采样，报告一致率和交换一致性，再加上对抗探针：空答案、常数答案、加长填充的答案，以及包含针对评分器的指令的答案。校正是统计手段：便宜的评分器照样跑全部 $N$ 题，另留一个小的 $n$ 题人工标注集，用 prediction-powered inference，把测出来的 judge 偏差加回 judge 的均值，无论 judge 多差它都是无偏的。这把预算问题从"我们能不能全标"重构成"多少个标签能换来可接受的区间"。另外要报评分器自身的错误率，因为比这个错误率更细的比较都撑不住。

**更深一层：**为什么光认证不够：一致性统计量告诉你 judge 以某个比例出错，但门禁需要的是对目标量的无偏估计，而不是对仪器的一份描述。PPI 把仪器测出来的误差转成一个校正项，这就是为什么一个平庸的 judge 加 200 个诚实标签，能打败一个没有标签的顶级 judge。

**问：同一个模型、同一个 prompt、温度为零，两次运行结果不一样。为什么？**

答：贪心解码原理上是确定的，在一套服务系统里则不是。归一化、matmul 和 attention 的 kernel 不是 batch 不变的，所以浮点归约的顺序取决于你的请求和什么被凑在一个 batch 里，而推导早期翻一个 token 会改掉后面的一切。同样症状的其他嫌疑：服务商在别名后面悄悄更新了模型、换了推理引擎或量化方式、或者解析器和沙箱本身不确定。补救按顺序是：钉住 revision 和引擎版本；如果可复现是硬要求，就用 batch 不变的 kernel 并接受吞吐的代价；或者接受运行间方差并把它测出来，反正误差棒也需要它。绝对不能做的是把单次运行的数字当成精确值报出去。

**问：你会怎么建一个两年后还有用的内部 benchmark？**

答：为刷新而设计，为"窥视次数的预算"而设计。题目持续从生产流量和专家那里来，每道题打时间戳，所有候选都能做对的题就退役（它们烧算力却不带信息）。切成两部分：一部分"内部公开"，供大家迭代；另一部分密封，带查询预算，每次对密封集的评估都记日志，在它上面挑一个 checkpoint 就消耗一次窥视。题目要带逐题的元数据以便切片（语言、长度、领域、难度），开放式题目存的是 rubric 而不是单一参考答案，这样评分标准是可调试的，另外要按计划给评分器重新认证。这个设计针对的失效模式不是内容过时，而是难度过时，所以针对难度补题比堆量更重要。

**问：评估网格是 12 个候选乘 15 个 benchmark 乘 5 个 seed。想办法把它变得付得起。**

答：四根杠杆，大致按省钱多少排序。**分阶段跑**：一个便宜的冒烟子集（跨 benchmark 取几百题）先粗排候选，只有活下来的才进完整网格，这一步通常能砍掉一半以上。**按协议哈希缓存**，这样改了打分或解析器之后重跑时，是给存下来的输出重新打分，而不是重新生成，这是迭代期间最大的一项节省。**按统计需求给每个 benchmark 定合适的样本数**：小 benchmark 需要多 seed，大的需要少 seed，所以到处都用 5 个 seed，等于在大套件上超支、在小套件上欠缺。**按题在多个服务商和 GPU 之间分片**，把成本压力换成墙钟时间压力。还有，砍掉的东西要报出来：如果安全套件只跑了 2,000 题里的 200 题，这就该写进报告，因为一个被悄悄截短的套件读起来像是全覆盖。

**问：公开 benchmark 和内部 benchmark 打架的时候你信哪个？**

答：信内部的，理由一句话说得清：它对得上我们在意的构念，而且它是唯一一个我能证明没被训练过的题集。不过公开那边的分歧仍然是信息。如果模型在公开榜上赢、在内部输，可能的原因是分布不匹配（我们的 prompt、我们的文档、我们的工具），或者污染抬高了公开的数字。如果公开输、内部赢，那这个模型可能在某个恰好适合我们的方向上做了特化，这也是个信号：该检查我们的内部题集是不是太窄了。不管哪种情况，部署由内部题集定，公开的数字留着讲对外可比性的故事。

## 常被答错的问题（陷阱）

**问：我们已经把 benchmark 的完全重复项从训练数据里删掉了，所以污染解决了。对吗？**

答：不对。精确匹配去重只抓住了最简单的一种，漏掉的是真正要紧的四种：近重复和改写、翻译版和重排版的镜像、格式泄漏（模型没见过题目却学会了这套测试的答案风格），以及从一个自身就被污染的教师模型蒸馏。它对选择性泄漏也毫无作用：训练里什么都没漏，但挑 checkpoint 的时候把测试集查了几百遍。站得住的答案会把去污染的说法和它的参数一起讲（n-gram 长度、归一化方式、近重复阈值），更重要的是配上黑盒证据：cutoff 之后题目上的表现、函数式孪生题上的表现，或者私有题集上的表现。

**更深一层：**这个陷阱危险在不对称上。去污染证据是关于一份只有训练方能查看的语料的宣称，而时间切分和函数式孪生题的检验谁都能跑。在面试里，伸手去拿那个可运行检验的人，是在表明他知道前一种宣称读者根本无法核实。

**问：MMLU 和 HumanEval 是标准，报这两个就行。对吧？**

答：它们曾经是标准，在前沿模型上已经饱和，也就是说候选之间的差距落在这个 benchmark 自身的标签错误和采样噪声之内。多选格式还有第二个问题：有不小比例的题目根本不看题干也能答得高于随机水平，所以这个格式测的一部分是选项辨别力，而不是产出答案的能力。如果你需要和已发表数字可比，那就重跑它们，但决策应该建立在有提升空间的 benchmark、同一构念的自由生成打分版本，以及你的内部题集上。另外，你依赖的任何多选题集，都要把"不给题干"的基线一起公布。

**问：agent 解决了 90% 的任务，那用户十次里会有九次看到它成功。对吧？**

答：只有当 pass@1 是按用户实际体验的方式测出来的才成立，而通常不是。$k \gt 1$ 的 pass@k 测的是覆盖率：$k$ 次尝试里至少一次成功的概率，当有验证器或者人来挑赢家时它是对的指标，对只有一次机会的用户就是错的指标。可靠性是 pass^k，$k$ 次尝试全部成功，而它按几何速度衰减：每次 90% 的成功率，到 $k = 8$ 时大约只剩 43%。如果报出来的数字本身是 best-of-k，或者来自一个结果验证很弱的套件，真实的单次成功率还要更低。

**更深一层：**这两个指标还指向不同的产品形态。pass@k 高而 pass^k 低，说明该做一个验证器在环的设计，也就是重试加检查器；而一个没法验证自己输出的系统，幻灯片上该放的就是 pass^k 那个数字。

**问：我们每题跑了一次贪心解码，所以数字是确定的，也是可比的。对吧？**

答：通常两者都不成立。贪心在一套批处理的服务系统里不可复现，因为 kernel 不是 batch 不变的；在各家推荐不同解码设置的情况下，它在候选之间也不可比。单次贪心运行还不给你任何方差估计，所以你没法就"差距是不是真的"说任何话。诚实协议的下限是：多个 seed 并报告离散程度，或者演示一次重跑能复现出完全相同的数字。

**问：把所有 benchmark 分数平均成一个数，好让管理层有一个单一指标。**

答：做指数是正当的，做朴素平均不是。不同 benchmark 的随机下限不同（四选一是 25%，自由生成是 0%），上限也不同，所以直接平均原始百分比是按量纲加权，不是按重要性加权；饱和的分项只贡献噪声；而不加权的平均仍然是一种加权，只是一种没被审视过的加权。要建就好好建：归一化、把权重说出来、剔掉饱和的分项、在题目上做 bootstrap，给指数和*名次*都加上区间，后者才是人们真正会读的东西。然后把每个 benchmark 的明细表摆在旁边，因为指数说不出到底是哪项能力动了。

**问：用手上最强的模型当 judge，它准确率最高。**

答：最强不等于认证过。专门针对 judge 的 benchmark 之所以存在，就是因为在错误答案听起来更好的、客观可核对的题对上，强的通用模型当 judge 表现平平；而一个和某个候选同门的强 judge 还会带来自我偏好偏差。正确的做法是：拿几个候选 judge 在人工标注的 meta-eval 集上量一遍，挑过了一致性门槛里最便宜的那个，用退化输入探它，确认常数答案或者填充答案拿不到高分，然后用一小份人工标注样本把它剩下的偏差在统计上校正掉，而不是假装它不存在。

**问：模型 A 全面得分更高，所以我们应该基于 A 来做。**

答：在什么上更高、代价多大、区间多宽。这句话变成决策之前要做三项检查：差距是不是超出了配对置信区间，还是说这其实是平局；比较有没有做成本对齐，因为一个多花五倍输出 token 的候选，该在前沿曲线上比，而不是在分数上比；benchmark 组合是不是对得上我们的负载，毕竟一个在竞赛数学上赢、在我们内部检索题集上输的模型，对一个检索产品来说是错的选择。Benchmark 用来筛候选，定盘的是内部题集和线上闭环。

**问：我们的微调模型超过了已发表的基座模型数字，所以它是个改进。**

答：不成立，因为那两个数字来自不同的流水线。已发表的数字用的是厂商的 prompt、few-shot 设置、token 预算和解析器，通常挑的是对自己有利的，还可能是另一个 benchmark 版本。唯一有效的比较，是在完全相同的协议下、在相同的题目上、在同一时间把基座模型重跑一遍，然后逐题配对比较。十次里有九次，重跑出来的基线会落在和已发表数字不同的地方，而且你那个改进的正负号也不总是保得住。

**更深一层：**这个陷阱也适用于团队内部的跨时间比较。benchmark 会被打补丁、harness 的默认值会变、服务商会在别名后面更新模型，所以半年前的一个数字用的是另一套协议，哪怕配置文件看起来一模一样。基线是重跑出来的，不是记住的，而协议哈希就是那个告诉你"该不该重跑"的东西。
