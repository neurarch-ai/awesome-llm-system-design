# 1. 澄清需求

跑任何一个 benchmark 之前，先弄清这个数字是*干什么用的*。下面是一段典型的对话，每个问题要么砍掉一部分工作量，要么改变协议。

**候选人：** 这个数字要驱动什么决策？选底座模型、追踪我们自己的训练 run、给发布做门禁，还是对外发布宣称？

**面试官：** 其中两个。我们要给一个产品线选底座模型，同时还在做继续预训练和微调自己的变体，所以需要知道每次训练 run 到底有没有真的改善什么。其中一部分数字最后会写进 model card。

**候选人：** 那我得知道这两类数字各自的受众是谁。内部选型的数字可以有噪声、可以便宜；model card 上的数字必须能被公司外的人复现。

**面试官：** 对，而且可以假设一定会有人来复现。

**候选人：** 产品真正在乎哪些能力？benchmark 的选择是最大的误差来源，一个和工作负载不匹配的组合，只会非常精确地测错东西。

**面试官：** 技术文档上的推理、代码生成、调用几个内部 API 的工具调用，还有长输入。多语言对两个市场很重要。

**候选人：** 候选模型是开放权重、纯 API，还是两者都有？这决定了我能不能用对数似然打分、能不能钉住一个版本、以及推理服务栈是不是我控制的。

**面试官：** 混合的。两个 API 模型，一个我们自己托管的开放权重模型。

**候选人：** 候选模型有没有可变的测试时计算，比如带预算、可以调高的推理或思考模式？

**面试官：** 有，其中两个有。

**候选人：** 那质量就不是一个标量，而是一条关于开销的曲线。我会报告分数对 token 和美元的曲线，而不是只报分数，否则比较会悄悄偏向那个我让它想得最久的模型。

**面试官：** 行。这要花我们多少钱？

**候选人：** 取决于题目数、每题的采样数和 seed 数。我会从你需要检测出的最小差异反推规模，而不是随便挑一个整数。

**面试官：** 我们需要能判断 2 分的差异。

**候选人：** 这一条对设计的约束比你前面说的所有东西加起来都大。

把问题陈述总结一下。**我们要设计一条 benchmark 评估流水线，在一个和产品工作负载匹配的能力组合上，给一组混合的候选模型（API 和开放权重，其中一些有可变的测试时计算）排序，用同一套协议追踪我们自己的训练 run，并产出经得起对外发布的数字。** 这条流水线必须能分辨大约 2 分的差异，控制污染，并且把成本和质量并排报告。

有两个结论立刻就能推出来，早点把它们说出口，这道题的大部分分数就到手了。

**结论 1：分数是一套协议产出的估计值，所以协议是结果的一部分。** 同一个模型在同一个 benchmark 上，随着 prompt 格式、few-shot 数量、打分模式、答案解析器、解码参数和输出 token 预算的不同，分数的波动能超过一代模型的差距。所以报告出来的产物从来不是一个裸数字，而是一个数字、一个区间，加上一个协议哈希，钉住 harness 的 commit、prompt 模板、模型版本、解码参数和采样数。如果同事没法从这条记录重新推出这个数字，那你并没有测量出什么，你只是生成了一个数。

**结论 2：公开发表的数字和你的数字不可比，所以每一个 baseline 都要在同一套协议下自己重跑。** 厂商 model card 上的数字来自另一套 harness、另一个 prompt、另一个 token 预算，而且通常是往有利的方向调过的。拿自己的微调版本去和对方公布的 baseline 比，是 benchmark 报告把内部决策做错的头号方式。规则是：一套 harness，一套协议，所有候选都跑，包括那个你以为自己已经知道分数的 baseline。

第三点虽然是范围界定而不是推论，也值得在面试里说出来：**benchmark 测的是模型，不是你的产品。** 它用来筛候选、追踪训练，不用来给功能做门禁，因为它不跑你的 prompt、你的检索、你的工具、你的用户。门禁在[评估一章](../evaluation/)里，好的回答会在面试官开口之前就把这条边界划清楚。
