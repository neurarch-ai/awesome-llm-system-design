# 8. 面试问答

面试官在生产环境 LLM 监控上真正会问的那些问题，按用途分组。最容易答错的那一组，才是面试真正分胜负的地方。

## 常问的

**问：生产环境里没有标签，你怎么衡量质量？**

答：衡量不了，只能用三类代理指标去估。第一，LLM-as-judge 跑在抽样出来的一片 trace 上，给 faithfulness（答案有没有被检索到的上下文支持）和 relevance（有没有回答到问题）打分。第二，grounding 检查把每个答案拆成原子论断，逐条对着日志里记下的检索上下文核验。第三，隐式用户信号：接受、丢弃、大改、立刻换个说法重问，这些行为信号密度高、也诚实，而且不花一分钱。这三样都不是准确率。它们只是估计值，而且在你拿人工标签把每一个都校准过、并报出 kappa 或 F1 一致性分数之前，它们都在骗人。

**问：具体怎么抓住一次幻觉飙升？**

答：拿 span 上记录的检索上下文，给每个响应算一个 groundedness 分数。把当前窗口汇总成一个无依据率，用 z-score 和基线比率比。$z_t$ 超过阈值才告警，而不是某一条响应被标记就告警。每次检索或模型变更之后都盯着这个比率的走势，对变化量告警。单独一条被标记的答案是噪声，比率的偏移才是信号。

**问：团队下周要换模型。你怎么防止一次悄无声息的回退？**

答：三步，按风险从高到低。第一，用冻结评估集跑一遍候选版本；如果分数掉到可接受区间以下，在任何用户看到之前就拦住发布。第二，冻结评估过了，就把百分之五到十的线上流量路由到候选版本（金丝雀），至少覆盖一个完整流量周期，把代理分数、延迟、成本和用户反馈跟对照组比。第三，可选：在金丝雀之前，让候选版本并行跑影子模式，做零风险的输出 diff。发布排期要和人力配合好，金丝雀出事的时候有人能立刻响应。

**问：为什么不干脆每个请求都跑一遍 judge？**

答：成本。一次 LLM judge 调用的开销大致和生成调用本身相当，所以每个请求都判一遍，等于服务账单直接翻倍。按我们百分之十五的观测预算算，最多只能判百分之十五的流量。正确做法是有策略地抽样（对可疑的尾部超额抽样），而不是均匀抽；再用一个便宜的 encoder 或者 NLI 模型做第一遍过滤，只把被标记的那一小部分送给昂贵的 judge。

**问：你会建哪些一等看板？**

答：六个我认为没得商量的看板：延迟分位数（p50、p95、p99 和 TTFT 分开看，不看均值）；每请求的成本和 token 数；按错误类别分的错误率和超时率；judge 分数的滚动平均加趋势线；无依据率加 z-score 告警；以及护栏触发率（拦截率、越狱命中率、拒答率）。护栏那几个比率之所以重要，是因为拒答率上升是一种无声的劣化：被拦掉的答案根本不会进入质量打分，所以质量看板一片健康，而正常流量正在被误杀。

## 有陷阱的（把人区分开的追问）

**问：judge 分数一个月比一个月高。这是好消息吗？**

答：不一定。judge 自己可能在漂：它是拿三个月前采集的人工样本校准的，从那之后领域、prompt 或者流量构成都变了。一月份 kappa 0.82 的 judge，到三月份可能已经在系统性地往高里判。报分数的时候要把 judge 与人工的一致性一起报；如果 kappa 在跌而分数在涨，那是仪器在骗人。定期在真实流量上采新的人工标签，重新校准。

**仪器为什么会漂：** 校准本质上是一个从 judge 分数到人类判断的映射，而这个映射只在它被测量的那个分布上成立。流量构成一变，judge 照样输出自信满满的分数，但它犯的错已经不是当初校准所涵盖的那些错了，于是报出来的数字和真实质量悄悄地脱了钩。分数本身发现不了这件事，只有新的人工标签能。

**问：你只对百分之五的流量做 judge。CEO 问你质量有没有在变好。你怎么回答？**

答：告诉他 judge 分数的趋势是目前能拿到的最好估计，同时把 kappa 一致性分数一起给出去，让他知道这个估计该信几分。另外再报隐式行为信号（接受率、重试率），它覆盖全量流量，不额外花钱，而且比 judge 更难被刷。这两个信号如果一致，那就有了互相印证的证据。如果它们背离，先去查清楚，别急着宣布质量变好了。

**为什么这个交叉验证撑得住场面：** 两个信号的失效方式是独立的。judge 会漂，也会被那种形式漂亮的输出骗过去，但它打分的是一个受控样本；行为信号单看每一次都很噪，但它们来自不为任何指标表演的真实用户，而且覆盖全量流量。能骗过其中一个的错误模式，很难同时把另一个往同一个方向骗，正因如此，两者一致才算证据，而不是巧合。

**问：跟 RAG 系统比，agent 系统在记什么、查什么上有什么不同？**

答：对 agent 来说，检索到的上下文被换成了一串工具调用，带参数、结果和错误。你需要的是一次工具调用一个 span，而不只是一个请求一个 span，因为故障可能出在六步计划里的第三步，没有步级粒度就根本找不到它。grounding 检查也变成了计划连贯性检查：agent 有没有用正确的参数调用正确的工具，它的结论是不是从工具返回的结果里推得出来的？冻结评估集也更难维护，因为 agent 的 trace 比单轮问答更长、变化更大。

**问：你的无依据率 z-score 告警每周一早上同一时间准时响。是模型坏了吗？**

答：大概率不是，这是固定基线 z-score 的经典翻车方式。z-score $z_t = (\text{rate}_t - \mu) / \sigma$ 假设基线均值 $\mu$ 和标准差 $\sigma$ 描述的是一个稳定的单一分布，但生产流量是有季节性的：工作日早高峰的查询构成（更多首次使用的用户，不同的主题）可能和基线里平均进去的周末窗口完全不同。比率是真的变了，z-score 也是真的飙了，但模型压根没变。修法在机制层面，不在调阈值：把基线算在一个对齐的窗口上（同一个"周内小时"），或者跟一个做过季节性调整的期望值做差，这样告警的就是剔除已知周期性之后的残差，而不是周期性本身。面试官用这道题看你有没有意识到，漂移检测靠的是一个平稳性假设，不是一个魔法阈值。

**问：grounding 分数看着挺好，用户还是不满意。你去哪儿找问题？**

答：grounding 只检查论断有没有被检索到的上下文支持。它抓不到这些：检索错了上下文（模型照着对的表格、错的文档作答）；答非所问（技术上忠实，但跑题了）；语气或格式不对（太长、太技术、语域不合适）；上下文过期（那份检索到的文档在半年前是准的）。要拿显式反馈、重试率和修改率交叉验证，才能把失败模式定位出来。

**grounding 为什么结构性地看不见这些：** 它是一个条件检查，衡量的是"给定上下文，论断是否成立"，所以它只能衡量对检索器返回的那份东西的忠实度。这个条件之上游的一切（有没有检索到对的文档，那文档现在还成不成立）和与它正交的一切（相关性、语气、长度）都落在被测量的量之外，所以一个满分的 grounding 分数完全可以配上一个毫无用处的答案。

**问：影子模式和金丝雀看着差不多，都是拿线上流量跑候选版本。差别到底什么时候才真的要紧？**

答：机制上的差别在于谁看到了输出。影子模式里候选版本处理的是真实请求，但它的答案跟对照组 diff 完就丢掉，用户风险为零；金丝雀里，一片真实用户实实在在收到了候选版本的答案。就这一个差别，决定了两者各自能测到什么：影子给你的是输出的分歧度（新模型有多不一样），但拿不到用户反应，因为压根没有用户见过那个输出；金丝雀给你的是行为信号（接受、重试、修改、投诉率），那是生产环境里最接近 ground truth 的东西。当你过发布关卡所需要的那个指标就是用户行为时，这个差别就要紧了：影子流量再多也生不出它来。反过来也一样要紧：当错误不可逆时（比如一个真的会执行动作的 agent），在 diff 证据足以支撑"让人看到它"之前，影子是唯一安全的选项。

## 常答错的（那些坑）

**问：看板上直接报响应延迟的均值行不行？**

答：不行。均值把尾部藏起来了，而在流式 UI 里用户感受到的恰恰是尾部。一个"无缝替换、效果更好"的模型，如果把 p99 延迟从 800ms 抬到 3000ms、TTFT 翻倍，那对大多数用户来说就是回退，哪怕均值几乎没动。永远把 p50、p95、p99 和 TTFT 分开报。TTFT 是流式场景下被感知到的延迟；p99 是你服务得最差的那批用户的真实体验。

**均值为什么藏得住尾部：** 延迟分布严重右偏，几千个快请求里混进少数几个好几秒的请求，几乎推不动平均值。到了一定规模，哪怕百分之一的请求也是一个很大的用户绝对数；再加上每个用户一次会话里会发很多请求，某个用户至少撞上一次 p99 的概率会逼近必然。

**问：点赞率高，就说明质量好，对吧？**

答：不对。会去点那个赞踩控件的，永远只是极小一撮自选样本，而且偏向特别满意和特别生气的两端。点击率低本身什么都不说明。要拿隐式信号交叉验证：修改率、重试率、放弃率覆盖的是全体用户。也要拿 judge 和 grounding 分数交叉验证。点赞率高同时重试率也高，那是一个需要去查的矛盾，不是一个值得庆祝的胜利。

**选择偏差为什么会把这个数字腐蚀掉：** 会点击的人不是随机样本，所以这个比率估计的是"会点击的那群人"的情绪，不是你全体用户的情绪。更糟的是，点击人群一变（改了个 UI，来了一批新用户），比率就会动，而质量一点没变，也就是说这个指标可以因为跟它声称要衡量的东西完全无关的原因，往任何一个方向走。

**问：换完模型跑了冻结评估集，分数看着没问题。可以发了吗？**

答：还不行。冻结评估集会过期：它是从过去的流量里搭出来的，未必覆盖得住当前流量的失败模式。一个新主题簇上的细粒度回退、团队新加支持的某种语言、上个月才冒出来的一种 prompt 写法，在一个陈旧的评估集里都不会显形。冻结评估是一道必要的关卡，不是充分的。过了它之后，还要在线上流量上跑金丝雀，才能全量发布。

**过期为什么是结构性的，而不是谁偷懒：** 评估集是从一个移动的分布上取的一个固定样本，所以哪怕没人碰它，它的覆盖率也在衰减。而且因为之前每一次改动都是一直调到这同一个集合通过为止，系统等于是被专门挑选成"在这些用例上好看"的（古德哈特定律），这会让冻结分数随时间推移相对线上真实质量越来越偏高。

**问：护栏的拦截率很稳，那安全是不是就没问题了？**

答：不一定。拦截率稳，也可能意味着危险输出照样没被抓住，一路放了过去。真正危险的是那些没有任何护栏标记过的有害输出。除了拦截率看板，还要在放行流量（没被拦下来的输出）上做抽样的安全性重扫，去接住护栏漏掉的那些。从机制上说，拦截率之所以是错的量具：它衡量的是护栏对着"它已经能识别的东西"的召回率，而不是对着真实的有害发生率，所以对任何分类器从没被训练过的新型攻击，它是全盲的。一族过滤器认不出来的越狱手法，产生的是零次拦截和一条完美平稳的拦截率曲线，与此同时有害输出正在往外流。只有把放行流量抽样送进一个独立的重扫（最好是另一个模型，或者人），才能估出主护栏判为安全的那部分流量上的漏检率。
