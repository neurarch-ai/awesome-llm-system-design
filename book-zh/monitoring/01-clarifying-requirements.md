# 1. 澄清需求

动手设计之前，先把系统必须做到的事钉死。下面每个问题，要么能砍掉一块工作量，要么会改变设计。注意这些问题没有一个是关于工具选型的，问的全是监控系统需要满足的契约。

**候选人：** 我们要监控的是哪种 LLM 应用？RAG 系统（检索增强生成：模型先检索文档，再基于文档作答）、带工具调用的 agent，还是单次补全的接口？

**面试官：** 一个 RAG copilot。每个请求先检索一组文档，拼成 prompt，再生成一个应当基于这些文档的答案。

**候选人：** 答错的代价有多大？一个坏回答是凌晨三点要被叫醒的级别，还是放进周报看板里回顾一下就行？

**面试官：** 这是企业级客服 copilot。一个自信满满但错误的回答会损害客户信任。我们希望在几小时内、而不是几天内，抓住一次质量回退（相对于上一版本的可度量的质量下降）。

**候选人：** 模型和 prompt 实际多久变一次？

**面试官：** prompt 一周会改好几次。模型可能一个季度换一次，但我们希望有能力换得更勤。

**候选人：** 观测的预算是多少？每个请求都跑一次 LLM judge（再调一次模型给答案质量打分），推理开销差不多要翻倍。

**面试官：** 监控最多可以花到服务成本的百分之十五。不可能每次调用都打分。

**候选人：** 有没有延迟到达的 ground truth？比如客服人员会不会采纳或者拒绝 copilot 的答案，工单会不会被重新打开？

**面试官：** 有。人工客服要么采纳并发送这个答案，要么丢弃它。这个信号有五到三十分钟的延迟。

---

把问题陈述总结一下。**我们要给一个生产环境的 RAG copilot 设计可观测层**，每个请求都会检索文档并生成一个有依据的答案。答案必须可追溯，质量必须在没有预先标注的生产数据的情况下持续估计，一次幻觉飙升（一批自信但没有检索文档支撑的回答集中出现）或者一次 prompt 修改后的回退，必须在几小时内浮出水面。观测预算大约是服务成本的百分之十五，所以必须抽样。

由此马上能推出两个结论，早点把它们说出来，就是这道题的大部分得分点：

- **生产环境没有 ground truth，所以质量永远是估计出来的，不是量出来的。** 在有标签的评估集上算的那种准确率，线上不存在。手上有的是代理信号：LLM judge 在抽样上给 faithfulness 打分，grounding 检查把每条论断和我们记录下来的检索上下文做比对，再加上隐式的用户动作（采纳、丢弃、重试）这种免费的行为信号。看板上的每一个数字，在被人工标签校准之前，都只是代理指标。
- **贵的检查不能在每个请求上同步跑。** 预算是百分之十五，而一次 LLM judge 的开销和生成本身差不多，那就意味着最多只能给百分之十五的流量打分。热路径上只能便宜地把 trace 发出去，所有重的检查，judge、grounding 打分器、安全复扫、人工审核队列，全都在这条 trace 流上异步跑。后面每一节里的架构决策都是由这一点决定的。
