# 3. 预算、延迟与尾部

## 输出长度现在是一个随机变量

对不思考的模型来说，回复长度大致可预测，波动也不大。对思考模型来说，同一个 prompt
可能产出 400 个 token，也可能产出 12,000 个，而且分布是右偏的：大多数请求靠近众
数，少数请求长好几倍，而正是这少数请求主导了下游的一切。

两个数字就能描述损害。令 $S$ 为服务时间（输出 token 数除以 decode 速率）。均值
$E[S]$ 决定容量。**变异系数的平方** $C^2 = \text{Var}(S)/E[S]^2$ 决定尾部，因为
单服务台队列里的排队延迟随二阶矩增长：

$$E[W] = \frac{\rho}{1-\rho} \cdot \frac{E[S]\,(1 + C^{2})}{2}$$

这就是 Pollaczek-Khinchine 公式，它的实际含义很直白：**两个平均服务时间相同的负
载，p99 可以天差地别，而思考负载永远是尾巴更肥的那个。** 在固定利用率下，方差翻
倍，延迟里的排队分量就翻倍。这也是为什么"加机器就行"在这里很贵：$\rho/(1-\rho)$
这个因子意味着，要让尾部保持体面，集群必须跑在远低于饱和的水平。

## 这对设计意味着什么

- **给每个请求设预算。** 最大思考预算是一条延迟保证，不是一个成本偏好。没有它，
  一个病态的请求就能占着一个槽位好几分钟。
- **截断必须是设计出来的行为。** 错误的版本是在思考中途悄悄切断输出，返回一堆垃圾
  （而且在评估里会被记成答错，见
  [Benchmark 一章第 3 节](../benchmark-eval/03-the-harness.md)）。正确的版本是在
  预算边界上加一个强制作答的步骤（"你的思考预算已经用完，现在给出你最好的答案"），
  或者显式拒答并走一条兜底路径。
- **准入控制胜过无限队列。** 过载时，要么丢弃，要么降级：直接走不思考的路径，而不
  是把一个思考请求排在另外二十个后面。一个快但差一点的答案，通常好过一个用户已经
  走了才到的慢而正确的答案。
- **把你承诺的尾部分开。** 首 token 延迟现在已经不能代表什么了，因为模型可能在第
  一个可见 token 之前思考很久。要承诺、度量、告警的是首个可见 token 的时间、总时
  间，以及撞到预算上限的请求占比。

## 队头阻塞才是真正的运维故障

一个长思考请求会在整个持续期间占着一个 KV 槽位。在连续批处理下，这意味着：

- **槽位占用是偏斜的。** 少数几个长生成就能占掉大部分 batch，其他所有人的有效并发
  随之崩掉。
- **短请求排在长请求后面。** 经典的队头阻塞，而常规的修法（最短作业优先）用不了，
  因为事先不知道长度。
- **显存压力随上下文飙升。** 长思考就是长上下文：一次 12,000 token 生成的 KV cache
  就是 [KV Cache 一章](../kv-cache/)算的那个尺寸，而这笔开销落在同一个集群上。

三种缓解手段，按该先试哪个的顺序：

1. **按预算类别分队列（或分集群）。** 最便宜的结构性修法：短请求永远不会等在长请求
   后面，因为它们根本不在同一个队列里。代价是牺牲一点效率，换来一条可预测的尾巴。
2. **预测长度。** 在 prompt 上跑一个便宜的分类器，给出一个粗略的类别（短、中、长），
   这就大致恢复了最短作业优先的调度，而且很方便的是，它和
   [第 4 节](04-allocation-and-routing.md)里驱动 effort 路由的是同一个分类器。
3. **抢占。** 队列积压时，暂停并驱逐一个长生成，稍后恢复。这在服务层是实打实的工
   作量，只有到了一定规模才值得做，但它能把一条硬尾巴变成软尾巴。

## 流式输出与感知到的尾部

用户体验到的不是 token 分布，而是不确定性。两个便宜的改动，买到的比一大堆工程还多：

- **思考期间流式推一个进度信号**（步骤计数、当前步骤的摘要，或者一个普通的指示器）。
  真实延迟没变；放弃率变了。
- **支持取消，并把它记账。** 被取消的请求应该停止生成，但仍然要被记录，token 一个
  不少，否则成本模型会悄悄少算。

要不要把推理 trace 本身流式推出去，是产品和安全决策，不是系统决策：trace 里可能
包含产品不该展示的中间内容，而且对任何读到它的人来说，它都是蒸馏的原材料。

## 什么时候用哪个手段

| 用什么 | 什么时候 | 代替什么 |
|---|---|---|
| 每请求硬性 token 预算 | 生产环境里永远要有 | 可以无限期占着槽位的无界生成 |
| 边界上强制作答 | 任务必须返回点东西 | 静默截断，返回格式错乱的输出，评估记为失败 |
| 按预算类别分队列 | 混合流量，且短路径上有延迟承诺 | 单队列，短请求继承长尾 |
| 长度预测加优先级 | 流量足够训一个分类器，并且尾部确实有问题 | 纯 FIFO，在这里对什么都不是最优的 |
| 抢占 | 大集群、严格的尾部 SLO、有工程预算 | 靠加容量掩盖一个方差问题 |
| 准入控制和降级 | 过载时段 | 无限排队，让所有人的 SLO 一起挂掉 |
| 进度流式输出 | 任何面向用户的思考路径 | 一个转圈图标加一份侥幸 |

## 实现上的坑

| 问题 | 症状 | 修法 |
|---|---|---|
| 没有预算上限 | 偶尔出现几分钟的请求；槽位被绑架 | 每请求设上限；对撞上限的占比告警 |
| 在上限处静默截断 | 答案格式错乱，评估把它们记成推理错误 | 强制作答步骤或显式拒答 |
| 只跟踪 p99 不建模 | 集群按平均服务时间配置；负载一上来尾部就崩 | 用 $E[S]$ 和 $C^2$ 来配置；利用率保持在远低于饱和 |
| 所有预算共用一个队列 | 短的交互式请求继承长尾 | 预算类别队列或优先级方案 |
| 把 TTFT 当延迟 SLO | 指标看起来没问题，用户却在等 | 分别度量首个可见 token 的时间和总时间 |
| 取消没有记账 | 成本模型和账单对不上 | 记录被取消请求已生成的 token |
| 预算凭感觉定 | 要么落在曲线的平坦段，要么有一堆截断 | 在自己的流量上测准确率对预算的曲线，把预算定在拐点 |
