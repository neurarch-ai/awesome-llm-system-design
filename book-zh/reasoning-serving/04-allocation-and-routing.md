# 4. 分配预算

一旦思考变成按请求购买的东西，系统就是一个带花费维度的路由器。这一节讲的是怎么
把这笔钱花出去的算术。

## 三种策略，以及各自什么时候赢

**永远思考。** 每个请求都拿一个大预算。简单，贵，而且对大多数根本不需要思考的请求
来说，它把延迟尾部撑大了。

**按 effort 路由。** 在生成之前，由一个分类器给每个请求分配一个预算类别。便宜，
上限是分类器的准确率：本该走长路径却被路由到短路径的请求，质量就这么丢了，而且
除非度量结果，否则你永远不会知道。

**级联。** 先跑便宜路径，检查答案，只在失败时升级。有验证器的时候它是最强的策略，
而且它有一个另外两种没有的性质：被升级的请求实际上得到了两次独立尝试，所以解决
率可以超过永远思考的策略，成本却只是后者的一小部分。

在路由和级联之间做决定的那笔账，按每个请求算：

$$C_{\text{cascade}} = c_{\text{short}} + c_{\text{verify}} + (1 - a)\,c_{\text{long}}, \qquad C_{\text{always}} = c_{\text{long}}$$

其中 $a$ 是便宜路径能给出可接受答案的请求占比。级联胜出的条件是

$$a \gt \frac{c_{\text{short}} + c_{\text{verify}}}{c_{\text{long}}}$$

如果短路径的成本大约是长路径的十分之一，验证器又便宜，这个阈值就落在 15% 附近：
**只要便宜路径能处理五个请求里的一个，级联在成本上就赢过永远思考。** 难点全在接受
测试上，下一节讲的就是它。

## 在拿到答案之前判断难度

按 effort 路由需要在准入时就有一个难度信号。按成本排序：

| 信号 | 怎么做 | 成本 | 注意 |
|---|---|---|---|
| 调用方声明 | 产品把某个入口标记为高风险 | 免费 | 调用方会过度声明；需要配额 |
| 对 prompt 的规则 | 任务类型、长度、有没有代码或数学 | 几乎免费 | 脆弱，但是一个很强的基线，而且完全可解释 |
| 小分类器 | 用日志里的（prompt，便宜路径是否解决）对训练 | 便宜 | 需要第 1 节里的结果日志 |
| 模型自报 | 先让模型给难度打个分 | 多一次调用 | 校准很差；当成一个弱特征用 |
| 便宜路径试一次 | 直接试，然后检查 | 便宜路径本身的成本 | 这就是级联，而且通常是更好的答案 |

最后一行是点睛之笔：**便宜的一次尝试加一个验证器，比任何难度分类器都更好的难度
分类器**，因为它度量的是你真正关心的东西（便宜路径能不能解决），而不是去预测它。
预测只在没有验证器、或者升级带来的延迟不可接受时才用。

## 自适应停止

预算也可以在一个请求内部自适应地花：

- **答案稳定就停。** 采样几个短的续写；如果它们一致，就停。这是把 self-consistency
  当停止规则用，而不是当投票规则用，它在占多数的简单请求上省得最多。
- **验证器通过就停。** 对可验证的任务，一直生成到某个样本通过或者预算耗尽，这就把
  预算换算成了期望尝试次数。
- **在边界上强制作答。**[第 3 节](03-budgets-and-latency.md)讲过了，它是一个降级
  答案和一个坏掉的答案之间的区别。

推理时的显式预算控制（压掉"思考结束"token 来强制多想，或者注入一个作答 prompt
来强制少想）是一种有文献记载的技术，不是野路子
（[s1: Simple test-time scaling](https://arxiv.org/abs/2501.19393)），当服务商没
有暴露预算参数时，靠的就是它。

## 模型路由和预算路由是可以组合的

维度有两个，不是一个：**用哪个模型**和**思考多少**。它们相互影响，而常见的错误是
把它们混成一个。

| | 小模型 | 大模型 |
|---|---|---|
| **不思考** | 抽取、分类、格式化 | 知识密集的单轮回答 |
| **思考** | 往往性价比最高：小推理模型配一个验证器 | 困难的多步问题，答错的代价很高 |

左下角那个格子是大量生产价值所在，也是面试里注意到它会加分的地方：一个小模型，给
它思考的空间，再配一个验证器来兜住它的错误，经常能打败一个立刻作答的大模型，成本
只是零头。通用的路由机制在
[成本优化一章](../cost-optimization/03-routing-and-cascades.md)里；本章加上的一点
是，升级的轴现在除了模型大小，还有每请求花费。

## 什么时候用哪个

| 用什么 | 什么时候 | 代替什么 |
|---|---|---|
| 永远思考 | 高风险、低流量、没有验证器、能容忍延迟 | 在混合负载里为每个请求都付尾部的钱 |
| 按规则做 effort 路由 | 今天就要上线，而且有明显的任务类型信号 | 等分类器训好了再动手 |
| 按分类器做 effort 路由 | 流量和结果日志够训练 | 模型自报难度，校准很差 |
| 带验证器的级联 | 任何可检查的任务，且便宜路径能解决相当一部分 | 预测 effort，那是在猜级联能直接量出来的东西 |
| 带验证器的 best-of-n | 延迟预算允许并行采样，且验证器够强 | 串行思考，当墙钟时间比 token 更重要时 |
| 自适应停止 | 思考路径里有一条长长的简单请求尾巴 | 一刀切的固定预算 |
| 完全不思考 | 抽取、格式化、回忆、受延迟约束的 UX | 因为 benchmark 分高就上推理模型 |

**一个完整的例子。** 一个混合负载（代码修复、数据抽取、解释）一开始跑的是永远思
考，又慢又贵。团队先给结果做埋点，因为没有结果就没法比较任何策略。抽取换成不思考
的小模型加约束解码，因为在那里斟酌买不到任何东西。代码换成级联：先来一次短尝试，
用仓库自己的测试当验证器，失败再升级，这让解决率超过了永远思考的基线（被升级的请
求有两次尝试），同时每个解决任务的成本砍掉了一半以上。解释没有验证器，所以保留一
个适中的固定预算，取在实测的准确率对预算曲线的拐点上，边界处加强制作答步骤。决定
哪个入口走哪条路的分类器每月用日志里的结果重训一次，整套东西汇报的是每个解决任务
的成本，而不是每请求成本。
