# 8. 面试问答

## 常被问到的

**问：我们换成了推理模型，质量上去了，p99 延迟变得没法预测，成本翻了三倍。说说你
会怎么做。**

答：三步，按顺序来。**先把结果埋点做了**：记录 token 数、墙钟时间、验证器有没有接
受、以及任务最终有没有被解决，因为从这一刻起所有的策略比较都要落在每个解决任务的
成本上，没这些数就算不出来。**再把尾部框住**：每请求一个硬性的思考预算，在边界上
接一个强制作答的步骤（绝不能静默截断），按预算等级把队列分开，让短请求不必排在长
请求后面，再加上准入控制，过载时降级而不是排队。**然后才做分配**：抽取和格式化走
不思考的那条路，可验证的任务走级联（先来一次便宜的尝试，跑检查器，失败了再升级），
不可验证的任务保留一个固定预算，取在实测的准确率与预算曲线的拐点上。对外报的主指
标是每个解决任务的成本和 p99，成对报。

**问：为什么一打开思考，p99 就比均值恶化得厉害得多？**

答：因为排队延迟取决于服务时间的二阶矩，不是一阶矩。对一个利用率为 $\rho$ 的队列，
等待项大致按 $\frac{\rho}{1-\rho}\cdot\frac{E[S]\,(1+C^2)}{2}$ 走，其中 $C^2$ 是平
方变异系数。思考让输出长度的分布变成长尾，$C^2$ 就上去了，于是即便平均服务时间没
变，尾部也跟着上去。上面还叠了第二个结构性效应：长生成占着 KV 槽位，有效批就塌了，
短请求排在它们后面，这就是队头阻塞。对应的修法也是两条：把运行利用率降下来、给预
算封顶以收窄尾巴；把队列分开，或者预测长度，别让短请求卡在长请求后面。

**问：测试时计算该用串行还是并行？**

答：串行（拉长一条链）不需要额外机制，代价是延迟，因为 token 是一个个串着出来的。
并行（k 个样本）代价是 token，延迟增加不多，因为样本是同时跑的，但没有办法挑出赢
家它就毫无用处：重复采样提高的是"存在*某个*样本是对的"这个概率，只有验证器才能把
它变成一个能交付的答案。所以答案取决于有没有检查器。可验证的任务、又对延迟敏感：
并行加执行器。没有验证器：串行加一个测量过的预算。而且这个配比应该按难度自适应，
而不是写死，这正是测试时扩展那批文献的发现。

**问：思考预算怎么定？**

答：测出来，别猜。在自己的真实流量上、在若干个预算档位上跑一遍准确率与预算的曲线，
找到它变平的地方，把封顶设在拐点。然后盯两个运营指标：撞到封顶的请求占比（在涨说
明分布漂了，或者封顶太紧），以及撞顶时的截断行为（必须是强制作答，不能是把 trace
剪断）。不同的任务类别配不同的预算，因为拐点是跟任务走的：竞赛风格的数学题能一直
往上涨很久，抽取任务就不行。

**问：把推理模型和非推理模型放在一起比，正确的做法是什么？**

答：成本对齐，至少也要成本标注。一个多花十倍输出 token 的模型，不应该只比分数，所
以这个比较是一条前沿曲线：分数对每任务的 token 数和美元数，延迟在旁边一并报。同一
个模型的两个预算设置，就是两个候选。而且比较应该在自己的数据上逐条配对做，还要带
区间，因为推理类 benchmark 又小又吵，单次跑出来的差距经常不是真的（见
[Benchmark 一章](../benchmark-eval/06-statistics-and-leaderboards.md)）。

## 有坑的

**问：你的级联有 20% 的请求会升级。流量一变，升级率变成了 60%。会发生什么，你怎么
办？**

答：长的那条路被打满，而长路又恰好是高方差的那条，于是所有人的 p99 都迅速恶化：这
是一次复合故障，一个质量信号（便宜那条路失败变多）变成了一次容量事故。立刻要做的
缓解是给升级率封顶，也就意味着明知故犯地让一部分请求只拿到便宜的答案，同时在准入
层丢弃或降级，而不是让它们排队。然后再诊断：是输入分布变了，是底下那个便宜模型被
人换了，还是验证器变严了？结构性的修法是：升级应该是一项有自己配额的预算化资源，
而不是验证器判个不通过就无限展开的后果。

**再深一层：**这就是为什么升级率应该和延迟并排放在同一块看板上。它同时是你手里最
早的质量信号（便宜那条路失败变多了），又是容量问题的先行指标，而多数团队是把它当
后者、而不是当前者发现的。

**问：用奖励模型做 best-of-16，答案反而比 best-of-4 差。怎么会？**

答：针对一个不完美的验证器施加的优化压力。在 16 个样本上取学习得来的奖励的 argmax，
是在更卖力地搜索"奖励模型高估的那类东西"，所以过了某个 k 之后，你越来越多地是在挑
奖励模型的伪影，而不是在挑正确答案。诊断办法：看看被选中样本的奖励是不是在涨、而人
工或执行器的一致率在跌，再跟"从同一批样本里随机挑一个"做个对照。修法是换一个更强
的、或者可执行的验证器，加一个 KL 风格的惩罚项拉住基础策略的似然，做验证器集成，
或者干脆把 k 卡在交付质量曲线的峰值处，而不是覆盖率的峰值处。

**问：不知道一个请求要跑多久的时候，怎么做调度？**

答：没有任务长度就做不了最短作业优先，所以要么把它估出来，要么让自己不需要它。估
出来：拿一个便宜的分类器读 prompt，预测一个长度类别，这就恢复了一个近似的优先级
序，顺带还能当 effort 路由的信号。绕开：按预算等级切成不同的队列，每个队列内部方差
都很低，短请求永远不会坐在长请求后面，代价是集群效率打点折扣。规模再大一些，就加
上抢占，队列积压时可以把一个长生成挂起。在面试里，能指出"FIFO 在这个场景下对任何目
标都不是最优"、以及"修法要么是预测要么是分区"，就是对方想听的答案。

**问：产品那边想把推理 trace 展示出来。从系统角度怎么看？**

答：流式推送一个进度信号几乎是免费的，而且能实打实改善体感延迟；把原始 trace 流出
去则是另一个决定，带三个后果。安全：trace 里有探索性的内容，包括对那些最终答案正
确拒答了的东西的推理，所以它需要自己的一遍审核。竞争：公开的 trace 就是把你的行为
蒸馏进别人模型的原料。产品：用户会把 trace 读成一个承诺，一条和答案自相矛盾的
trace 比没有 trace 更糟。多数团队走的中间路线是给出摘要过的、或者带步骤标签的
trace，而不是原始的那份，这样既留住了延迟上的好处，又不用承担暴露的风险。

## 常被答错的

**问：推理模型更好，所以我们应该把所有请求都走它。**

答：不能一刀切。思考起作用的地方，是模型能找到、并且能*认出*一个比它第一反应更好
的答案。在事实召回上它什么都加不了（知识要么在权重里要么不在，该做的是检索），在
抽取和格式化上它只增加漂移和成本，而在受延迟约束的交互界面上，尾部就是产品本身。
它还会让评估变得有误导性：推理模型赢 benchmark，有一部分原因就是它花得多，所以比较
必须成本对齐。站得住的立场是一个混合负载：多数请求那条路不思考，预算花在能改变结
果的地方。

**问：我们采 8 个候选取最好的，所以质量应该接近 pass@8 那个数。**

答：只有在选择器有那么好的时候才成立。pass@8 衡量的是这 8 个里有没有*任意一个*是对
的；交付质量等于这个覆盖率乘以"在存在正确样本时你的选择恰好挑中它"的频率。选择器
平庸的话，你花的钱大半就蒸发了：覆盖率接近 0.98，配一个六成时候选对的选择器，交付
出去大约是 0.6。这个落差就是"该把钱投在验证器上而不是多采样本上"的论据，也是"只要
输出能跑就优先用执行器而不是模型裁判"的论据。

**再深一层：**同一个区别也解释了为什么有单元测试的团队能从测试时计算里榨出多得多
的东西：执行器几乎是一个完美的选择器，所以他们的交付质量能跟住覆盖率，而其他人都
被自家的裁判封住了顶。

**问：我们给思考预算封了顶，所以尾部已经处理好了。**

答：封顶框住的是*服务时间*的尾巴；它框不住排队延迟，那是由方差和利用率驱动的，它
也修不了队头阻塞。一个跑在高利用率上的集群，就算服务时间封了顶但依然多变，p99 照样
守不住，因为 $\rho/(1-\rho)$ 这个因子占主导。封顶只是三个控制手段之一，另外两个是
把目标利用率降下来、以及按预算等级给队列分区。另外，封顶而不接强制作答的步骤，等
于把延迟离群点转换成了畸形答案，这比慢是更糟的失败。

**问：加 GPU 加到 p99 好看为止不就行了。**

答：你确实可以花钱把自己往 $\rho/(1-\rho)$ 曲线下方买，但这是手里最贵的一根杆子，
因为方差项意味着你得跑在离饱和相当远的地方才动得了尾部。其他每一根杆子都更便宜：
预算封顶直接收窄尾巴，按预算等级分队列消掉阻塞，路由把那些本来就不需要思考的请求
拿走，而级联干脆把长路从大多数流量里整个移除。容量是正确答案，但只在那些之后才是，
capstone 的数字说明了为什么：在同一个集群上，光是改策略就把每个解决任务的成本挪动
了两倍以上。

**问：每请求成本降下来了，所以这次改动是成功的。**

答：只有在解决率没掉的前提下才成立。每请求成本可以靠"失败得更快"轻松压到最低，而
这恰恰就是一个过于激进的 effort 路由器干的事：它把难请求送去便宜那条路，账单下来
了，用户去重试或者干脆走人。真正管事的指标是每个解决任务的成本，延迟在旁边一并报，
而它要求按请求记录结果。一个把每请求成本砍半、却让解决率掉了三分之一的策略，在真正
重要的那个指标上是更差的，capstone 里就有这么一个例子：每请求最便宜的那个策略是产
品上最糟的那个。
