# 5. 验证

并行采样提高的是*某一次*尝试正确的概率。验证器才是把这个概率变成一个可以交付的答
案的东西。本章里所有贵的东西，验证器一变好就都变便宜，这就是为什么杠杆最大的投资
通常是验证，而不是思考。

## 验证器的阶梯

| 验证器 | 信号 | 成本 | 能被钻空子吗？ | 什么时候用 |
|---|---|---|---|---|
| 执行（单元测试、编译器、跑一遍 SQL） | 被测行为上的 ground truth | 沙箱时间 | 只能靠对测试过拟合 | 代码、查询、任何能跑的东西 |
| 符号或程序化检查 | 对所检查的性质是精确的 | 可以忽略 | 很少 | 数学答案、schema 合法性、约束满足 |
| 确定性的 self-consistency（对规范化答案做多数投票） | 一致性，不是正确性 | k 个样本 | 它分不清"自信地错"和"正确" | 简短的规范化答案，且没有检查器 |
| 结果奖励模型 | 对最终答案的一个学习得来的分数 | 一次模型调用 | 会，而且是经典的 reward hacking 目标 | 有训练数据的开放式任务 |
| 过程奖励模型（步骤级） | 每个推理步骤一个分数 | 好几次调用 | 会，而且更隐蔽 | 长推导，且失败是可以定位的 |
| 带评分标准的 LLM 裁判 | 一个模型的意见 | 一次模型调用 | 会：冗长偏好、自我偏好、注入 | 开放式任务，且只在认证之后 |

排序本身就是建议：**优先选一个能执行的检查器，而不是一个必须信任的模型。** 在不得
不用学习得来的验证器时，步骤级监督比只看结果的监督强得多
（[Let's Verify Step by Step](https://arxiv.org/abs/2305.20050)），而"选择质量封
顶了采样的价值"这个一般性发现，正是没有验证器的覆盖率只是幻觉的原因
（[Large Language Monkeys](https://arxiv.org/abs/2407.21787)）。

## 经济账：验证器是预算的乘数

单次尝试成功率为 $p$，尝试 $k$ 次，覆盖率是 $1-(1-p)^k$，但交付出去的准确率是覆盖
率乘以"在存在正确样本时，选择器选中正确样本"的概率。两个后果：

- **弱选择器浪费尝试。** 在 $p = 0.4$、$k = 8$ 时，覆盖率大约是 0.98，而一个六成
  时候选对的选择器交付出去的大约是 0.6。你付了八个样本的钱，拿到的质量差不多是一
  个半。
- **改进验证器胜过增加样本数。** 把 $k$ 翻倍，覆盖率沿着一条越来越平的曲线挪一
  点；改进选择器，整个乘积都在动。

这和 [Benchmark 一章第 5 节](../benchmark-eval/05-scoring-and-autoraters.md)里
pass@k 与交付质量的区别是同一回事，面试里值得点出来：**pass@k 是你能买到的东
西；验证器决定你能留下多少。**

## 验证器是怎么失效的

- **弱测试放过错误答案。** agentic benchmark 的文献记录的正是评估框架里的这种失败：
  测试集太弱，拒绝不了错误的补丁，分数就被抬高了
  （[Establishing Best Practices for Building Rigorous Agentic
  Benchmarks](https://arxiv.org/abs/2507.02825)）。在服务里，同样的弱点会让错误答
  案通过接受测试。
- **优化压力会找到缝隙。** 对着一个学习得来的奖励模型做 best-of-n，就是*针对验证
  器*做优化，所以样本会往验证器奖励的方向漂，而不是往正确的方向漂。$k$ 越大，压
  力越狠。
- **裁判可以通过内容被攻击。** 当验证器是一个读模型输出的模型时，嵌在输出里的一条
  指令就是一个注入向量（见[安全一章](../safety/)）。
- **验证器也是一项成本。** 一个过程奖励模型给一条 10,000 token 的 trace 的每一步打
  分，可能比它检查的那次生成还贵。在每个解决任务的成本里要把验证 token 明确算进
  去。

## 实用的接受测试

对级联来说，接受测试不需要完美，它需要**朝正确的方向保守**。放过一个错误答案是代
价高昂的错误；把一个其实没问题的答案升级上去，代价只是那一次升级。

| 任务 | 便宜的接受测试 |
|---|---|
| 代码改动 | 跑仓库的测试；只在全绿时接受 |
| SQL 或查询生成 | 在测试数据库上执行，比较结果行集 |
| 结构化抽取 | schema 校验，加上逐字段对照来源的一致性检查 |
| 数学或数值答案 | 符号化地重新计算，或者检查答案是否满足题目给定的约束 |
| 带来源的自由形式解释 | 每一条断言都必须能映射到一段检索到的片段（groundedness 检查） |
| 其他任何任务 | 一个经过认证的评分标准裁判，认证流程见 [Benchmark 一章第 5 节](../benchmark-eval/05-scoring-and-autoraters.md) |

最后一行带着一个警告：拿一个未经认证的裁判当接受测试，会把一个质量问题变成一个
无声的质量问题，因为级联会自信地接受裁判喜欢的任何东西。

## 什么时候用哪个

| 用什么 | 什么时候 | 代替什么 |
|---|---|---|
| 基于执行的验证 | 输出能跑 | 让模型判断代码看起来对不对 |
| 符号或 schema 检查 | 输出有可检查的形式 | 多采几个样然后祈祷 |
| Self-consistency 投票 | 简短的规范化答案，没有检查器可用 | best-of-n，它需要一个你没有的选择器 |
| 结果奖励模型 | 开放式输出，有训练数据，$k$ 不大 | 大 $k$ 的 best-of-n，优化压力会把它弄坏 |
| 过程奖励模型 | 长推导，且预算撑得起逐步打分 | 在错误可定位的 trace 上只按结果打分 |
| 经过认证的评分标准裁判 | 其他都不适用 | 未经认证的裁判，它让失败变得看不见 |
| 把钱投在验证器而不是 token 上 | 覆盖率很高但交付质量不高 | 再把 $k$ 翻一倍 |
