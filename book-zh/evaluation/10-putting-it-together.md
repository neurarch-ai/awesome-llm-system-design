# 10. 把它们拼起来：完整的方案

第 1 到 6 节把每个环节的选项和取舍讲了一遍，第 7 节展示了真实团队在哪里分道扬镳。但它们都没有给出一套每个决定都已经拍板的完整评估系统。这一节压轴做三件事：给出一套有主张的默认技术栈，免得选择困难症卡住第一次搭建；把本章的场景从头到尾走一遍，每个选择都落地并算清成本；再展示当约束变化时，同样这些决定会怎么翻转。最后收在一个最小可运行的 judge 实验上，一个文件，不用装任何东西。

## 默认技术栈：从这里开始，有理由再偏离

本章的每个环节都有好几个说得通的选项，第一次搭系统的人可能花一整周比较各种框架，却一次改动都还没卡住。别这样。下面这套是第一版生产评估系统的合理默认值；每一行都写明什么时候该偏离，以及哪一节解释了原因。工具年年在变，但每个环节的接口（建黄金集、打分、评判、校准、卡关、线上确认、重新校准）不会变，所以按接口逐环节选，任何一个具体框架都当成可替换的。

| 环节 | 默认做法 | 什么时候偏离 | 为什么（对应小节） |
|---|---|---|---|
| 黄金数据集 | 约 1,000 行带版本的样本：常见路径、已知的难例、每修一个 bug 加一行；再留一个从不用来调优的留出分片 | 第一天：先从几百条精挑细选的样本起步，之后从生产流量里长起来 | [3](03-offline-eval.md) |
| 标签 | 以人工标注为锚；生产信号（点赞点踩、编辑）用来提名该刷新哪些样本 | 罕见或对抗性的分片没被覆盖到：补合成样本，并按人工标签做校准 | [3](03-offline-eval.md) |
| 任务指标 | 只要答案可核对，就用精确匹配、F1 或通过与否；主动改造任务，把可核对的信号暴露出来 | 永远不偏离。先用它们，judge 只覆盖它们覆盖不了的部分 | [3](03-offline-eval.md) |
| judge 模式 | 候选版本对生产基线做 pairwise，两种顺序都跑取平均 | 需要按维度拆解：给每条轴加一个 pointwise rubric | [4](04-llm-as-judge.md) |
| judge 校准 | 对人工标签的 kappa 过线；换一个模型家族；钉住模型版本和 prompt 版本 | kappa 没过线：去修 rubric，先别拿它卡关 | [4](04-llm-as-judge.md) |
| 回归门禁 | 每次改 prompt、模型或配置都自动触发；卡最差的分片；容差取自实测的 judge sigma | 永远不要只卡平均值 | [5](05-online-eval.md) |
| 安全门禁 | 单独一套二元的策略合规集，配它自己的阈值 | 永远不要并进能力分里 | [3](03-offline-eval.md) |
| 成本控制 | 对没变过的（输入、输出、judge 版本）三元组做缓存；本地跑 50 行冒烟子集，门禁处跑完整套件 | 改动频率很低（个人项目、每周一改）：每次都跑完整套件也没问题 | [6](06-serving-and-scaling.md) |
| 线上证据 | 先金丝雀，再在行为指标上做 A/B，同时盯着延迟、成本和拒答护栏 | 输出还不能展示出来：用影子模式；受监管的输出：用人类专家 A/B | [5](05-online-eval.md) |
| 反馈闭环 | 每次离线与在线不一致，就重新校准套件，而不是改容差 | 永远不偏离 | [5](05-online-eval.md)、[2](02-frame-the-eval.md) |

第一行是新手最容易跳过、之后最后悔的一条：没有带版本的黄金集，每次改 prompt、每次换模型都只是凭感觉，你根本说不清一次改动到底有没有帮上忙。花一个下午做标注，等到同事第一次提议"平替升级一下模型"的时候就回本了。

## 完整的方案

回到[第 1 节](01-clarifying-requirements.md)的那个场景：一个面向客户、回答产品问题的助手，输出开放式、没有精确匹配指标，prompt 每天都在改、模型大约每月升级一次，最糟的失败是编造产品事实，每次改动都要过自动门禁、人工评审只留给拿不准的用例，每次候选评估的预算是几百美元。下面是整套系统，每个选择都已拍板，以及它胜出的理由。

| 决定 | 选择 | 它为什么胜出 |
|---|---|---|
| 黄金集 | 从生产环境采样的 1,000 行，在源码里做版本管理，留出 15%（示意用的划分比例） | 覆盖度优先于数量；那个留出分片正是"测量"和"优化表演"的分水岭 |
| 分片 | 语言、query 类型、客户档次 | 一个抬高了均值却把某一种语言打穿的改动，照样必须被拦下 |
| 可核对的分片 | 把产品事实类断言改造成可抽取的字段，用精确匹配打分 | 任务指标免费且骗不了；judge 只留给它核对不了的东西 |
| judge 模式 | 候选版本对生产基线做 pairwise，两种顺序都跑取平均 | 相对判断比 1 到 10 的量表可靠；取平均能抵消位置偏差 |
| 维度打分 | 用 pointwise rubric 分别给准确性和有用性打分 | 场景里这两点都点名了；它们可以各自独立退化，单一的胜负结论看不出是哪一项动了 |
| judge 校准 | 换一个模型家族、钉住版本，对人工标签的 kappa 高于 0.6 才卡关 | 没校准的 judge 只是一个第二意见，不是一台仪器 |
| 门禁 | 最差分片的差值，容差设成实测的 judge sigma（1 到 2 个点） | 拍脑袋的容差会让门禁反复横跳；零容差会因为噪声就拦人 |
| 安全 | 二元的对抗集，单独一道门禁 | 一个能力更强但更不安全的候选版本必须照样被拦下 |
| 评估框架 | 并行 worker、结果缓存、本地迭代用 50 行冒烟子集 | 门禁必须在几分钟内跑完，否则工程师会绕着它走 |
| 线上 | 内部金丝雀，然后在任务完成率、编辑率、点赞点踩上做 A/B；延迟、成本、拒答当护栏 | 离线在结构上就看不见这些信号，它们只存在于真实流量上 |
| 人工评审 | 只看接近阈值的判定和每月的模型升级 | 量交给自动化，需要判断力的交给人 |

**套件规模。** 1,000 行分布在三条切片轴上，大约十来个 segment，每个 segment 差不多 80 行（示意数字）。这一点很重要，因为门禁是按最差分片触发的：一个远低于约 50 行的 segment，judge 噪声比容差还宽，它自己就能让门禁反复横跳。黄金集的规模要按你必须保护的最小分片来定，而不是按总量。

**每次门禁的 judge 成本。** 1,000 行做 pairwise 且两种顺序都评，大约是每个候选版本 2,000 次 judge 调用（[第 6 节](06-serving-and-scaling.md)）。按每次评判几百 token、每千 token 一毛钱算，跑一次完整门禁接近 \$80（示意数字），
落在[第 1 节](01-clarifying-requirements.md)给的每候选几百美元的预算之内。冒烟子集是 50 行，本地一轮大约 100 次调用、\$4（示意数字）。让每天这个节奏撑得下去的关键是缓存：上一轮以来没变过的输出永远不会被重新评判，所以正在迭代的工程师只为自己这次改动真正影响到的那些行付费。

**门禁的耗时。** 1,000 行的套件串行执行、每次调用两秒，要跑三十多分钟；三十路并行大约一分钟（[第 6 节](06-serving-and-scaling.md)）。一分钟能像测试套件一样焊进 CI。三十分钟会被跳过，而一道被跳过的门禁不是门禁。

**线上的统计功效。** 偏好是一个比例，所以 95% 置信区间是 $\hat{p} \pm 1.96\sqrt{p(1-p)/n}$，而且区间必须不含 0.5 才能宣布赢家。真实胜率 54% 时，这大约需要 2,400 次比较（[第 5 节](05-online-eval.md)）；效应量减半，样本量大致要翻两番（[第 6 节](06-serving-and-scaling.md)）。这套算术正是离线套件存在的理由：A/B 的名额既贵又慢，所以先用便宜的离线门禁筛掉弱候选，A/B 的预算只花在大概率会赢的候选上。

**第一个月会坏在哪。** 早期运营中有三种失败模式最常见，所以上线前就要把它们的信号接好：judge 漂移（按固定节奏在一个存好的（输入、输出）对组成的校准集上重新打分；候选版本没动而分数变了，就是仪器动了，见[第 4 节](04-llm-as-judge.md)）、离线与在线不一致（把离线结论跟每一次金丝雀和 A/B 的结果记在一起；反复不一致就说明套件测错了东西，必须重新校准，见[第 5 节](05-online-eval.md)）、门禁反复横跳（同一个候选版本在多次重跑里时而被拦时而通过，说明容差落在了 judge 的噪声底线之下；这时要在相同输入上重新测 sigma，而不是手动把门禁放宽）。

## 同样的技术，换一组约束

实践中真正要回答的评审问题不是"哪个 judge 最好"，而是"在我的约束下哪套评估技术栈才对"。下面是同一套系统搭了三遍。只有中间那一列是上面那套方案，另外两列保持完全相同的环节接口，却几乎换掉了每一个实现选择。

| | 编程助手（任务可核对） | 客服助手（本章） | 受监管的法律文书起草 |
|---|---|---|---|
| 输出的可核对性 | 高：代码要么过测试要么不过 | 低：开放式答案，没有参考 | 低，而且出错的代价很严重 |
| 黄金集 | 几千条用例外加带可执行 CI 的坏仓库 fixture | 1,000 行带版本的样本，按语言、query 类型、客户档次切片 | 几百条专家撰写的用例；增长很慢，每一行都很贵 |
| 打分 | 几乎所有东西都用单元测试通过率和 pass@k；只有对话解释那个分片才用 judge | 可核对的事实分片用任务指标；其余用验证过的 pairwise judge | 半自动的任务评估；judge 只是建议，绝不是最终结论 |
| judge 校准 | 轻量：judge 只覆盖一小部分分片 | 对人工标签的 kappa 过线、钉住版本、定期重新打分查漂移 | 有校准，但从属于领域专家的评审 |
| 线上证据 | 内部金丝雀（dogfood）加每日对比生产版本的回归 | 金丝雀，然后在完成率、编辑率、点赞点踩上做 A/B | 人类专家 A/B 作为最终裁决；不在客户身上做线上实验 |
| 门禁频率 | 每次提交，CI 的形状 | 每次改 prompt 或换模型，每轮几分钟 | 每次发布；时间线由人工放行主导 |
| 什么算过度设计 | 对单元测试已经打过分的行再上 pairwise judge | 每天每一次改 prompt 都要人工放行 | 高频自动化；瓶颈是专家评审，不是算力 |

由此得出两个教训。第一，编程助手那一列基本上是在做减法：任务一旦可核对，judge、它的校准、它的漂移监控、它的偏差修正就全都缩到系统的一个角落里，评估账单也随之塌缩，因为跑一次测试是免费的，而一次 judge 调用不是。这是本章那条规则最有力的形式：任务允许的地方一律用任务指标。第二，法律那一列展示的是门禁的信任锚点在移动：自动套件照跑，但它是在为人类专家筛候选，而不是取代他们，频率从每天降到每次发布，在线回路变成了人类偏好而不是真实流量，因为对受监管的输出做 A/B 根本不是一件可用的工具。

## 每条约束各自决定什么

压缩版的决策指南。从自己的需求里对照左列，右边两列告诉你它在你比较任何工具之前，先撬动的是哪根杠杆。

| 你的约束 | 它撬动的杠杆 | 经验法则 |
|---|---|---|
| 输出的可核对性 | 打分工具 | 可核对：用任务指标，没有 judge 要校准。开放式：用验证过的 judge，并且把每一个可核对的子部分都挪出它的管辖范围 |
| 改动频率 | 成本控制 | 每天都改：缓存、冒烟子集、挑过 kappa 线里最便宜的 judge。每月升级：每次都跑完整套件也无妨 |
| 评估预算 | judge 的尺寸和套件的深度 | 给几个 judge 分别测 kappa，挑过线里最便宜的；两种顺序都跑会让调用翻倍，预算要留出来 |
| 流量规模 | 线上的测量工具 | 流量大：A/B。流量小：内部金丝雀。还没有流量：先上离线门禁，等流量来了再拿在线结果验证它 |
| 爆炸半径 | 人的参与程度 | 受监管或不可撤销：设人工放行门禁。否则：人只看接近阈值的判定 |
| 你必须保护的最小分片 | 黄金集的规模 | 按最小分片定，而不是按总量；一个薄到低于 judge 噪声底线的分片是卡不住任何东西的 |
| 想检出的效应量 | 线上的样本量 | 样本量随效应量的平方成反比增长；效应减半，比较次数翻两番 |
| judge 与人类的一致性 | 门禁的可信度 | kappa 没过线：去修 rubric。绝不要为了迁就一台坏仪器而放宽容差 |

## 最小可运行的 judge 实验

每一篇评估框架教程收到的评价都一样：读者拼出了一套框架，却还是看不出这套协议为什么重要。所以这里把本章核心的测量问题装进一个文件，不用装任何东西。每一个生产组件都换成了接口相同的最小实现：LLM judge 变成一枚带固定随机种子的硬币，携带一个已知的质量信号和一个刻意加进去的先手偏好；评估套件变成一个循环；显著性检验变成百分位 bootstrap。形状本身就是这一课；本章的第 4 节和第 5 节各自升级了这个文件里的一个函数。

```python
"""A biased pairwise judge, the swap fix, and why small eval sets lie. Stdlib only."""
import random

random.seed(7)
TRUE_WIN = 0.54          # candidate A's true win rate over baseline B
POSITION_BIAS = 0.12     # fixed extra preference for whichever answer is shown first

def judge(first, second):
    """Simulated pairwise judge: sees the true quality signal plus a fixed
    first-position preference. Production: one LLM call with a rubric."""
    p_first = (TRUE_WIN if first == "A" else 1 - TRUE_WIN) + POSITION_BIAS
    return first if random.random() < p_first else second

def win_rate_a_first(n):
    """Naive protocol: A always shown first. The bias lands entirely on A."""
    return sum(judge("A", "B") == "A" for _ in range(n)) / n

def paired_verdicts(n):
    """Debiased protocol: judge each pair in both orderings and average,
    so every pair yields 1, 0.5, or 0 wins for A and the offset cancels."""
    return [((judge("A", "B") == "A") + (judge("B", "A") == "A")) / 2
            for _ in range(n)]

def bootstrap_ci(verdicts, iters=2000, alpha=0.05):
    """Percentile bootstrap CI on the mean win rate. Same math on real verdicts."""
    n = len(verdicts)
    means = sorted(sum(random.choices(verdicts, k=n)) / n for _ in range(iters))
    return means[int(alpha / 2 * iters)], means[int((1 - alpha / 2) * iters) - 1]

# -- part 1: position bias, measured and cancelled --------------------------
N = 5000
print(f"true win rate of A over B:           {TRUE_WIN:.3f}")
print(f"judged with A always first (n={N}): {win_rate_a_first(N):.3f}")
swapped = paired_verdicts(N)
print(f"both orderings, averaged   (n={N}): {sum(swapped) / N:.3f}")

# -- part 2: how many pairs before the gate can call a 54% winner? ----------
print("\npairs   estimate   95% bootstrap CI    verdict")
for n in (100, 400, 2400):
    v = paired_verdicts(n)
    est = sum(v) / n
    lo, hi = bootstrap_ci(v)
    call = "A wins" if lo > 0.5 else ("B wins" if hi < 0.5 else "cannot separate")
    print(f"{n:5d}   {est:.3f}      [{lo:.3f}, {hi:.3f}]    {call}")
```

跑一下，输出会用大约四十行代码演示本章关于协议的两个论断。第一部分：A 永远排在前面时，judge 给一个真实胜率 0.540 的候选版本报出了 0.659 的胜率，凭空多出十一个点的提升，而这个数字在一道天真的门禁面前会一路畅通；两种顺序都跑再取平均，恢复到 0.533，在采样噪声范围内贴住真值，这正是[第 4 节](04-llm-as-judge.md)的顺序交换修法。第二部分：100 对去偏样本时 bootstrap 区间是 [0.465, 0.590]，400 对时是 [0.497, 0.565]，两个都跨过 0.5，所以这套套件区分不出一个确实更好的候选版本和一个平局；到 2,400 对时区间是 [0.529, 0.557]，A 终于赢了，跟[第 5 节](05-online-eval.md)针对 54% 效应推出的大约 2,400 次比较对上了。把这枚硬币换成真实的 judge 调用，把循环换成你的黄金集，把打印出来的判定换成一道分片门禁，你就把本章重建了一遍。
