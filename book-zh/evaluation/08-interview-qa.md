# 8. 面试问答

面试官关于 LLM 评估系统真正会问的那些问题，按用法分组。其中"常被答错"的那一类，是面试成败的分水岭。

## 常被问到

**问：输出没有唯一正确答案的时候，怎么评估一个 LLM 的输出？**

答：两条路，一起用。第一，先想办法把任务的一部分改造成可核对的：与其去评一段自由文本，不如让模型输出一个能精确比对的结构化字段（一个类别、一段 JSON、一个已解析出的实体），这部分用任务指标。剩下那些真正开放的维度（有用性、语气、是否忠于上下文），用带清晰 rubric 的 LLM-as-judge，但要先拿人工标签验证它，并在拿它卡任何东西之前报出 judge 与人类的一致率（Cohen's kappa）。能用任务指标的地方用任务指标、必须用 judge 的地方用验证过的 judge，这个组合才是诚实的答案；单靠任何一边都不完整。

**问：离线评估和在线评估的区别是什么，为什么两个都要？**

答：离线评估是拿一个候选版本（prompt 加模型）跑一个固定的黄金数据集，得出一个分数，快、便宜、可重复。在线评估是把真实流量导给候选版本，测行为信号：用户有没有完成任务、有没有去改输出、会话有没有继续下去。两个都要，是因为离线拿不到那些真正反映用户价值的信号（任务完成、留存、成本），而在线又没办法在东西发出去之前拦住一个回归。离线门禁是护栏，在线测量是真值检查，用来告诉你这道护栏校准得对不对。

**问：怎么把评估焊进发布路径，让一个回归没法不小心溜出去？**

答：把离线套件当单元测试对待：prompt、模型标识或推理配置一有改动就自动跑，任何一个 segment 跌破基线超过容差就让构建失败，而且要逐分片卡，不能只卡平均值。换模型是一次带版本的产物变更，走同一道门禁。只有门禁过了，候选版本才进金丝雀；只有金丝雀过了，才全量。关键的两个接线点是 CI 触发（这样不用谁记着去跑）和分片门禁（这样某个 segment 的回归没法藏在一个上涨的均值后面）。

**问：你怎么知道自己的评估本身靠不靠谱？**

答：看在线与离线的相关性。跑一遍离线套件，让候选版本走到在线 A/B，再把离线的结论和在线的结果对一对。如果两边一直吻合，这套套件就攒下了信任。如果不吻合（离线预测会赢但 A/B 显示输了，或者反过来），说明套件测的不是该测的东西，那就去修套件，而不是去调容差。Spotify 把这点说得很明确：离线评估和 A/B 结果之间的差距，是最主要的校准信号。一套从没被至少几次在线结果验证过的评估，不是门禁，是猜测。

**问：怎么评估一个 RAG 系统？**

答：检索和生成要分开评，因为一个 RAG 答案可能因为两个完全不同的原因失败，只给最终答案打分的话，你没法知道该修哪一半。检索质量：该出的文档出来了吗？对着标注好的相关文档测 recall@k 和 precision@k。答案的有据可依（faithfulness）：给定检索到的上下文，答案里的每一条断言都被它支撑吗？这是一个 judge 任务。答案的相关性：这个答案回答了那个问题吗？也是 judge 任务，但要和 groundedness 分开打分。拆成这三块，才能把失败定位出来：检索 recall 低说明证据压根就没拿到；检索 recall 高而 groundedness 低说明模型在好的上下文上产生了幻觉；groundedness 高而相关性低说明它忠实地回答了另一个问题。

## 有陷阱的（拉开差距的追问）

**问：离线分数涨了，在线 A/B 却显示回归。发生了什么，你怎么办？**

答：最常见的几个原因：judge 有啰嗦偏差，在奖励那个更长、听上去更自信、但用户其实觉得更没用的候选版本；黄金集过时了，没覆盖到回归所在的那些 query 模式；或者分数的平均方式把出问题的那个 segment 盖住了。诊断办法是先看线上是哪些 segment 退化了、它们在黄金集里有没有覆盖，再查 judge 是不是系统性地给更长的输出打了更高的分。修法不是去调容差，而是照着在线回路告诉你的真实用户价值，把套件重新校准。

**更深一层：** 啰嗦偏差是可以测的，不是靠直觉：在一组配对样本上把 judge 分数对输出长度做回归，斜率显著为正就说明 judge 有一部分是在给长度打分而不是给质量打分。这时候控制长度（或者在 rubric 里对它罚分）比整体换掉 judge 更对症，因为它拿掉的正是线上失利暴露出来的那个混杂因素。

**问：同事说"我们每次发布前人工检查一下质量就行了"。这样有什么问题？**

答：三个问题。一个团队里 prompt 天天在改，人工评审撑不住这个量。它不可重复：两个评审在不同的日子看同一条输出，打分可能不一样。而且它不逐分片卡关；一个靠眼睛扫例子的评审，会漏掉埋在某一种语言或某一档客户里的回归。人工评审的价值在于校准 judge，以及处理那些自动门禁判不出胜负的模糊金丝雀用例。它替代不了一道焊进流程、每次改动都跑、并且逐 segment 卡关的自动门禁。

**更深一层：** 不可重复这件事是可以量化的，就是评审自身前后的一致性和评审之间的一致性偏低，跟你给 LLM judge 算的 Cohen's kappa 是同一个东西。一道从没测过 kappa 的人工门禁，就是一台没校准的仪器，而且没有焊进流程的套件所具备的版本历史和逐分片可审计性，所以它连"两次通过是不是同一个意思"都回答不了。

**问：pairwise 评判里位置偏差为什么是个问题，两种顺序都跑一遍真的就够了吗？**

答：位置偏差是指 judge 系统性地偏爱排在前面（有时是后面）的那个答案。它会把胜率估计朝一个方向偏移一个固定的量。两种顺序都跑再取平均能把这个偏移抵消掉，因为偏差在两次展示中是对称的，取平均就把它减掉了。这个修法成立的前提是偏差在这一对上是一致的，对大多数模型 judge、大多数 rubric 而言这个前提是成立的。如果取完平均还检出残余偏差（比如在一组已知等价的输出上检查交换一致性），那可能是 rubric 本身有问题，得改。

**更深一层：** 取平均只能抵消可加且对称的位置效应。如果 judge 变成了不管谁放在那个位置就选谁（一种顺序里 A 赢 B，另一种顺序里 B 赢 A），那这一对根本没携带真实信号，应该记成平局，而不是平均成一个虚假的半场胜利。交换一致性率，也就是判定在交换顺序后依然成立的样本对比例，就是判断自己落在哪种情况的诊断指标。

**问：judge 漂移怎么办？托管的 judge 模型悄悄更新了，昨天的分数和今天的没法比。**

答：三道防线。第一，显式钉住 judge 的模型版本，像钉一个库的版本那样，把它当成带版本的依赖。第二，judge prompt 要和候选 prompt 分开做版本管理；改 judge prompt 的破坏力和换 judge 模型一样大。第三，维护一个固定的校准集，里面是分数已知的（输入、输出）对，定期重新打分；候选版本没动而校准集上的分数变了，就是 judge 漂移的信号。检出漂移之后，不要跨过这条分界线去回溯比较分数，而要在下一次门禁之前，对着新的 judge 版本重新建立基线。

**更深一层：** 校准集之所以管用，是因为两次打分之间唯一变化的变量就是 judge，所以任何分数移动都能归因到它，这和回归测试控制变量的逻辑是一样的。而要让它真能抓到漂移，集合里必须包含靠近决策边界的样本，也就是分数轻微移动就会翻转判定的那些，而不是只有那些不管 judge 怎么变都排得对的极端简单样本。

**问：黄金集和 judge 校准集看起来很像，都是固定的带标注数据集，这个区别到底什么时候才要紧？**

答：它们看起来可以互换：都是带版本的输入集合，配着已知的参考标签，跨轮次保持固定。但它们测的是同一个实验的相反两面。在黄金集上，变的是候选版本，judge 固定：你把黄金输入喂给一个新的 prompt 或模型，让 judge 给输出打分，所以分数变了就意味着候选版本变了。在校准集上，候选版本固定，变的是 judge：（输入、输出）对是冻结的，所以分数变了只可能意味着仪器变了。这个区别在分数发生变化、你必须归因的那一天要紧：如果只有黄金集，一次 judge 模型更新和一次真实的候选版本回归是分不开的，因为两者呈现出来都是同样的掉分。把这两个集合分开，才让漂移检测成为可能；这也是为什么校准对里必须存下输出，而不能只存输入：重新生成输出等于把候选版本又变回一个变量，那个受控对比就毁了。

## 常被答错的（陷阱题）

**问：能不能拿 MMLU 或 HumanEval 这样的公开 benchmark 给我的功能当质量门禁？**

答：不能。公开 benchmark 测的是模型层面的通用能力，而且会受污染影响：如果训练数据里包含了 benchmark 用例的近似重复，模型在 benchmark 上很好看，到生产环境就垮。选基座模型时，它们可以当一个粗糙的能力筛子，但当不了某个具体功能的质量门禁。你的门禁需要的是从自己的任务和流量里新采样出来的、私有的黄金集，带版本，并且从 prompt 迭代中留出来。

**更深一层：** 污染只会、且专门会把 benchmark 分数抬高，所以 benchmark 分数和生产表现之间的差距，恰恰在你最需要抓住的那些用例上被拉大。只有在模型训练完成之后才新采样出来的私有集合，你才能主张它从未进过训练数据，这正是它能当一道可信门禁、而不只是一个粗筛的原因。

**问：为了保持一致，LLM judge 是不是应该用被评估的那个模型？**

答：不应该。自我偏好偏差是有文献记载的失败模式：模型会系统性地偏爱来自自己家族的输出。让被评估的模型给自己当 judge 会把它的分数抬高，等于没有 judge。条件允许就用不同模型家族当 judge，测它跟人工标签的 kappa，并把跨家族的一致性记录下来。如果跨家族的选择有限，那至少要在具体的那份 rubric 上，更仔细地拿人工标签验证这个同家族 judge，然后才谈得上信任。

**更深一层：** 自我偏好不只是"眼熟"这么简单：模型会给靠近自己输出分布的文本赋予更高的似然，所以哪怕 rubric 严格只问事实性，它也会觉得自己的补全更流畅、更正确。换一个家族当 judge 打断了这个共享的分布，正是这个机制让跨家族的判定独立于候选版本自身的文风。

**问：如果我的评估分数很高，还需要在线 A/B 吗？**

答：通常还是要，至少头几次得用它来验证这道门禁。离线分数是预测，不是证明。judge 在结构上就看不到任务完成、用户编辑率、会话长度、成本，以及任何需要真实用户才存在的信号。一套新的离线套件第一次跑起来的时候，你并不知道它的结论能不能预测线上结果。只有当这道门禁已经证明它能可靠地预测过去的 A/B 结果，你才挣到了单靠离线门禁发布的资格。即便到了那时，重大改动（换模型家族、能力大幅变化）在全量之前也仍然应该走一遍线上金丝雀。

**更深一层：** judge 的盲区是范畴性的，不是精度问题。它无法观察用户有没有留下这条输出、有没有重试、有没有流失，因为这些信号在评估的那一刻根本不存在。judge 再好也变不出一个在离线输入里结构性缺席的变量，这也是为什么在线验证是另一种测量，而不是同一种测量的更精确版本。

**问：我们的 judge 过了 kappa 线，那它的分数可以直接当质量数字对外报吧？**

答：过线让这个 judge 可以在同一份 rubric 上给两个候选版本*排序*，但并不会让它的绝对数字变得无偏。kappa 说的是 judge 和人类以某个比例存在分歧，这是仪器的属性，不是对测量结果的修正。如果这个数字要离开团队（进一份报告、一张 model card、一次发布评审），就得做校正：让 judge 跑完全部样本，在其中几百条上保留人工标签，再把实测的 judge 偏差加回 judge 的均值上（prediction-powered inference）。无论 judge 好坏，这样得到的结果都是无偏的，代价是一笔你可以估算规模的标注预算，而不是一笔你根本付不起的标注预算。参见 [给模型做 Benchmark 第 5 节](../benchmark-eval/05-scoring-and-autoraters.md)。

**更深一层：** 区别在于相对断言和绝对断言。"候选版本在这份 rubric 上赢了基线"在一个有偏 judge 下依然成立，只要偏差对两边一视同仁，这正是门禁能奏效的原因。"我们的助手准确率 74%"就不行，因为这个数字直接继承了 judge 的偏差，而它偏偏就是最后会被放上幻灯片的那个。

**问：把门禁容差设成零吧，只要有任何回归就拦住部署。**

答：judge 是有噪声的，容差为零会让门禁不停地反复横跳。judge 是一台有噪声的仪器；同样的输入和输出，跨轮次的打分会因为模型温度、prompt 的细微敏感性以及 judge 模型自身的方差而略有差别。零容差会把这些噪声当成真实回归，把合法的改动拦下来。容差应该从 judge 在相同输入上实测的分数方差来定（同一条输出重复打分的标准差），一般是一到两个百分点，这样门禁拦得住真回归，又放得过噪声。

**更深一层：** 这个阈值是从噪声底线推出来的，不是凭口味挑的：测一下在相同（输入、输出）对上重复打分的标准差，把容差设在这个 sigma 之上的一个小倍数，这样门禁的误拦率就被控制在一个已知的水平上。容差如果设在实测的一倍 sigma 噪声之下，就会以一个可预测的、很高的比例拦下合法改动，而这正是"零容差"方案必然带来的反复横跳。
