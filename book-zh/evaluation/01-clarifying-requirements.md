# 1. 澄清需求

动手设计之前，先把系统必须做什么定下来。下面是候选人和面试官之间一段典型的交流。注意每一个问题要么砍掉了一部分工作量，要么改变了设计方向。

**候选人：** LLM 产出的是哪种输出？是有唯一正确答案、可以核对的封闭式回答，还是摘要、聊天回复这类开放式的内容？

**面试官：** 主要是开放式的。这是一个面向客户的助手，回答产品相关的问题。没有唯一正确答案。

**候选人：** 有没有现成的人工判断可以拿来对照，还是从零开始？

**面试官：** 生产环境里有一些用户点赞/点踩的信号，偶尔也做人工标注研究，但都不成体系。

**候选人：** prompt 或者模型多久变一次？是每天都在改 prompt，还是更像按季度升级模型？

**面试官：** 两者都有。产品团队一直在改 prompt。我们还计划大概每月升级一次基座模型。

**候选人：** 一次失败的代价是多少？法律流水线里的一个错误答案，和聊天机器人语气稍微差一点，完全是两回事。

**面试官：** 没帮助的回答会消耗信任、赶走用户。编造出来的产品事实更糟。我们最在乎事实准确性和有用性。

**候选人：** 回归需要自动发现，还是人工审核就可以接受？

**面试官：** 人工审核跟不上节奏。我们需要每次改动都过自动门禁，人工审核只留给拿不准的情况。

**候选人：** 跑评估本身的预算有多少？每一条被评判的样本都要一次模型调用。

**面试官：** 合理范围内。每次候选版本的评估可以花几百美元，但不能花几千。

我们来总结一下问题陈述。**题目要求设计一套面向客户的 LLM 助手的评估系统。** 输出是开放式的自然语言，不存在精确匹配指标（也就是检查输出是否与参考字符串完全一致）。系统必须在每次 prompt 或模型改动上线前自动把关，按细分群体捕捉回归，成本要低到每次改动都能触发，还要能区分事实准确性和一般意义上的有用性。人工审核只留给拿不准的情况，其余一切都必须通过自动化的门槛。

由此立刻能推出两个结论，早早把它们说出来，这道题的大部分分数就到手了。

**结论 1：不能只靠精确匹配指标。** 输出是开放式的。这就迫使我们要么设计一个任务指标（把问题的一部分改写成可核对的形式），要么在真正主观的维度上依赖一个 judge 模型。引入 judge 就多了校准的开销：一个没有拿人工标注验证过的 judge，只是一个没理由相信的第二意见。这一步验证不是可选项，它正是区分"可信的评估系统"和"自以为在测量"的那条线。

**结论 2：门禁必须自动化，而且按分片执行。** 单一的总分会把回归藏起来。一个改动可以拉高平均分，同时把某种语言、某个客户层级或某类查询搞砸，照样能上线。门禁必须盯着最差的那个细分群体触发，而不是盯着均值；而且必须像单元测试在每次提交上自动跑一样，在每次改动上自动触发。
