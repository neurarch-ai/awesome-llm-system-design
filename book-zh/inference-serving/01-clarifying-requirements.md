# 1. 澄清需求

动手设计之前，先把系统必须做到的事钉死。下面是候选人和面试官之间一段很典型的交流。注意每一个问题要么砍掉了一部分工作，要么改变了设计，要么改变了瓶颈所在的位置。

**候选人：** 延迟目标是多少？是针对首 token，还是针对后面的每一个 token？
**面试官：** 两个都重要。我们要求 p99 首 token 延迟（TTFT，用户等到第一个输出 token 出现的时间）低于 500 ms，p99 token 间延迟（也叫 TPOT，每个输出 token 的耗时）低于 50 ms。它们是两个独立的 SLO。

**候选人：** 预期 QPS（每秒查询数，也就是请求到达速率）是多少？流量有没有尖峰？
**面试官：** 平均大约每秒 500 个请求，尖峰能到 3 倍。某些时段流量是突发性的。

**候选人：** 典型请求长什么样？长 prompt 还是长输出？
**面试官：** 混合的。有些是 RAG 调用，8k token 的 prompt 配短回答；另一些是代码或 agent 调用，prompt 短但输出长。假设在请求进入时无法预判是哪一种。

**候选人：** 模型能放进一张 GPU 吗？
**面试官：** 模型是一个 700 亿参数的稠密 transformer，放不进单张 A100。假设有 H100 可用。

**候选人：** 需要同时服务多个模型或多个微调版本，还是只有一个模型？
**面试官：** 目前只有一个。如果你想加一个小的草稿模型做投机解码，可以。

**候选人：** 需要支持多租户、不同优先级吗？
**面试官：** 需要，有付费层和免费层。过载的时候必须保住付费层。

**候选人：** 成本目标是什么？
**面试官：** 把每百万输出 token 的成本压到最低。GPU 时间是主要开销。

把问题陈述总结一下。**我们要为一个 70B 参数的 LLM 设计 serving 系统，流量约 500 QPS（尖峰 3 倍），满足 p99 首 token 延迟 500 ms 和 p99 token 间延迟 50 ms 两条 SLO，负载是 prefill 重和 decode 重两种请求的混合，跑在 H100 上，有两个优先级层，同时把每百万输出 token 的成本降到最低。**

两个推论会立刻冒出来，而早早把它们说出口，就是这道题里大部分的信号：

**TTFT 和 TPOT 是两个不同的旋钮。** 一次长 prefill（在任何输出 token 之前一次性处理整个 prompt 的那趟前向）占满一整个 step 的 GPU，会把这个 step 里所有正在 decode 的请求都堵住，TPOT 飙升。反过来，一个塞满了在途 decode step（每一步产出一个输出 token）的 batch，会让等着开始 prefill 的新请求干等，TTFT 飙升。想优化一个而不伤另一个，要么把 prefill 切成块，要么把两个阶段拆到独立的资源池上。选哪条路，是第一个设计决策。

**模型放不进一张 GPU。** 一个 70B 稠密模型，BF16 下光权重就约 140 GB。单张 H100 有 80 GB 的 HBM（高带宽显存，GPU 封装内的内存）。在考虑批处理或调度之前，必须先把模型切到至少两张 GPU 上。张量并行（把每一层切到多张 GPU 上）或流水线并行（把不同层切到不同阶段）不是可选项，而是前置条件。这也意味着从一开始设计的就是一个多 GPU 引擎，而不是简单的单设备栈。
