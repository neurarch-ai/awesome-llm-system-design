# 8. 面试问答

面试官在 LLM 推理服务这块真正会问的问题，按用途分成三组。经常被漏掉的那些，才是面试拉开胜负的地方。

## 常问的

**问：为什么 decode 受显存带宽限制，而 prefill 受算力限制？**

答：prefill 在一次前向里并行处理全部 prompt token。每加载一个字节的权重，GPU 要做的运算（attention、前馈、layer norm）很多，算术强度高，所以落在 roofline 的算力那一侧。decode 每次前向只吐一个 token，为了产出这一个输出，GPU 要把整个模型和整个 KV cache 读一遍，每加载一字节对应的运算数接近 1，落在带宽那一侧。加大 batch 对 decode 有效（把固定的权重读取成本摊到每步更多的 token 上），对 prefill 却几乎没用（它本来就受算力限制）。瓶颈不同，能用的杠杆也不同。

**问：什么是连续批处理，它为什么有用？**

答：静态批处理要凑齐一组固定的请求，把它们全部跑完，再开下一组。请求结束时间参差不齐时，GPU 就得干等最慢的那个。连续批处理在 token step 这一层做调度：每个 decode step 结束后，调度器立刻让完成的序列退出，把等待中的序列填进腾出来的槽位。请求之间没有空窗，GPU 因此一直是满的。Anyscale 测出相比朴素静态批处理最高有 23 倍吞吐（其中约 8 倍来自调度，剩下的来自 PagedAttention 的显存效率）。

**问：KV cache 是什么，为什么它是卡住的那个内存约束？**

答：KV cache 存的是一个序列到目前为止每个 token 在 attention 里的 key 和 value 投影。每个 decode step 都要读它，才能在整个上下文上算 attention。以一个 80 层、8 个 KV head、head 维度 128 的 70B 模型、BF16 精度算，每个 token 大约吃 320 KB 的 KV cache。一条 4,000 个输出 token 的序列会占掉约 1.3 GB，50 条这个长度的并发序列就要 64 GB，权重还没算进去就已经超过 H100 的 HBM 了。限制并发的通常是 KV cache 的大小，不是模型权重。

**问：为什么一个长 prefill 会让其他用户的 token 间隔出现尖峰？**

答：大 prompt 的一个 prefill step 会独占 GPU 整整一次迭代：在途的每一条 decode 序列都要卡到这一步跑完为止。如果一个 32k token 的 prefill 要 400 ms，那一刻其他所有用户看到的都是 token 之间 400 ms 的空档。分块 prefill 的解法是把这个 prefill 切成短块，和正在进行的 decode step 交错着跑，于是这段停顿被摊到很多个小步里，而不是集中砸在一步上。

**问：什么时候该用张量并行，什么时候该用流水线并行？**

答：TP 把每一层的矩阵切到多张 GPU 上，每层做一次 all-reduce。它能降低每张 GPU 的显存占用，也能压低单请求延迟，但需要快速互连（NVLink），因为每个 token 在每一层都要触发 all-reduce。TP 要限制在单节点内。PP 按层的分组把模型切到多个节点上，只在 stage 边界通信。它对慢一些的节点间链路容忍度更高，但会引入流水线气泡，对单请求延迟不利。经验法则：节点内用 TP，为了装下模型或者压低延迟；跨节点用 PP，为了突破单节点的 GPU 数量上限；一旦单份副本能装下，就整份复制。

## 有坑的（区分度就在这些追问里）

**问：正常负载下 p99 TTFT 看着挺好，一到流量尖峰就炸。你怎么办？**

答：问题出在你是拿滞后信号（已经涨上去的延迟）在做扩容。换成领先信号：队列深度（等待开始 prefill 的请求数）或者队列平均等待时间。该在队列开始堆积时触发扩容，而不是等 TTFT 已经错过目标。同时准备一两个热备副本，在新实例启动期间吃掉尖峰。如果尖峰快到新副本根本来不及，唯一的保护就是感知 SLO 的准入：用 429 式的信号主动降载，而不是把注定要超时的请求放进来。

**为什么：** TTFT 是滞后信号，因为它只有在一个请求排完队、做完 prefill 之后才测得出来，等 p99 TTFT 动起来，队列其实已经堆了好几秒。而队列深度在到达速率超过服务速率的那一瞬间就会涨，那正是你想据以扩容的条件，并且它比延迟分位数早好几分钟。

**问：某个团队声称投机解码带来 4 倍吞吐。这可信吗？**

答：要看负载。投机的加速比服从：
$\text{speedup} = (1 - \alpha^{k+1}) / ((1-\alpha)(1+ck))$。
在高接受率下（$\alpha \approx 0.8$、$k=4$、$c=0.1$），公式算出来大约 3 到 4 倍。LinkedIn 在 Hiring Assistant 上做到接近 4 倍，是因为输出大量复述 prompt 里的内容，n-gram 草稿的接受率因此非常高。换成自由发挥的创意生成，接受率会垮掉，通用草稿甚至能让推理慢 1.5 倍（Fireworks 测到的正是这个）。所以这个说法对那种负载是可信的，换成任意文本生成就不成立了。

**为什么它能掉到 1 倍以下：** 起草成本 $ck$ 是每一步都要付的，不管结果如何。接受率低的时候，目标模型每次验证大致只保住一个 token，跟普通 decode 每步出一个 token 的进度一样，只是你还额外付了起草的钱，以及那些被拒 token 上白做的验证。开销没有对应的回报，净结果就是变慢。

**问：batch 加到多大就不再提升吞吐了？**

答：有两道天花板。第一道是带宽天花板：decode 吞吐随 batch 增大而上升，因为固定的权重读取成本被摊到了更多 token 上，但一旦 GPU 饱和（带宽用满），再加序列也不会提高 tokens/s/GPU。第二道是 KV cache 天花板：并发序列越多，它们的 KV cache 越把 HBM 填满，最终再也塞不下新序列，调度器开始抢占或拒绝。过了这个点，"更大的 batch"其实意味着调度器在劣化。别默认越大越好，先测出自己真实的 roofline 和 KV 占用率。

**问：投机解码和大 batch 吞吐都是"让 decode 更快"，为什么不能直接叠加？**

答：因为它们抢的是同一份资源。投机解码是拿富余算力去换更少的串行目标模型前向：每一步在 $k+1$ 个候选 token 上并行跑一次目标模型，保留最长的已验证前缀。只有 GPU 有闲置算力时，这种并行验证才便宜，而那正是中小 batch 下 decode 受带宽限制的情形。大 batch 的连续批处理（出自 Orca，OSDI 2022）做的是反方向的事：它塞进足够多的并发序列，把 decode 推向算力 roofline，于是"免费"的验证算力不复存在，投机每一步的额外工作开始跟真实 token 抢资源。落到机制上就是：batch 一旦算力饱和，加速比公式里的开销项 $ck$ 就不再可以忽略。实践中要二选一：对延迟敏感的低 batch 流量用投机，对吞吐敏感的批量流量用大 batch，在两者之间做路由，而不是把它们摞在一起。

**问：重新训练并重新部署模型时，怎么守住 p99 延迟？**

答：重新部署期间最大的风险是过渡窗口：一部分副本跑旧模型，一部分跑新模型。如果模型的输出格式或行为变了，从不同版本拿到 token 的客户端可能看到前后不一致的流。做灰度滚动发布：先把一小部分流量导到新版本，在真实流量上同时校验延迟和输出质量，再逐步放量。在新版本被确认健康之前，旧副本要一直留着作为回滚目标。如果是分离部署，还要确认 prefill 池和 decode 池是一起更新的，并且两个版本之间 KV cache 的格式互相兼容。

**为什么灰度恰好能保住 p99：** 刚启动的副本前缀缓存是冷的、kernel 也没预热（CUDA graph 捕获、JIT 编译），所以它们最初的几个请求明显慢于稳态。只导入一小部分流量，能让新副本在承担会影响 p99 的负载之前先热起来；而把旧副本继续热着，则保住了一条本身不需要冷启动的回滚路径。

**问：张量并行和加副本看着很像，都是"给模型更多 GPU"。这个区别到底什么时候才重要？**

答：复制几乎能线性放大吞吐，因为每个副本服务各自独立的请求、彼此不共享任何东西，但它没法让任何单个请求变快，也装不下超出单副本显存的模型。张量并行把每个权重矩阵切到多张 GPU 上，所以这两件事它都能做：每张 GPU 的显存按 TP 度数下降，每个 token 的矩阵乘也更早算完。代价是每个 token 在每一层都要 all-reduce，吃互连带宽，使得每 GPU 吞吐变成次线性。这个区别恰好在两个边界上才要紧：模型装不进一张 GPU 时（只能上 TP），以及 batch 等于 1 都还达不到单 token 延迟 SLO 时（只有 TP 有用，因为复制永远碰不到单个 token 的关键路径）。除此之外，按每张 GPU 的性价比算，加副本更划算。

## 经常答错的（陷阱）

**问：为了最大化吞吐，是不是永远该选最大的 batch？**

答：不是。过了带宽饱和点，再加序列只会用 KV cache 把 HBM 填满，调度器开始抢占正在跑的序列，吞吐和延迟一起变差。正确的目标是找到那个既让 GPU 饱和、又不超出 KV cache 预算的 batch 大小。做 profiling 并设一个硬上限，别默认"越多越好"。

**为什么抢占的代价这么大：** 一条被抢占的序列，要么把它的 KV block 通过 PCIe 换出到 CPU 内存、之后再换回来，要么直接丢掉、之后用一次多余的 prefill 重算。两条路都是在重做 GPU 已经做过的工作，所以过了 KV 天花板，每多放进一条序列消耗的总算力都超过它的贡献，于是利用率看着很高，吞吐却在往下掉。

**问：投机解码改变了输出分布，所以上线前需要额外做评测，对吗？**

答：结论方向对，理由错了。只要用拒绝采样正确实现，投机解码可以证明等价于直接从目标模型采样；输出分布是完全相同，不是近似。你需要做质量评测，不是因为分布变了，而是因为接受规则写错或者验证配错了，会悄无声息地让质量回退。上线前在留出集上测一致性，然后把它当成正确性检查，而不是一笔质量上的取舍。

**为什么分布得以保持：** 接受规则以 $\min(1, p(x)/q(x))$ 的概率保留一个起草的 token $x$，其中 $p$ 是目标分布、$q$ 是草稿分布；拒绝时，则从 $p - q$ 正部归一化后的分布里重新采样。把两种情况加起来，恰好还原出 $p$，这跟经典拒绝采样是同一套论证，所以实践中观察到的任何漂移都是 bug，而不是近似误差。

**问：任何大规模部署，prefill 和 decode 分离都是对的解法。**

答：只有当 prefill 和 decode 的 SLO 确实互相冲突，并且有快速互连来做 KV 交接时才成立。单一资源池加分块 prefill 更简单、延迟更低，对绝大多数负载已经够用。分离部署会把 KV 传输变成一个新的潜在瓶颈：prefill 池和 decode 池之间没有 NVLink 级别的互连，交接就会成为主导项，收益也就没了。先把互连规格定下来，否则别做分离。

**为什么交接会成为主导项：** 这次传输要在 TTFT 预算之内，把整个 prompt 的 KV cache（每个 token 几百 KB，长 prompt 就是好几个 GB）从 prefill 池搬到 decode 池。走慢速网络时，这次拷贝比它本想隔离掉的那个 prefill 还慢，于是拆分不但没消除干扰，反而增加了延迟。

**问：任何模型都可以在 serving 时直接量化，不用重新训练。**

答：权重量化通常可以在训练后施加，质量损失很小（现代硬件上的 FP8 和 INT8），但 KV cache 量化，尤其是对 attention 结构的改动（MQA、GQA、跨层共享），必须从一开始就训进模型里。把一个用完整 KV head 训出来的模型在 serving 时切成 MQA，质量会严重下降。Character.AI 那套之所以行得通，是因为这些压缩是在他们的训练过程里就烙进去的，不是 serving 时贴上去的一层。机制上：MQA（Google，2019）和 GQA（Google，2023）把许多 key/value head 收拢成一个或少数几个，于是所有 query head 都得通过共享的 KV 投影去做 attention。如果你在 serving 时把训练好的各 head 的 KV 投影做平均池化，query head 从来没有被优化过去读那个平均出来的子空间，attention 会指向错误的 token；只有重新训练（至少是一小段 uptraining）才能让 query head 重新学会共享。权重量化没有类似的问题，因为它只是把每个存下来的数值轻微扰动，并没有改变 attention 计算读取的是哪些参数。
