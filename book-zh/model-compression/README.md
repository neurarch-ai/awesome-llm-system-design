# 模型压缩：量化、剪枝与蒸馏

> 本章是英文原版的中文译本，原文见 [book/model-compression/](../../book/model-compression/)。译文和原文同步维护，发现问题请提 issue。

面试官很少会直接说"讲讲 GPTQ"。他们会说：**"这个模型对我们要跑它的地方来说
太大、太慢了。想办法让它装得下，并告诉我代价是什么。"** 约束有时候是 GPU 账单，
有时候是延迟预算，而且越来越多的时候是一台设备：固定的内存上限、散热包络，
以及一颗只在特定数值格式上才跑得快的加速器。

这个问题有一个听起来对、其实错的答案（"量化到 4-bit，基本没损失"），也有一个
多三句话的正确答案：到底是哪个资源卡住了，在*你的*硬件上哪根杠杆能撬动这个资源，
以及怎么证明你放弃的那部分质量是你付得起的。这些杠杆之间会互相影响，kernel 对
它们的支持程度也不一样，而验收测试正是大多数候选人跳过的那一步。

## 一页纸的决策

```mermaid
flowchart TD
  START["模型太大 / 太慢 / 太贵"] --> Q1{"什么在卡？"}
  Q1 -->|"内存上限"| MEM["权重占大头？<br/>先量化权重"]
  Q1 -->|"decode 延迟"| DEC["decode 受带宽限制：<br/>每个 token 少搬几个字节"]
  Q1 -->|"prefill / 高 batch"| PRE["受算力限制：<br/>需要低精度算术（fp8），<br/>纯权重量化的招不管用"]
  Q1 -->|"长上下文成本"| KV["KV cache 占大头：<br/>GQA/MLA，量化 + 分页 KV"]
  MEM --> Q2{"还是装不下？"}
  DEC --> Q2
  Q2 -->|"是"| SMALL["换更小的模型：<br/>结构化剪枝 + 蒸馏，<br/>或者换一个更小的底座"]
  Q2 -->|"否"| GATE["验收测试"]
  SMALL --> GATE
  PRE --> GATE
  KV --> GATE
  GATE --> EVAL{"分能力评估<br/>+ 相对基线的翻转率<br/>+ 目标硬件上实测的延迟"}
  EVAL -->|"退化集中在<br/>某一项能力"| BACK["把敏感层的精度<br/>提上去，重新测"]
  EVAL -->|"通过"| SHIP["上线，把压缩后的模型<br/>当作独立候选来对待"]
```

从验收测试往回绕的那条线，是压缩项目和压缩 demo 的分水岭：第一个配置几乎从来
不会一次通过，而修法通常是外科手术式的（几层提高精度），而不是整根杠杆放弃。
