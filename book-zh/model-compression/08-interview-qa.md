# 8. 面试问答

压缩这块真正会被问到的问题，按用途分组。最后那些坑题形状都一样：一个数字对
*张量*来说是真的，对*系统*来说是假的。

## 常考

**问：我们的模型又大又慢。讲讲你会怎么下手。**

答：先找出到底是哪个资源卡住了，因为四根杠杆撬的是不同的资源。内存上限就是权重
量化，从 int8 逐通道开始，不够再上 int4 分组。小 batch 的 decode 延迟也是这根杠杆，
因为 decode 受带宽限制，每 token 的时间跟着读取的字节数走。prefill 或者高 batch
吞吐意味着成本是 FLOPs，那纯权重那套招几乎没用，我需要一个计算侧的格式（fp8）
或者一个结构上就更小的模型。长上下文的服务成本意味着 KV cache 占主导，顺序是先
架构（GQA 或 MLA），再分页，最后量化 KV。做这些之前我会先把免费的杠杆过一遍：
连续批处理、前缀缓存、投机解码，它们买到速度但不花质量。然后是验收测试：在目标
硬件上实测的延迟和内存，以及对照未压缩模型、分能力的逐题配对质量比较。

**问：纯权重量化和权重加激活量化，各自什么时候需要？**

答：纯权重让模型变小，并加速受带宽限制的 decode 阶段，int8 下几乎无损，int4 配
分组 scale 也能用。它不改变算术：kernel 会反量化，然后在更高精度上做乘法，所以
FLOPs 没变，prefill 也不受影响。想让计算本身变便宜，就得连激活一起量化，而这难
得多，因为激活分布里有极端的离群通道。这就是为什么 fp8 在支持它的硬件上很有吸引
力：同样位宽下，浮点的指数位对离群值的容忍度远好过 int8，而且它在两个阶段都能带
来真实的提速。

**问：激活量化为什么难这么多，你怎么处理？**

答：少数几个激活通道的数值比其余大好几个数量级，而且它们在功能上是重要的，所以
一个宽到能表示它们的 scale，留给其他所有值的分辨率就几乎没有了。修法有四类：把
离群通道留在高精度上并把矩阵乘拆开（LLM.int8）；用逐通道 scaling 把离群值搬进
权重张量（SmoothQuant）；取整之前保护由激活量级识别出来的显著权重通道（AWQ）；
或者用一个正交变换旋转基底，让任何一个坐标都不再是离群值，在旋转后的空间里量化
（QuaRot、SpinQuant）。旋转这一类正是让 4-bit 激活和 4-bit KV 变得实用的东西，
运维上的要求是旋转必须在导出时融进相邻矩阵，这样运行时才不花钱。

**问：非结构化、2:4，还是结构化剪枝，怎么选？**

答：看硬件能为什么形状省下工作量。非结构化稀疏在给定稀疏度下质量最好，但在稠密
矩阵乘单元上没有提速，所以除非你有稀疏存储和稀疏 kernel，它就是一项省内存的技术。
2:4 模式之所以存在，是因为稀疏 tensor core 真能跳过它；同样的名义稀疏度下它比
非结构化更伤质量，恰恰是因为这个约束是刚性的。结构化剪枝去掉的是头、通道或整层，
产出一个更小的稠密模型，到哪儿都快，代价是需要一轮以几十亿 token 计的修复训练。
能重训的话，结构化剪枝加从父模型蒸馏是最强的选项；不能重训的话，按每省一份资源
换到的质量算，量化通常胜过一次性剪枝。

**问：压缩后的模型怎么评估？**

答：不看 benchmark 平均分。压缩是把行为打散，不是把行为整体挪一下，所以两个模型
可以报出同样的准确率，却在很大一部分单题上给出不同答案。这套测试有四块：对照
未压缩基线的逐题配对比较，并报出翻转率；分能力切片，因为损伤是集中的（代码、
工具调用和 JSON 合法性、长上下文检索、多语言、拒答行为是常见的重灾区）；在目标
硬件上、按生产的 batch 和上下文长度实测延迟、内存和吞吐，而不是在 batch 为 1 的
脚手架里测；再加一次线上流量的影子跑，把输出和当前模型逐条对比，这能抓到离线
集合抓不到的格式退化。

**问：长上下文的负载该压什么？**

答：KV cache，因为它是那个随上下文和 batch 增长的项，而权重是固定的。顺序是先
架构（一个用 grouped-query 或 latent attention 的模型，胜过事后去压一个 KV 头很
多的模型），然后分页分配，让省下来的内存变成 batch 而不是碎片，然后才是 cache
本身的量化，key 按通道、value 按 token，因为它们的离群结构不一样，最后才是淘汰
或者开窗，因为那会改变模型能注意到什么。KV 明明占主导却去压权重，是在解错的那
一半问题。

**问：换成端侧，答案有什么变化？**

答：三个约束替换掉了服务端那些：一个和操作系统共享的硬内存上限；一块只在一小串
格式上跑得快的加速器；以及 batch 恒等于 1。batch 为 1 是纯权重量化的最好情况，
每 token 的收益是最大的。但硬上限通常意味着一个被重度压缩的大模型还是装不下，
所以上线的套路是：一个为目标尺寸蒸馏出来的小模型，量化到 NPU 能加速的格式，在
一个常驻底座上换任务专属的 adapter，再配一个服务端模型接住超出它能力的请求。

## 有坑的（拉开差距的追问）

**问：你想剪枝、蒸馏又量化，什么顺序？**

答：先剪枝，再修复或蒸馏，最后量化，而且要重新评估组合后的产物而不是各个步骤。
道理是每一步都该作用在一个已经处于最终结构形态的模型上：量化的 scale 是照着它
看到的权重拟合的，所以在剪枝之前量化，等于把 scale 拟合到你马上要删掉的权重上；
而量化之后再做一轮修复训练会和量化器打架，除非它是量化感知的。另一条排序规则是
修复步骤需要全精度梯度，所以它该排在最后那次量化之前。如果既要激进的位宽又要
结构改变，组合起来的路径是：剪枝，以父模型为老师做蒸馏，最后一步用量化感知训练。

**再深一层：**"评估组合"不是咬文嚼字：每一步都只是小幅度地过了自己那道关，而且
误差并不独立，因为剪枝和量化都把损伤集中在同一批对离群值敏感的通路上。两根各花
一分的杠杆，合起来可能花掉四分。

**问：你量化到了 int4，benchmark 平均分守住了，用户却反馈工具调用里的 JSON 坏了。
发生了什么，你怎么办？**

答：这是压缩最典型的失败：损伤是真实的，而且恰好集中在平均分会掩盖掉的那项能力上。
结构化输出依赖模型把高概率压在少数几个确切的 token 上，而低 bit 量化会把这些
余量压平，所以格式先崩，语义后崩。诊断办法：在一个工具调用集合上做逐题配对比较，
报合法率而不是一个质量分，并算出逐层敏感度。修法几乎从来不是回滚量化，而是把
真正要紧的那几层精度提上去，通常是输出投影、embedding，以及第一个和最后一个
block，然后重测。受约束的 decoder 或者语法是一个互补的缓解手段，但不该用它来
糊住一个你还没量化过的退化。

**问：校准集从哪里取，取坏了会怎么表现出来？**

答：从服务分布里取，包含你在意的那些形态：长上下文、代码、工具调用格式，以及你
服务的每一种语言。后训练量化是照着它观察到的激活来拟合 scale 的，所以一个由通用
网页文本构成的校准集，拟合出来的 scale 会对不上你真实的流量。它表现出来是：模型
在公开 benchmark 上看着挺好，偏偏在你的负载上退化，而这是最难归因的失败，因为
公开数字替这个产物开脱了。几百条挑好的样本就够了，代表性远比数量重要。

**问：有人提议用 QLoRA 把模型量化了拿去服务，对吗？**

答：不对，而且这个混淆值得掰开讲。QLoRA 把底座量化到 4-bit，是为了便宜地做*微调*，
在一个冻结的量化底座上训一个更高精度的 adapter。它是一项训练显存的技术。产出
服务产物的是后训练量化（GPTQ、AWQ、fp8 配方）；而当 PTQ 在你需要的位宽下守不住
质量时，你要做的是量化感知训练，通常还配上一个来自全精度老师的蒸馏损失。相关的
一个实践陷阱是：针对全精度底座训出来的 adapter 不一定能干净地迁到量化产物上，
所以 adapter 该针对你真正会部署的模型来训，至少也要在它上面验证。

**问：你怎么决定哪些层保留更高精度？**

答：靠测，不靠猜。做逐层敏感度分析：一次量化一层（或一个 block），其余保持全精度，
在一个不大但能力覆盖多样的评估集上记录差值。结果是一个排序，你的内存预算从最上
面开始花。有几条先验值得作为起点，因为它们跨模型都成立：embedding 和输出投影
占参数的一小部分、占损伤的一大部分；第一个和最后一个 transformer block 通常比
中间的更敏感；norm 和 bias 太小了，永远留在高精度里。产出是一个混合精度画像，
它的有效位宽比名义位宽高一点，而这就是一个上线产物正常的样子。

**问：一个压缩过的大模型，还是同家族里一个更小的模型，怎么选？**

答：把它们当成两个候选，放在同一套验收测试里比，而不是比参数量。小模型是照着这个
尺寸训出来的，容量分配是自洽的，也没有离群敏感性带来的损伤；压缩过的大模型保留
了更多父模型的知识，还有很重要的一点，保留了父模型行为上的怪癖，而当 prompt 和
评估都是照着父模型调的时候，这一点很值钱。经验法则：中等压缩下通常是压缩过的
父模型质量更好；激进压缩下，或者目标格式被硬件钉死时，原生的小模型更好；而如果
你需要和父模型的行为兼容，把父模型蒸馏进小模型能两头都要到。

## 常答错的（那些坑）

**问：从 fp16 换到 int4，我们的服务成本大概能砍到四分之一。对吗？**

答：不对。它把权重的*字节数*砍到大约四分之一，在小 batch 下这几乎能换算成每 token
的 decode 延迟，因为那个阶段受带宽限制。它完全没有减少 FLOPs，所以 prefill 不受
影响；而随着 batch 变大，decode 阶段把权重读取摊到很多行上，逐渐漂向受算力限制，
收益就缩到接近于零。生产服务成本由你实际跑的那个 batch 下的吞吐主导，所以诚实的
答案是去那个 batch 上测。如果目标是高 batch 下每百万 token 的成本，杠杆是 fp8 这
类计算侧格式，或者一个真的更小的模型。

**再深一层：**还有一个反方向的下限：一条没有融合的先反量化再矩阵乘的路径，会让
量化后的模型比原来*还慢*，因为你给每个权重加了活儿，却一点算术都没减掉。你的
形状、运行时和硬件上到底有没有融合 kernel，是比你挑了哪个量化算法更重要的问题。

**问：我们剪掉了 50% 的权重，推理应该快一倍吧。**

答：只有当这个稀疏的形状是硬件能跳过的时候才行。在稠密矩阵乘单元上，非结构化的
零和别的数一样要乘一遍，所以一个 50% 非结构化的模型跑得和原来一样快，而且只有
你同时用稀疏方式存它才省内存。稀疏 tensor core 加速的是 2:4 这种半结构化模式；
结构化剪枝则在任何地方都有真实提速，因为矩阵是真的变小了。谁一报稀疏度百分比，
第一个问题就是它是三者中的哪一种，第二个问题是实测延迟是多少。

**问：压缩后的模型在我们的 benchmark 上和原模型打平，所以这次压缩是免费的。**

答：平均分打平不等于行为打平。压缩后的模型经常保住了总分，却在相当一部分单题上
和基线不一致：赢的和输的在均值里抵消了。这很要紧，因为你的 prompt、few-shot
样例、护栏和下游评估都是照着原模型的行为调的，所以哪怕平均分没动，翻转照样会
弄坏东西。要报出配对的翻转率和分能力切片，并且把和父模型的偏离本身当作一项成本，
哪怕准确率没变。

**再深一层：**要补的这个测量很便宜：在一个固定集合上，逐题记录基线和压缩后的
输出，算出不一致率，有输出概率的话再加一个分布距离。一次准确率守住且翻转率很低
的压缩才是真的安全；准确率守住但翻转率很高的，那是另一个模型套着同一个分数。

**问：1.58-bit 的模型都有了，我们把自己的量化到 2-bit 应该没问题。**

答：那些模型是*在那个区间里训练出来的*，权重是在预训练过程中学会做三值的。把现有
模型后训练量化到 2-bit 甚至更低会急剧退化，因为网络从来没学过对那个量化器保持
鲁棒。在一个现成模型上做到很低位宽，路径是带蒸馏损失的量化感知训练，那要花掉一次
训练；而且即便如此，大多数生产技术栈停在 4-bit 权重加分组 scale 再加一个混合精度
画像这里。

**问：蒸馏总是比直接训小模型好。**

答：不总是。蒸馏赢在：卡住你的是数据预算而不是算力，因为软目标每个 token 携带的
信息远多于硬标签；老师明显强过任何你能直接训出来的东西；或者和父模型的行为兼容
很重要。打平甚至更差的情况是学生容量远低于老师，覆盖型的目标函数会把一个小学生
摊薄在它表示不了的模态上，而且整个训练过程都要付老师推理的钱。还有两个副作用要
说出来：从长推理轨迹蒸出来的学生会继承它们的长度，也就继承进了你的延迟和成本；
学生还会继承老师的污染，而你怎么清洗自己的语料都撤销不了。

**问：长上下文的话，先量化 KV cache。**

答：它很少是第一步。最大也最持久的 KV 缩减来自架构：grouped-query 或 latent
attention 按一个固定的乘性因子砍掉 cache，质量代价不大且可以找回来，所以只要模型
选择还开放着，这一步排第一。然后是分页分配，它免费，而且把省下来的内存变成能用的
batch 而不是碎片。然后才是 cache 本身的量化，8-bit 下接近免费，4-bit 下需要分能力
测试。淘汰和开窗排在最后，因为它们改变了模型能注意到什么，那是能力的改变，不是
表示的改变。

**问：我们在评估脚手架里测到了两倍提速，那就完事了。**

答：脚手架通常跑的是 batch 1 加短 prompt，这对纯权重量化是最有利、对生产最不有
代表性的那个配置。回到你真正服务的 batch、上下文长度和并发上，在目标硬件上，用
你将要部署的运行时和 kernel 重新测。另外在启动时断言数值路径：好几套技术栈在缺
kernel 的时候会悄悄退回更高精度，表现出来就是没有提速、没有报错，外加一个一头
雾水的星期。
