# 5. 蒸馏

量化和剪枝是从一个大模型出发，把它弄伤。蒸馏反过来，从一个小模型出发去教它，
大模型只提供监督信号。它是最贵的一根杠杆，质量曲线也最平滑，所以当目标是一个
真正不同的尺寸档位时，你伸手去够的就是它。

## 软目标为什么比标签带的信息多

拿硬标签训小模型，每个 token 只给它一个 bit 的信息：正确的下一个 token。拿老师的
完整分布去训，还额外给了老师在所有错误答案之间的相对偏好，同样一条样本，信号
密集得多。标准目标函数是老师和学生分布之间带温度的 KL：

$$\mathcal{L} = \tau^{2}\,\text{KL}\!\left(p_{T}^{(\tau)} \,\Vert\, p_{S}^{(\tau)}\right) + \lambda \cdot \mathcal{L}_{\text{CE}}(y, p_S)$$

其中 $p^{(\tau)}$ 是温度为 $\tau$ 的 softmax，它把两个分布都压平，低概率 token 之间的
结构才不会被抹掉；$\tau^{2}$ 这个因子则保证 $\tau$ 变化时梯度量级还能对得上。
前向 KL（老师在前）是覆盖型的：老师在哪里有概率，学生就被推着在哪里也放上概率。
学生容量够时这正是我们想要的，容量不够时它就成了问题。

## 三种模式，以及对 LLM 真正重要的那一种

| 模式 | 学生的训练数据怎么来 | 主要失效方式 |
|---|---|---|
| 离线，老师打分的语料 | 老师在固定语料上的 logits | 最便宜，但学生永远看不到自己犯的错 |
| 序列级 | 在老师生成的序列上训练 | 格式迁移更好；分布仍然是固定的 |
| On-policy | 学生自己生成，老师给学生自己的输出打分 | 训练期间要能访问老师；效果最强 |

on-policy 那一版修掉了限制前两种的分布错配：学生是在它推理时真正会产生的序列上
训练的，而不是在老师会产生的序列上，所以被纠正的错误正是学生真正会犯的错误
（[On-Policy Distillation of Language Models](https://arxiv.org/abs/2306.13649)）。
代价是每一个训练步都要老师打分，于是老师从一个预处理步骤变成了你训练基础设施的
一部分。

## 把蒸馏当作修复步骤

蒸馏在压缩项目里价值最高的用法，不是凭空造一个小模型，而是**修复你刚刚造出来的
那个**。套路是这样：

1. 把一个大的父模型结构化剪枝到目标架构。
2. 用父模型的分布（而不是普通的 next-token loss）把父模型蒸馏进剪完的子模型。
3. 逐题拿子模型和父模型比，而不是和 benchmark 平均分比。

这比预训练那个小模型便宜得多，落点也更靠近父模型的行为，而这正是重点：一个
*和父模型错得不一样*的子模型，会打断上游那些照着父模型调好的 prompt 和评估
（[Compact Language Models via Pruning and Knowledge Distillation](https://arxiv.org/abs/2407.14679)）。

## 学生什么时候能赢过从头训练的小模型

不总是能赢，而面试的追问通常恰恰就是这一句。

**蒸馏赢在**：卡住你的是数据预算而不是算力预算（软目标每个 token 的信号更密集）；
老师明显强过任何你能直接训出来的东西；或者和父模型的行为兼容性很重要（同样的
格式、同样的拒答、同样的工具调用风格）。

**打平甚至更差的情况**：学生的容量远低于老师，覆盖型的目标函数会把学生摊薄在
它根本表示不了的那些模态上；或者老师只比直接训出来的模型强一点点，那你付了老师
推理的钱，拿到一个差不多的结果。前一种情况正是那些寻峰型（反向 KL 一类）变体
存在的理由。

有两条实践中常碰到的注意事项：

- **蒸馏推理轨迹会把输出长度撑起来。** 从长 chain-of-thought 轨迹里蒸出来的学生
  学会了照样产出长轨迹，这会改变你的服务成本和延迟预算。除了质量，还要量每条
  回复的 token 数。
- **蒸馏会连老师的污染和偏见一起继承过来。** 老师要是见过 benchmark 题目，学生的
  分数就因为继承而虚高，而对*你自己*语料做任何去污染都抓不到这一点（见
  [给模型做 Benchmark，第 4 节](../benchmark-eval/04-contamination-and-validity.md)）。

## 什么时候用哪个

| 用什么 | 什么时候 | 而不是 |
|---|---|---|
| 离线的老师打分蒸馏 | 语料是固定的，训练期间没法把老师跑起来 | on-policy，当卡住你的是访问老师这件事 |
| 序列级蒸馏 | 主要是想把老师的格式和风格搬进一个更小的模型 | 只做 logit 匹配，它迁移的表层行为更少 |
| on-policy 蒸馏 | 负担得起把老师打分放进循环，而且想要最强的学生 | 离线蒸馏，它从来不纠正学生自己的错误 |
| 先剪枝再蒸馏 | 需要更小的模型，手上有个大父模型加一笔不大的 token 预算 | 从头训练目标尺寸 |
| 带蒸馏损失的量化感知训练 | 已经压到 4-bit 以下，PTQ 保不住质量 | PTQ 加混合精度，在它不再管用之后 |
| 不做蒸馏 | 现成的小模型已经达标 | 定制一个学生，从此被绑在一条训练流水线上 |

**出处。** 软目标蒸馏是 Hinton 等人（Google，2015）；语言模型上的 on-policy 形式是 generalized knowledge distillation（Google DeepMind，2023）；剪枝加蒸馏的生产配方是 Minitron 这条线（NVIDIA，2024）。

**工具。** 蒸馏跑在普通的训练技术栈上（PyTorch 配 DeepSpeed 或 Megatron-LM）；TRL 和 Axolotl 覆盖 SFT 形态的那些变体，on-policy 的方案则是一个服务运行时（vLLM 或 SGLang）负责学生采样，加上训练循环里老师打分那一遍。离线变体真正的约束是老师 logits 的存储：完整词表分布很大，所以对老师分布做 top-k 截断是标准做法。

**实例。** 一个团队要做端侧助手，手上有一个很强的 30B 级父模型。从头训一个 3B 模型超预算，于是他们把父模型结构化剪枝到目标形状，再把父模型蒸馏进去，语料取自真实产品流量而不是通用文本，用的是 top-k 的老师分布。因为学生将来会被拿去跑和父模型同样的 prompt，验收是逐题和父模型配对比较并报告翻转率，而不是一个 benchmark 平均分。他们除了质量还量回复长度，因为父模型的推理风格会一起迁移过来，不管的话会把端侧延迟预算撑爆。只有学生通过之后，才量化到设备加速器支持的格式，并且在量化后的学生上重跑同一套验收测试，而不是假定这两步能自动叠加。

## 实现上的坑

| 问题 | 症状 | 修法 |
|---|---|---|
| 学生容量远低于老师 | 学生流利但浅；覆盖型目标把它摊薄了 | 选一个更大的学生，或者换寻峰型目标，或者把任务范围收窄 |
| 只做离线蒸馏 | 在老师生成的文本上好看，在自己的输出上很脆 | 转到 on-policy，让被纠正的是学生自己的错误 |
| 在通用语料上蒸馏 | 学生偏偏就在你的流量上比父模型差 | 蒸馏语料从真实产品流量里取 |
| 忽略输出长度 | 质量守住了，延迟和成本却退化了 | 把每条回复的 token 数当作一等指标来跟踪 |
| 拿学生跟 benchmark 比而不是跟父模型比 | 学生"MMLU 打平"，调好的 prompt 却崩了 | 逐题和父模型配对比较，并报告翻转率 |
| 继承了老师的污染 | 学生的 benchmark 分数好得不像这个尺寸 | 用截止日期之后的题或私有题来评；把继承来的污染当作下游修不了的事 |
