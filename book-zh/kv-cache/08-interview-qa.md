# 8. 面试问答

面试官在长上下文服务这块真正会问的问题，按用途分组。
"常被答错的"那一节，才是面试拉开差距的地方。

## 常考的

**问：为什么 decode 受显存带宽限制，prefill 受算力限制？**

答：decode 阶段每一步都要把整个模型读一遍（7B 模型 FP16 大概 14 GB），
还要把整个 KV cache 读一遍，就为了吐出一个 token。做的 FLOPs 和读的字节数之比大约是
1 FLOPs/byte；而现代 H100 要达到受算力限制，得有大约 150 FLOPs/byte。decode 永远远在这个线之下。
prefill 阶段是 $S$ 个 token 一次性处理，同一次权重读取被摊到全部 $S$ 个 token 上：
算术强度升到大约 $S$ FLOPs/byte，在 $S \approx 150$ 个 token 往上就越过了受算力限制的门槛。
该伸手去拿哪个修法，取决于哪个阶段是墙，所以先 profile 再优化。

**问：KV cache 的显存公式是什么，为什么它重要？**

答：$\text{kv-bytes} \approx 2 \cdot L \cdot S \cdot h_{\text{kv}} \cdot d_{\text{head}} \cdot b \cdot B$。
一个 32 层 GQA 模型（8 个 KV 头，$d_{\text{head}} = 128$，FP16，batch 为 1）上单条 100k token 的会话：
$2 \times 32 \times 100000 \times 8 \times 128 \times 2 \approx 13.1$ GB。
同一个模型的权重是 14 GB。并发 100 条会话时 cache 就是 1.3 TB，而权重还是 14 GB。
长上下文下吃显存的是 KV cache，不是权重。所有杠杆（GQA、MLA、量化、分页、前缀缓存）
都是在打这个公式里某一项的主意。

**问：GQA 是什么，为什么它成了多数现代模型的默认选择？**

答：分组 query 注意力让一组 $g$ 个 query 头共享一个 KV 头，把 $h_{\text{kv}}$ 从 $h_q$ 降到 $h_q / g$。
$h_q = 32$、$g = 4$ 时 $h_{\text{kv}} = 8$，cache 小了 4 倍，质量接近 MHA。
从现有的 MHA checkpoint 转过来，做个 uptraining 就行，大约花预训练算力的 5%。
服务栈不用改。转换容易加上省显存明显，这两点合在一起，让它成了 Llama 3、Mistral、Gemma
以及 2023 年之后大多数生产模型的默认选择。

**问：PagedAttention 解决的是什么问题？**

答：碎片。没有分页时，每条序列在到达时预留一整块连续的 KV 缓冲区。
序列在不同时刻到达和结束，释放出来的缓冲区留下的空洞装不下大小不同的序列（外部碎片），
而且每块缓冲区尾部还可能有用不上的空间（内部碎片）。
PagedAttention 用定长块管理 cache，每条序列配一张块表，跟操作系统的虚拟内存一模一样。
块可以散落在显存的任何地方，碎片趋近于零。结果是在同等吞吐下并发能力提升 2 到 4 倍。
它并不会让单个请求更快，它是把更多并发请求塞进同一块 GPU。

**问：为什么前缀缓存能改善首 token 延迟？**

答：因为它跳过了 prefill。prefill 阶段的开销就是给所有 prompt token 建 KV cache 的算力成本。
当一个请求和之前缓存过的请求共享一段前缀（system prompt、共享文档），
服务栈会直接复用那些 KV 块：这些 token 一点 prefill 都不用算。
模型从第一个不一样的 token 开始直接进入 decode。
如果有一段 4k 的共享 system prompt 每次请求都命中缓存，
首 token 延迟就从 4000 个 token 的 prefill 掉到接近一步 decode 的开销。

## 有坑的（拉开差距的追问）

**问：GQA 和 MLA，什么情况下你愿意为 MLA 多担这份复杂度？**

答：当 KV cache 是长上下文下真正的约束，而且训练在你手里的时候。
GQA 缩的是 $h_{\text{kv}}$，把 cache 按一个固定比例减小（一般是 $4x$ 到 $8x$）。
MLA 则把整个 K/V 存储换成一个 $d_c$ 维的潜向量，相比 MHA 大约压缩 93%，
而且跟头数多少无关。当连 GQA 都不足以让你在目标上下文长度和并发下摆脱显存限制，
下一步就是 MLA。代价是实打实的：RoPE 分头设计必须在训练时就烙进去，
而且解码每一步的上投影会多一点算力开销。如果你服务的是一个改不了的现成模型、无法重训，
那 MLA 就不在选项里，能上的是 GQA uptraining 或者 KV 量化。

**为什么 MLA 的压缩率和头数无关：**cache 里存的是每个 token 一份共享的潜向量，
而不是每个头一份 key 和 value，所以省下来的量取决于潜向量的宽度 $d_c$，跟有多少个头来读它没关系。
重建各头 key 的那个上投影，可以在代数上被吸收进 query 投影里，
这也是为什么 decode 时直接读潜向量并不会额外产生逐头重建的开销。

**问：你服务的是一整个 GPU 节点集群，不是一台机器。前缀缓存在这里会怎么坏掉？**

答：单节点的前缀缓存不跨节点。请求 A 在节点 1 上为一段共享 system prompt 建好了 cache，
请求 B 却被路由到节点 2，那 B 就不命中，明明刚刚算过同一段前缀，它还是要付全额 prefill 成本。
在集群规模上配轮询路由，实际命中率会比单节点数字看起来低得多。
修法是缓存感知路由：把共享同一段前缀的请求路由到持有这些前缀块的那个节点上。
llm-d 的缓存感知调度做的就是这件事。它增加了路由的复杂度，但把前缀缓存的命中率收益在多节点规模上找回来了。

**为什么这是个真实的取舍而不是白捡的修法：**缓存感知路由会把所有共享某个热门前缀的请求
都钉在持有它的那个节点上，这是在集中负载而不是分散负载。
所以路由器必须在"命中缓存（prefill 便宜）"和"排在所有想去同一个节点的人后面"之间权衡，
过了某个热度阈值，把前缀复制到第二个节点、多付一次 prefill，反而比继续往热点上堆更快。

**问：估算一下 Llama 3 8B 服务 1000 条并发会话、每条 32k token 时的 KV cache。**

答：Llama 3 8B 有 $L = 32$ 层，$h_{\text{kv}} = 8$（GQA），$d_{\text{head}} = 128$，FP16。

$$\text{kv-bytes} = 2 \times 32 \times 32000 \times 8 \times 128 \times 2 = 4.29 \text{ GB per session}$$

1000 条并发会话就是 4.29 TB。单个 H100 节点（8 张卡，每张 80 GB，一共 640 GB）装不下。
你需要以下之一：(a) 激进的前缀缓存，把每条会话的有效 S 降下来；(b) KV 量化，压缩单会话的占用；
(c) 多节点加缓存感知路由；(d) 会话淘汰。
能在一个真实模型上把这笔账算出来，是对"你会怎么把它扩上去"这个追问最有力的回答。

**问：小的 draft 模型能靠投机解码加速 decode。什么时候它没用？**

答：当 target GPU 已经跑满的时候（大 batch、受显存限制的 decode）。
投机解码是借 target 模型的一次并行前向一口气验证 $k$ 个草稿 token，减少昂贵的 target 步数。
但这只有在那些 target 步骤本身就是瓶颈时才有用。
batch 非常大的时候，GPU 已经逼近显存饱和；再加上 draft 模型的算力和更长的验证序列，
只会让总的显存压力更大，却解不开这个瓶颈。
投机解码赢得最干净的场景，是中低 batch 加上结构化或者可预测的输出（代码、格式固定的回复）。

**问：为什么 MLA 需要一个专门的"解耦 RoPE"头，而不能像别的地方一样直接对潜向量施加 RoPE？**

答：因为 RoPE（Su 等人，2021）是用一个跟位置相关的矩阵去旋转 key，
而 MLA（DeepSeek，2024）想的是每个 token 只存一份共享的低秩潜向量，
到算注意力的时候再上投影成各头的 key。这两个目标是冲突的：
如果在压缩之前施加位置旋转，旋转就被烙进了存下来的潜向量里，
你就没法再把上投影从 query 和 key 的点积里提出来，而这恰恰是 MLA 便宜的全部诀窍。
如果在上投影之后再施加，那每一步 decode 都得把重建出来的每个头重新旋转一遍，省下来的又还回去了。
DeepSeek 的解法是把每个头拆成两部分：一个大的压缩部分承载内容，存成不带位置信息的潜向量；
另一个小的独立部分承载 RoPE，直接缓存起来。
面试官爱问这个，是因为"直接给潜向量上 RoPE"是最自然的错误猜测，
它能看出你是否明白 MLA 为什么是训练期的改动，而不是服务端的一层附加物。

**问：GQA 和 KV cache 量化看着差不多，都是把 cache 按一个常数因子缩小。这个区别到底什么时候才有意义？**

答：它们打的是同一个公式里不同的项，而这个区别决定了谁能用它们。
GQA 缩的是 $h_{\text{kv}}$，这是一个架构属性：它必须训练（或者 uptraining）进 checkpoint 里，
因为 query 头得学会去读共享的 KV 投影。量化缩的是 $b$，也就是每个元素占的字节数，它是一种存储格式：
不用训练，服务时就能施加到任何 checkpoint 上。
两者的错误模式在机理上也不同：GQA 减少的是头的多样性，但存下来的是全精度的精确值；
量化保留了每一个头，却扰动了每一条存下来的记录，而 key 上的误差可能会翻转 softmax 里谁胜出。
这个区别在两种情况下有意义：当你服务的是别人的固定模型时，量化是唯一可用的杠杆；
当训练在你手里时，两者是相乘的（8 个 KV 头配 FP8 就是 8 倍乘 2 倍），
所以该问的不是"选哪个"，而是在你的长上下文评测指标动起来之前，每根轴上还能往下走多远。

## 常被答错的（陷阱）

**问：PagedAttention 会降低单个请求的延迟吗？**

答：不会。PagedAttention 减少的是碎片，让更多序列能装进显存，
从而抬高聚合吞吐（所有请求加起来每秒多少 token）。
任何单个请求的每步延迟都没有改善；真要说的话，块表这层间接寻址还给注意力 kernel 加了一点点开销。
它赢的是并发，不是单请求速度。汇报它的收益要用全机队每秒 token 数，而不是单请求的 decode 延迟。

**为什么并发越高吞吐越高：**decode 受带宽限制，每一步那次固定的模型权重读取，
是被 batch 里所有活跃序列共享的。往显存里塞进更多序列，就意味着同一次权重读取能产出更多 token，
所以聚合的每秒 token 数上去了，尽管每条序列本身每步的推进速度还是一样。

**问：logQ 校正（或者任何校准偏移）会在服务时施加到 KV cache 的注意力分数上吗？**

答：不会。这是把两件不相干的事混为一谈了。
候选检索里的 logQ 校正（从 logits 里减去采样概率的对数）是训练期对 softmax loss 做的去偏，
不是服务推理阶段的东西。KV cache 服务里没有任何类似的运行时校正；
KV cache 就是老老实实存精确的 key 和 value（或者它们量化、潜向量压缩之后的等价物），
注意力照常算。如果你听到这个问题的变体，问的是 decode 时"修正"注意力分数，答案也一样：
生产服务栈里的注意力就按存下来的样子读 KV 记录，不做任何分数调整。

**问：权重和 KV cache 能各自独立量化吗？**

答：能，而且它们是两根正交的杠杆，取舍各不相同。
权重量化（INT8、INT4 GPTQ、AWQ）缩小的是模型体积，加速的是 decode 里读权重的那部分。
KV cache 量化缩小的是 cache 体积，加速的是读 cache 的那部分。
长上下文服务里 cache 常常比权重还大，所以在那种上下文长度下，KV 量化的边际收益更大。
两个可以一起上：不少生产栈跑的是 INT8 权重配 FP8 或 INT4 的 KV。
但每一个都需要自己的评测，因为错误模式不一样（权重量化影响所有 token 的计算；
KV 量化伤的是上下文里旧 token 的历史注意力精度）。
还有一个机理上的细节：在 KV cache 内部，key 通常比 value 更敏感，
因为 key 的误差要穿过 softmax，可能翻转哪些 token 拿到注意力权重，
而 value 的误差只是在权重定下来之后扰动加权平均。
所以生产方案里 key 的位宽会比 value 高（或者保留一段全精度的近期 token 窗口），
而不是把两者一视同仁。

**问：MLA 不就是"KV 头更少"的另一种说法吗？**

答：不是。GQA 和 MQA 是字面意义上在减公式里的 $h_{\text{kv}}$：头更少意味着每个 token 的记录更少，
机制是多个 query 头共享一个 KV 头。MLA 走的是一条根本不同的路：
它把满秩的 K 和 V 张量整个从 cache 里去掉了，换成每个 token 一个低秩潜向量。
到算注意力的时候，这个潜向量再上投影成各头的 key 和 value。
cache 里存的是一个 $d_c$ 大小的向量（比如 512），而不是
$2 \times h_{\text{kv}} \times d_{\text{head}}$（比如 $2 \times 32 \times 128 = 8192$）个数值。
把它描述成"头更少"，既说错了机制，也把 RoPE 那个麻烦完全漏掉了。

**为什么一个学出来的潜向量能压这么狠还不伤质量：**这个压缩是端到端训出来的，
模型学到的投影会把注意力真正需要的东西打包进 $d_c$ 维里，
而不是事后去近似一组已经训好的满秩头。
这同样解释了为什么 MLA 不能在服务时硬套到一个现成的 checkpoint 上：
那个潜向量只对训练期就照着它优化过的 query 头才有意义。
