# 1. 澄清需求

动架构之前，先把系统必须做到的事钉死。下面每个问题要么能砍掉一部分工作，要么会把答案整个改掉。

**候选人：** 负载长什么样：长 prompt 配短回答，还是短 prompt 配长回答？

**面试官：** 混合的，但最疼的点是一个 RAG 聊天机器人，带一大段公共的指令块，每个会话有 10 到 15 轮历史。prompt 能到 32k token，回答一般不到 500 token。

**候选人：** 目标上下文长度是多少？8k 和 200k 说的"长上下文"完全是两回事。

**面试官：** 现在是 32k，但产品团队想做到 128k。

**候选人：** 最在意哪个延迟指标：首 token 延迟、token 间延迟，还是两个都要？

**面试官：** 用户两个都能感觉到。首 token 要在 2 秒以内，token 间要在 100 ms 以内。现在负载一上来，p99 decode 延迟（decode 就是逐个生成输出 token 的那个阶段）远远超标。

**候选人：** 质量底线是什么？具体说，能不能量化 KV cache、能不能改注意力架构，还是说我们服务的是一个改不了的第三方模型？

**面试官：** 权重是我们自己的，所以训练时改架构可以谈。量化也行，前提是在我们的评测上质量不掉。

**候选人：** 并发目标呢：同时多少个会话？

**面试官：** 每个 GPU 节点 500 到 1000 个并发会话，流量峰值能到 3 倍。

**候选人：** system prompt 是大部分请求共用一份，还是每个用户不一样？

**面试官：** 有一段 4k token 的 system prompt，所有请求共用。后面的用户历史是按会话来的。

---

总结一下。**我们要服务一个 32k 到 128k 上下文的 RAG 聊天机器人，目标是首 token 延迟 2 s 以内、token 间延迟 100 ms 以内，并发 500 到 1000 个会话，有一段 4k 的公共 system prompt，模型在我们自己手里。** 只要能过长上下文评测，质量可以拿来换显存。

从这里立刻能推出两件事：

**吃掉 GPU 显存的会是 KV cache（把每个历史 token 的 key 和 value 存下来，模型就不用每一步重算），而不是模型权重。** 一个典型的 7B 模型用 GQA 配置（grouped-query attention，多个 query head 共用一组 key 和 value，用来缩小 cache），在 32k token 时单个会话的 cache 就已经超过 1 GB。到了 128k 上下文、1000 个并发会话，这个数字会把权重占用衬得微不足道。搞懂为什么会这样，就是整个成本模型，下一节讲。

**那段 4k 的公共 system prompt 是一份礼物。** 只要推理栈支持前缀缓存（直接复用公共前缀已经算好的 KV，而不是重算），每个复用这段前缀的请求都可以完全跳过它的 prefill（prefill 是一次性的前向计算，为所有 prompt token 建好 KV cache）。单这一件事对首 token 延迟的影响，就比几乎任何其他杠杆都大。早早把它点出来，是一个很强的信号，说明你真的搭过或者认真研究过这类系统。
