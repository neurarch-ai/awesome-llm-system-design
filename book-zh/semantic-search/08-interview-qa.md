# 8. 面试问答

语义搜索与 embedding 服务设计面试里真正会被问到的问题，按面试官的使用方式分组。经常答错的那一组，才是面试的胜负手。

## 常考

**问：为什么不在查询时直接算精确最近邻？**
答：一亿向量、每次距离计算 1 微秒，一次查询就是 100 秒。ANN 检索用一点可控的召回损失，换来 10 到 100 倍的加速。而这点召回损失，会由重排阶段在真正影响精度的少数头部结果上补回来。这里的选择本质上不是"精确还是近似"的路线之争，而是在这个规模上精确检索物理上就太慢。

**问：为什么要在稠密通道之外再跑一路词法通道？**
答：稠密 embedding 会漏掉精确 token 类的查询：商品 SKU、错误码、版本串、人名，以及任何在训练语料里罕见的 token，在 embedding 空间里的表示都可能很差。BM25 天生就能处理这些，而且并行跑一路几乎不花成本。用 reciprocal rank fusion 把两路融合起来，在查询类型混杂的场景下稳定优于单独任何一路。这是面试官期待的标准答案；答不出来就说明你对生产环境的搜索不熟。

**问：检索阶段怎么评估？**
答：在一份带标注的查询-物品集合上量 recall@k，而且要量在你真正往下游传的那个 k 上（比如 100 或 500），不是 k=5 或 k=10。用基于时间的划分（留出未来的查询，评估今天的索引能不能检索出 ground-truth 文档），避免泄漏未来信息。上线要用一次在线 A/B 来把关，量端到端的任务成功率，因为检索召回和下游质量并不总是同向变动。

**问：一篇新文档怎么变成可检索的？**
答：写路径把文档发到队列上；embedding worker 对它编码（用的是跟索引里其他内容同一个编码器）；向量 upsert 进 ANN 索引，文本加进词法索引。两次写入都必须在新鲜度 SLA 之内落地。HNSW 支持增量插入，不用重建；IVF-PQ 则追加到最近中心点的倒排表上。冷启动这种情况不需要特殊处理，因为编码器只吃内容特征，没有任何按文档训练出来的部分。

**问：升级 embedding 模型的时候会出什么问题？**
答：索引里的每一个向量都得重新 embed。新旧向量处在不同的空间里；把它们混在同一个索引里会悄无声息地毁掉召回。安全的做法是：新索引和旧索引并存，在标注集上验证召回，双读一段时间，然后再切流。这是一次全量重建索引事件，不是滚动发布。

## 有坑的（区分候选人的追问）

**问：离线的 recall@k 涨了，线上的端到端质量却掉了。可能是什么原因？**
答：主要有三种。第一，召回的提升来自更多地把热门物品捞上来（它们本来就不容易漏），而长尾的覆盖反而缩小了，用户看到的内容变得不够多样。第二，检索的改进被重排器的质量下滑抵消了，因为召回集合的分布变了。第三，离线评估的查询划分不是按时间来的，所以那点提升来自泄漏（记住了未来的交互）而不是泛化。诊断方法是在召回之外，同时量覆盖率和长尾物品的可检索性。
**为什么聚合指标会掩盖第一种原因：** recall@k 是在标注查询集上取的平均，而标注查询本身就偏向头部内容；于是一个模型可以靠在热门物品上变好、在长尾上变差来赢下这个平均值，数字涨了，可恰恰是那些不在标注集里的查询体验变差了。

**问：有团队说"想要更好的召回，换个更大的 embedding 模型就行了"。对吗？**
答：这很少是第一步该做的事。维度变大，索引内存线性上涨，检索延迟接近线性上涨，在一亿向量上成本是成倍放大的。在花钱上更大的模型之前，先看看这个召回缺口是不是来自词法通道就能补上的领域不匹配，或者干脆是因为没做混合检索。Dropbox 用 MTEB 发现不同模型之间的 MRR 差距很大，说明模型是否契合确实重要，但他们同时也为了 4KB 的存储上限压住了维度。先分别量一下有词法通道和没有词法通道的差距；如果混合检索就能补上，更大的编码器就没必要。
**为什么把模型做大补不上领域缺口：** 扩规模能提升的是训练分布覆盖到的那部分内容的表示质量；一个不在这个分布里的 token 或概念，参数量再大也没有一个有依据的表示。所以问题出在模型见过什么，而不是它有多大，而词法通道解决的正是那种再多容量也学不出来的身份匹配。

**问：HNSW 很流行；什么情况下你不会用它？**
答：两种情况。第一，语料装不进内存：HNSW 要存完整的图加上向量，一亿条 768 维 float32 向量大约是 600GB，这很贵。这时换 IVF-PQ 做压缩，或者用 DiskANN 落到 SSD。第二，需要非常激进的过滤：HNSW 的图遍历没法高效地天然跳过被过滤掉的节点。IVF 或者分区索引可以在扫描之前把检索限制到相关分区，对高选择性的过滤便宜太多。
**为什么过滤会跟图打架：** HNSW 是靠沿边走过一批中间节点才到达目标区域的，而这些"踏脚石"里有很多是过不了过滤的；跳过它们，通往答案的路径可能就断了，留着它们，检索又把预算浪费在永远不会被返回的节点上。分区索引在任何遍历开始之前就把搜索空间缩小了，从根上绕开这个两难。

**问：HNSW 的 ef 和 IVF 的 nprobe 看起来很像（都是把搜索面放宽来换召回）；这个差别什么时候才真的要紧？**
答：两者都是各自索引上那个召回换延迟的旋钮，在分布均匀的语料上，从外面看调哪个都差不多。机制上是不同的：ef 拓宽的是图上一个 best-first 的 beam，所以多出来的工作是自适应的，始终集中在查询的近邻区域；nprobe 加的是一整个预先算好的单元，多出来的工作是粗粒度、固定大小的增量，而且要把新加的每个单元里的东西全扫一遍，不管有没有希望。差别在两种场合会显现：一是查询落在单元边界附近（真正的邻居被切分到不同单元里，于是召回只能随着整个单元被加进来阶梯式上升，而 ef 的前沿可以自然地越过边界）；二是簇的大小很不均衡时，多加一个单元可能让扫描成本翻倍。它还决定了带过滤检索的形态：限制单元对 IVF 很容易，而限制图遍历恰恰是 HNSW 吃力的地方。

**问：MIPS 和欧氏最近邻有什么区别，为什么这对量化很重要？**
答：MIPS（最大内积检索）按文档与查询的点积排序；欧氏 NN 按距离排序。只有向量做了单位归一化时，两者才等价。对双塔点积检索来说，相关的度量是内积，而标准的 PQ 量化（它最小化的是平均重建误差）是按欧氏距离调的。ScaNN 的关键洞察是：对 MIPS 而言，平行于查询向量方向的误差（它直接削减内积）应该比正交方向的误差受到更重的惩罚。拿一个按欧氏距离调过的量化器去做内积检索，会悄无声息地在内积最高的那批物品上损失召回，而那批恰恰是排在最前面的。

**问：什么时候会选 ColBERT 的延迟交互，而不是 cross-encoder 重排器？**
答：cross-encoder（源自 Sentence-BERT，UKP Darmstadt，2019）把查询和文档拼在一起，每一对跑一次完整的 transformer 前向，所以准，但没法预计算：每个候选在查询时都要重新算一遍。ColBERT（Stanford，2020）离线地把文档的每个 token 独立 embed，查询时用 MaxSim 打分：对每个查询 token 取它与文档 token embedding 的最大点积，再把这些最大值加起来。因为文档的 token embedding 是预计算并建了索引的，ColBERT 可以撑起第一阶段检索，或者在很大的候选集上做便宜的重排，用一点精度换来文档编码开销的摊薄。当你需要好于 bi-encoder 的质量、候选量又大到 cross-encoder 承担不起时，就用它；最后那份小短名单还是留给 cross-encoder，那里它的全交叉注意力才划算。

用代码写出来的 MaxSim，能让"把每个查询 token 的最佳匹配加起来"这件事变得具体：

```python
import numpy as np

def maxsim(query_tok, doc_tok):              # query_tok, doc_tok: arrays of shape (n_tokens, dim)
    sims = query_tok @ doc_tok.T             # every query-token vs every doc-token dot product
    return sims.max(axis=1).sum()            # for each query token take its best doc match, then sum
# maxsim(np.eye(2), np.array([[1.,0.],[0.,1.],[0.5,0.5]])) -> 2.0
```

## 经常答错的（陷阱）

**问：查询时要不要对压缩带来的偏差做一个分数修正？**
答：错误答案是"要，在线上从 ANN 分数里减掉一个修正项"。压缩带来的失真（PQ 码、int8 量化）让第一阶段的分数只是近似值，正确的做法是对短名单做一次**全精度重打分**：把原始向量调回来，重新算精确分数。压缩后的分数上没有什么神奇的修正项可用；你需要的是真正的向量。这次重打分很便宜，因为它只在短名单上跑（比如 200 个候选），而不是整个语料。
**为什么根本不可能存在这样一个修正项：** 量化误差是逐向量的，而且跟方向有关，所以两篇压缩后分数完全相同的文档，真实误差可以是一正一负；任何标量的、或者按查询算的修正都会把两个分数往同一个方向挪，换不了它们的顺序。要恢复真实排序，需要的是编码时丢掉的那部分信息，而只有原始向量还留着它。

**问：能不能把 BM25 的词项级特征塞进 embedding 模型，这样只留一路检索通道？**
答：做不干净。embedding 捕捉的是分布式语义；BM25 的精确匹配是另一种信号。把 BM25 特征当输入 token 拼进去，复现不出词法倒排索引在罕见 token 上的召回行为。生产环境的答案是两路通道并行跑然后融合：稠密管语义，词法管精确匹配。想用一个 embedding 模型把两件事都学了，结果是两件事都做不好。
**为什么一个向量装不下两种信号：** embedding 把文本压进固定的若干维，而精确匹配的召回要求分辨出每一个罕见 token 的身份，这部分信息量是随词表增长的；压缩必然要丢掉的，恰恰就是词法匹配所依赖的罕见 token 身份，而倒排索引在构造上就把这个身份精确地存了下来。

**问：语料一共一亿，但只有 100 万篇文档属于"活跃"类目。要不要对 ANN 的结果做后过滤？**
答：不要，至少别那么天真地做。当过滤能放过很大一部分文档时（比如 50%），后过滤 ANN 结果是可行的，因为在一亿上跑 ANN 通常至少能返回 k 篇能过的文档。但如果过滤只放过 1%（一亿里的一百万），在全量语料上跑 ANN，它的头部候选里能匹配的文档可能不足 k 篇，召回直接崩掉。正确的做法是按类目给索引分区，把带过滤的查询直接路由到那个一百万文档的子索引；或者用 IVF 索引，在扫描之前就根据过滤条件限定搜哪些簇。
**为什么通过率一低算术就变得很残酷：** ANN 检索是按相似度排序的，它不知道过滤条件的存在，所以能通过的文档在候选列表里出现的比例大致就是过滤的基础通过率；通过率 1% 时，几百个候选里期望只有寥寥几个能过，而要向索引多要候选来保证凑够 k 个，延迟就要乘上通过率的倒数。

**问：embedding 捕捉的是含义，那混合检索是不是只是给弱 embedding 模型打的补丁？**
答：不是。哪怕一个在全人类文本上训出来的完美 embedding 模型，也召回不了一个训练之后才产生的商品编码的查询。模型没见过的任何 token，映射到的向量所在的邻域反映的是它罕见出现的统计特征，而不是它真正的身份。词法检索和语义检索在结构上是互补的，不是弱模型的替代品。
**为什么没见过的 token 会落到错误的位置：** 分词器会回退到子词片段，于是一个新的商品编码被 embed 到那些共享它字符片段的字符串旁边；那是拼写相似伪装成了语义相似，而任何在历史数据上的训练目标，都没法给这个编码赋予它真正的身份。

**问：给 ANN 索引多加几个分片，召回就能变好，对吧？**
答：不对；除非做出补偿，否则通常反而会掉召回。分片是把语料切成 N 份，每个分片返回自己的局部 top-k，然后再合并。HNSW（Malkov 和 Yashunin，2016）的召回是逐分片的：一次本来遍历完整图就能找到真正邻居的查询，现在可能落到某个局部图里根本没有那个邻居的分片上，而合并环节救不回任何一个分片都没捞出来的文档。分片买到的是吞吐和内存余量，不是召回；要守住召回，必须提高每个分片的 ef，或者过量取（每个分片要多于 k 个），让合并环节有足够的候选可用。把分片数当成召回旋钮，等于把真实的权衡关系搞反了。
