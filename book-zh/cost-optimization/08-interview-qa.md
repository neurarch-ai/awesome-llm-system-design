# 8. 面试问答

面试官在成本优化和模型路由这块真正会问的问题，按常见用法分组。面试的输赢，往往就在那些经常被答错的问题上。

## 常考题

**问：面对一个你从没见过的系统，你会从哪儿下手？**
答：先在前面架一个网关，让开支变得可观测，然后 profile 钱到底花在了哪里：是输入 token（检索过多、prompt 太长）、输出 token（生成太长），还是请求量（大模型上的高 QPS）？这一次测量就决定了先动哪个杠杆：输入成本就裁剪加压缩，输出成本就路由加 right-sizing，请求量就上缓存。跳过 profiling 直接上路由或缓存的设计，经常优化的是错的那一项。

**问：什么时候用路由器，什么时候用级联？**
答：这是延迟上的取舍，不是质量上的取舍。路由器在任何生成发生之前就盲判，所以适合延迟 SLO 很紧的场景，但它没法知道自己什么时候判错了。级联先跑便宜模型，给自己的答案打分，只在拿不准的时候升级；它能抓住自己的错误，代价是多一次首轮调用加一个打分器。延迟有余量，而且有一个可信的置信度信号（可验证的任务：代码、SQL、引用），就用级联。SLO 很紧就用路由。两者也能叠：先路由把流量分桶，再在拿不准的中间那一桶里做级联。

**问：语义缓存的相似度阈值取多少合适？**
答：没有一个放之四海的答案，要在一份标好"应该命中"和"不该命中"的样本对数据集上扫一遍，挑一个在把错邻居答案的比例压在质量容忍度以下的前提下、命中率最高的阈值。常见的错误是拿裸命中率来调：阈值一放松，命中率涨了，同时被返回的响应里错的那部分也可能涨。

**问：估一下路由器能省多少。**
答：路由器的单请求节省：$S = f_{\text{weak}} \cdot (c_{\text{big}} - c_{\text{small}}) - c_{\text{router}}$。

```python
def router_savings(f_weak, c_big, c_small, c_router):
    # savings = big-vs-small gap captured on the weak-handled fraction, minus router cost
    return f_weak * (c_big - c_small) - c_router
# e.g. router_savings(0.5, 10.0, 2.0, 0.25) -> 3.75
```

$f_{\text{weak}}$ 要用一份真实流量样本量出来（有多大比例的查询，小模型答出来能过线？），不能用一个希望它是的数。一个常见的坑是假定便宜模型能接住 70% 的流量，而在一份难度足够的评测集上量出来的实际数字是 40%。

**问：语义缓存可能出什么问题？**
答：三种失效模式。第一，阈值太松，把邻居的答案返回给了一个其实完全不同的问题（又自信、又便宜、又错）。第二，易变的事实从缓存里出来就过期了，要设 TTL。第三，共享缓存用在有权限范围或个性化的答案上，会把用户 A 的响应泄露给用户 B；要么给缓存 key 加上范围，要么个性化内容干脆不缓存。

## 有坑的题（能分出高下的追问）

**问：路由器上线之后账单降了 40%。质量保住了吗？**
答：没有分桶的质量追踪就答不了。成本降了却没有配套的质量数字，那是一次悄悄的回退，不是胜利。成本看板一片绿，恰恰就是路由器把新变难的查询甩给小模型时的特征。该汇报的是每个路由分桶各自省了多少成本、保住了多少质量，难的长尾也要算进去。如果没测，正确答案是"我不知道，而这本身就是个问题"。

**再深一层：** 这个盲区是结构性的，不是偶然的。总体质量指标被占多数的简单流量主导，所以一个集中在难长尾（只占很小一部分请求）上的回退，几乎不会让均值动一下。只有在固定的难长尾切片上按分桶测质量才能暴露它，这也正是为什么总体看板保持绿色是这种失效的特征，而不是它没发生的证据。

**问：大家都在用语义缓存。是不是永远都该部署一个？**
答：只有命中率过了盈亏平衡点才值得：$h^{\ast} = c_{\text{embed}} / (c_{\text{model}} - c_{\text{hit}})$。

```python
def cache_breakeven(c_hit, c_embed, c_model):
    return c_embed / (c_model - c_hit)   # hit rate above which caching nets positive
# e.g. cache_breakeven(0.005, 0.02, 1.0) -> 0.020100502512562814  (about 2%)
```

按典型数字算大约是 2%，但如果流量几乎全是各不相同的自由文本查询（比如一个通用助手），就算调好了的语义缓存也可能达不到盈亏平衡。上缓存之前，先在样本上量一下自然命中率。

**再深一层：** 被服务的模型越便宜，盈亏平衡点 $h^{\ast}$ 反而越高，因为分母 $c_{\text{model}} - c_{\text{hit}}$ 变小了，而 embedding 成本 $c_{\text{embed}}$（不管命中还是未命中，每条请求都要付）是固定的。所以一份已经被路由到便宜小模型的负载，即使命中率看着挺体面，缓存也可能是净亏的，这和"缓存永远是白捡的钱"那个直觉正好相反。

**问：更大的 LLM 更慢、单 token 更贵。是不是任何一个子任务都能换成小模型？**
答：不一定。在窄而稳定、有标注的任务上，微调过的小模型经常追平甚至超过前沿模型。而在需要广泛推理、需要新的世界知识、或者要在长上下文里跟随指令的任务上，小模型是真的会退步。判据是把两个都放到你自己的评测集上跑一遍，而不是往任何一边假定。运维成本也是实打实的：机队里每多一个模型，就要多评测、多监控、多更新一份。

**再深一层：** 退步专门出现在落在微调训练分布之外的输入上，所以今天能通过离线评测的小模型，明天照样可能栽在没见过的表述上。所以真正的风险是分布漂移：评测集必须对着线上流量持续刷新，否则差距会在离线数字仍然保持绿色的同时悄悄重新拉开。

**问：LLMLingua 压缩在什么情况下才真的划算？**
答：当输入 token 省下来的钱超过压缩这一趟本身的成本时：$c_{\text{big}}
\cdot (n_{\text{orig}} - n_{\text{comp}}) \gt c_{\text{small}} \cdot n_{\text{orig}}$。

```python
def compression_net_win(c_big, c_small, n_orig, n_comp):
    # gain from tokens removed on the big model vs cost of the small-LM pass over the full prompt
    return c_big * (n_orig - n_comp) > c_small * n_orig
# e.g. compression_net_win(10.0, 1.0, 1000, 200) -> True
```

Prompt 很短、或者负载以输出为主的时候，小语言模型这一趟纯属额外开销。而在又长又啰嗦、冗余很多的 RAG 上下文上（检索了 20 个 chunk，里面一堆重复的样板文字），它能带来 5 到 10 倍的回报。上压缩之前先 profile 账单；先裁到 top-3 chunk，因为那是零成本的，而且往往已经拿走了输入 token 减少量的大部分。

**再深一层：** 压缩这一趟本身就是让小语言模型在完整的原始上下文上前向一遍，给每个 token 的重要性打分，所以它的成本随 $n_{\text{orig}}$ 而不是 $n_{\text{comp}}$ 增长。这就是盈亏平衡背后的机制：输入很短或以输出为主的负载上，这一趟纯属额外开销，因为它删掉的 token 本来就不值钱；只有当被删掉的输入 token 既多、在大模型上又贵的时候，收益才真的出现。

**问：上下文裁剪和 LLMLingua 那类压缩看起来很像，都是把 prompt 变小，两者的差别到底什么时候才重要？**

答：两者都在大模型调用之前减少输入 token，而在一份注了水的 RAG prompt 上，用哪个都能把账单压下来。差别在粒度和代价上。裁剪是按相关性分数整块丢掉检索到的 chunk，而这个分数流水线往往本来就算好了，所以近乎免费，留下来的文本一个字没动。压缩则要让小语言模型在整段原始上下文上前向一遍给每个 token 打分，然后在模型真正要读的文本内部删掉信息量低的 token。差别在两种情形下才重要。如果浪费在 chunk 之间（检索了 top-20，其中 17 个是填充），裁剪几乎能拿走全部节省而且没有质量风险，压缩只是加了成本换来一点点额外收益。如果浪费在 chunk 内部（答案要从一堆啰嗦的样板文字里抽出来），裁剪够不着，只有 token 级的压缩才有用，代价是那一趟打分，以及删掉答案所依赖的那个 token 的风险。正是这个风险分布，决定了裁剪在抽取类任务上是安全的，而压缩不是。

## 经常被答错的题（陷阱）

**问：能不能在路由器里加一次前沿模型调用，让它判得更准？**
答：不行。路由器必须严格便宜于它所把守的最便宜那个模型。用前沿模型来做路由，意味着每条请求都要付一次前沿价格，再加上被路由到的那一部分的模型调用。路由器的成本 $c_{\text{router}}$ 在公式里是从节省中扣掉的；它大到一定程度，节省就变成负的了。用分类器、启发式规则，或者一个小的微调模型。

**再深一层：** 就算不谈价格，一个前沿模型路由器还会在任何有用的生成开始之前，给每条请求都加上它的完整延迟，于是恰恰在路由本该加速的那些简单查询上，把首 token 延迟拖得更糟。路由器必须在价格和速度两条轴上都比它把守的东西更便宜、更快。

**问：路由器是不是应该以成本最小化为目标？**
答：不是。只按成本来优化路由器，会导致成本项一旦主导训练信号，它就把新变难的查询甩给小模型。正确的目标是"在每个分桶都有质量下限的约束下最小化成本"。评测集里要把难长尾放足，这样一个处理不好难查询的路由器就会显示成质量回退，而不是成本上的胜利。

**再深一层：** 这是一次奖励设定上的失败。成本在每条请求上都完整、廉价地可观测，而难长尾上的质量只是稀疏采样，所以一个没有约束的目标会朝着它看得见的那一项漂。把分桶质量下限写成硬约束而不是软惩罚，才能拦住优化器拿长尾质量去换一个好看的成本数字。

**问：FP8 量化提升了吞吐。是不是意味着 API 变便宜了？**
答：只有自建才是。走按 token 计费的 API 时，服务基础设施是供应商控制的，你这边做量化不会改变账单。FP8 是一个自建的杠杆：它降低显存占用、提高每 GPU 秒的 token 数，而这只有在 GPU 是你自己的时候，才会转化成更低的单 token 成本。

**再深一层：** 在 API 上，单 token 价格由供应商的合同定，和他们的服务效率是解耦的，所以他们从量化里拿到的任何吞吐收益都进了自己的毛利，不会进你的账单。你的量化只有在 GPU 小时是你自己在付的时候才会挪动成本，这也正是为什么这个杠杆只存在于自建的 QPS 盈亏平衡点之上。

**问：离线批量任务要不要走和交互流量一样的路由逻辑？**
答：不要。离线批量任务（回填、每晚分类、离线评测生成）没有用户在等，也没有延迟 SLO。把它们送到供应商的 batch API（大约是同步端点单 token 价格的一半），或者送到一个在 spot 算力上跑满最大 batch 的自建模型。交互路由逻辑是围绕一个延迟预算设计的，而离线任务根本没有这个预算；把它套到离线流量上，就是在为离线工作付在线价格。

**再深一层：** batch 端点之所以能便宜，靠的是推迟执行、把请求打包成大 batch 来最大化 GPU 利用率，而这恰恰是交互 SLO 不允许的"用延迟换吞吐"。所以那个大约一半的价格，是 batching 这个机制在账单上的体现，不是一个随便给的折扣；把交互流量走这条路，延迟预算会直接爆掉。
