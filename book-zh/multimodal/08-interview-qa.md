# 8. 面试问答

面试官在多模态服务上真正会问的那些问题，按用法分了组。常答错的那一组，才是面试拉开差距的地方。

## 常问

**问：为什么服务一个视觉语言模型比服务一个纯文本 LLM 贵？**
答：因为一张图会变成几百上千个 token，而且落在整条流水线里最贵的那一段。
一张 1024x1024 的图按 16 像素的 patch 切，会产出 4096 个 token。这些 token 进入 LLM 的 prefill（计算量随序列长度平方增长），
还会在每一层解码器里把 KV cache 撑大。一个纯文本问题可能只有 30 个 token；加一张高分辨率的图，这个请求在 prefill 上就贵了 130 倍以上。
服务成本贵的不是图像本身，是图像 token。

**问：视觉语言模型有哪三个组件？**
答：视觉编码器（ViT 风格，每个图像 patch 产出一个特征向量）、projector 或者说连接器（把编码器特征映射进 LLM 的 token embedding 空间，
同时定下图像 token 预算），以及 LLM 解码器（吃进图文交错的 token 序列，自回归地生成）。
编码器可批处理、可缓存；解码器是自回归的、受显存带宽限制。把这个区别想清楚，整个服务架构就跟着定下来了。

**问：带图请求的首 token 延迟怎么压到 2 秒以内？**
答：把图像 token 数降下来（用更低的分辨率，或者用 resampler 这类固定上限的连接器），缓存编码器输出让重复的图跳过编码，
再把编码器拆成独立的、可批处理的一层，别让它跟自回归的解码器抢同一块 GPU 资源。
如果是混合负载，还要把纯文本请求整个绕过编码器。

**问：用户传了一张分辨率极高的图，会发生什么？**
答：在编码之前先校验并限制尺寸。一张 4000x3000 的图必须在编码器看到它之前降到系统的分辨率上限，
否则 token 数会把编码器所在的 GPU 打爆显存，同一个 batch 里其他请求也跟着变慢。
这个上限是一个产品决策：通用问答缩到 512px 或 768px，文档 OCR 缩到 1024px 并接受更高的成本。

**问：projector 是干什么的，它为什么对服务这么关键？**
答：projector 把编码器特征映射进 LLM 的 embedding 空间，同时定下图像 token 数。
MLP projector 每个编码器 patch 过一个 token（细节随成本一起涨）；resampler 或 Q-Former 压成固定的少量 token（成本有上界，但细节也被封顶）。
选 projector 就是在选那个质量与成本的工作点。

## 有坑的

**问：换了更高分辨率的编码器之后离线 VQA 准确率提升了，但线上 TTFT 从 0.8 秒涨到 3.2 秒。发生了什么，怎么修？**
答：分辨率翻倍会让 token 数变成四倍（随图像边长平方增长），更长的序列让 prefill 慢得不成比例。
一个常见错误是只评准确率，不在实际服务分辨率下测延迟。
修法：只对真正需要细节的任务有选择地开分块，并且把分辨率做成按请求或按任务可调的旋钮，而不是一个全局常量。
通用问答用 336px 服务，OCR 请求用 1024px 加分块。

**为什么慢下来的幅度比 4 倍还大：** token 数随图像边长平方增长，self-attention 的成本又随 token 数平方增长，
所以分辨率翻倍最多会让 attention 的 FLOPs 变成 16 倍。离线评估从来没暴露过这一点，因为准确率是逐样本测的，没有延迟预算；
这个回退只有在服务时、作为序列长度的函数才存在。

**问：应该缓存原始图像字节、编码器 embedding，还是解码器的 KV 条目？**
答：缓存编码器 embedding（不是原始字节，那还得重新编码一遍）。KV 条目太大，而且和会话绑死。
给定图像，编码器输出是确定的，对同一张图的任何 prompt 都能复用。缓存的 key 要用图像内容的 hash，不要用文件名或 URL，
这样同一张图换个名字也照样命中。vLLM V1 还把图像 hash 折进前缀缓存的 key 里，
让围绕同一张图的多轮对话不用重复算 KV。

**这三个缓存候选的区别在哪：** 它们处在依赖链的不同位置。原始字节不依赖任何东西，但也什么都省不下（那趟贵的编码还是要跑）。
编码器 embedding 只依赖像素，所以对任何 prompt、任何用户、任何会话都有效。
KV 条目还额外依赖序列里排在它前面的每一个 token，包括位置和周围的 prompt，
所以只有整段前缀完全匹配时才能复用，这也是为什么它属于前缀缓存，而不是一个独立的图像缓存。

**问：文本 prompt 的前缀缓存本来跑得好好的。为什么一上多模态输入就坏了？**
答：文本前缀缓存用 token ID 当 key。而在多模态模型里，图像占位符是一组固定的特殊 token，不管插进去的是哪张图，它们长得一模一样。
两张不同的图会产生同一串占位 token，于是一个天真的前缀缓存会不声不响地返回另一张图的 KV 条目。
修法是把图像内容的 hash 折进缓存 key。

**问：什么时候该用 resampler 而不是 MLP projector？**
答：当每个请求的成本和延迟必须被严格框住、不管输入分辨率是多少的时候。
resampler 把编码器那张变长的特征网格压成一块固定大小的 token（BLIP-2 用 32 个，Idefics2 用 64 或 320 个）。
代价是密集内容、OCR 和精细的几何细节会部分丢失，因为 resampler 必须丢掉信息才能压进那个固定预算。
任务偏通用理解、预算又紧的时候用 resampler；任务需要精细细节、而且承受得起可变 token 数的时候用 MLP projector。

**固定预算为什么会丢细节：** resampler 的做法是让一小撮学出来的 query token 去 cross-attend 整张 patch 网格，
所以解码器将来能知道的关于这张图的一切，都必须从那个固定宽度的瓶颈里挤过去。剩下的交给信息论：
4096 个 patch 的网格被总结成 64 个向量，不可能保住每一个字形和边缘，于是这些 query 学会保留训练任务奖励的东西，
也就是全局语义，而不是密集的文字。

**问：编码器 embedding 是按内容 hash 缓存的，但两个用户把同一张照片稍微裁一下或者重存一次，缓存命中率就是零。缓存坏了吗？**
答：没坏，它就是这么设计的，而且这正是重点。内容 hash 是刻意脆弱的：只有字节完全一致（如果 hash 的是解码后的像素，则是像素完全一致）才命中，
因为只有输入真正相同时，编码器输出才保证可复用。重新裁剪、重新压缩、改写一次 EXIF，得到的都是不同的像素网格，
因而是一份合法地不同的 embedding，这时候要是命中了，返回的就是陈旧的特征，会不声不响地把答案带偏。
如果想让近似重复也复用，靠 hash 是拿不到的；那需要感知哈希或者 embedding 相似度检索，
用精确性换召回，同时把"给出另一张图的特征"这个风险重新引回来。
这道题的信号在于认出：这个"未命中"是缓存在拒绝出错，而不是缓存在失效。
提升命中率的正确杠杆是在上游把输入归一化（固定降采样、剥掉元数据、统一重新编码），让真正等价的上传在 hash 之前就收敛到同一串字节。

**问：视觉编码器和 LLM 解码器怎么独立扩容？**
答：把它们跑成两个独立的服务。编码器是一趟有界的、可批处理的无状态计算，靠复制编码器 pod 就能横向扩容。
解码器是那趟自回归、受显存带宽限制的计算，需要 GPU 显存来放 KV cache，扩容方式完全不同。
编码器的输出（一块固定大小的 embedding）通过一条轻量的消息交给解码层。
这样拆开之后，还能在编码器上用 DP、在解码器上用 TP，两边互不牵扯。

**这两层为什么扩容方式差这么多：** 编码器是一趟无状态的前馈计算，吞吐几乎随副本数线性增长，而且任何副本都能服务任何请求。
解码器持有按会话的 KV 状态，这些状态必须留在序列所在的那张 GPU 上，所以它的容量被 HBM 卡住，请求也和自己的副本粘在一起。
把两者塞进同一个服务，就是强迫那个无状态、吃算力的阶段和那个有状态、吃显存的阶段共用一套扩容策略，结果是两边都不合身。

**问：分块和原生更高分辨率的编码器看上去差不多，都是给模型更多像素。这个区别到底什么时候才要紧？**

答：机制上的差别在于这些多出来的像素是在哪里和 attention 相遇的。原生高分辨率编码器在整张 patch 网格上跑 self-attention，
所以每个 patch 都能关注到其他任意 patch：全局版式被保住了，但成本随网格大小平方增长，而且编码器必须在那个分辨率上训练过。
分块则是复用一个固定分辨率的编码器，把图切成若干张小图各自独立编码：成本只随块数线性增长，也不用重训，
但一个块里的 patch 永远关注不到另一个块里的 patch，于是跨块边界的结构（表格的一行、示意图里的一根箭头）会被割裂，
只能由解码器重新缝起来，通常靠块位置标签加一张低分辨率缩略图当全局地图。
这个区别要紧的时刻恰好是任务需要跨区域几何关系的时候：读整页表格或图表更适合原生分辨率（或者精心设计的 tile 标签），
而找小字这类局部精细细节则容忍分块，而且便宜得多。

## 常答错

**问：图像是不是作为一个特殊 token 进 LLM 上下文的？**
答：不是。图像会变成一块 token，MLP projector 是每个编码器 patch 一个，resampler 是固定的一组，但绝不会是一个。
把一张图当成一个 token，是导致成本估算错得离谱的那个核心错误。
336px 的图大约 576 个 token；1024px 的图可以到 4096 个。这两个数字要随时能报出来。

**为什么一个 token 不可能够用：** 解码器只能用序列里实际存在的信息，而单个 embedding 向量的容量，
远不足以把一个场景表达到能回答问题的细节程度。每个 patch 一个 token 保住了一种空间对应关系，注意力机制可以利用它
（模型可以去关注包含答案的那块区域），这也是为什么建立在"一张图就是一个 token"上的成本估算会差三个数量级。

**问：图像 token 缓存是按文件名或 URL 做的吗？**
答：按内容 hash。文件名和 URL 都不稳定；同一张图可能带着不同的名字、从不同的 URL 到达。
内容 hash 保证字节相同就一定命中，也保证不同的图即使 URL 撞了也绝不会串。这一点很细，但在实践里很要命。

**为什么撞 key 比未命中糟糕得多：** 未命中只是多编码一次，撞 key 却会把另一张图的 embedding 当成这一张的送出去，
解码器会心安理得地回答一张错误的图，整条流水线里没有任何地方会报错。
所以缓存的 key 必须从被缓存的值真正依赖的东西推出来，对编码器输出而言，那就是像素，而不是它到达时用的名字。

**问：给解码器所在的机器加显存，能让带图的重请求变快吗？**
答：主要不能。带图重请求的瓶颈是 prefill 计算，它随序列长度平方增长，是受算力限制，不是受显存带宽限制。
更多显存有利于 KV cache（能塞下更多并发会话），但解决不了长图像 token prefill 造成的高 TTFT。
该做的是把 token 数降下来，或者把 prefill 并行化。

**问：能不能把图像 token 直接拼在所有文本 token 后面，这样 LLM 就一点都不用改？**
答：技术上可行，但质量会掉。多数 VLM 是把图像 token 交错插在指令模板里图像占位符的位置（在问题之前或者问题中间），
让模型在有问题作为上下文的情况下去关注图像。把图像 token 拼在末尾，等于逼着模型先在没有图的情况下读完问题，再看到图。
经过指令微调的 VLM 期待的是它们微调时见过的那种交错排布。机制层面的原因是：解码器是因果的，
一个 token 只能关注到位置不晚于自己的 token。如果图像 token 排在问题后面，问题里的 token 一个都关注不到图像，
只有生成出来的答案 token 才看得见它，模型实际上是先回答了一个纯文本问题，然后一边解码一边瞟了图一眼。
把图像放在问题之前，每个问题 token 都能关注到视觉证据，这也是为什么 LLaVA（2023）的指令模板以及后续那些方案，
都是把图像 token 交错在占位符处，而不是拼在末尾。
