# 1. 澄清需求

动手设计之前，先把系统必须做什么定下来。下面是候选人和面试官之间一段典型的对话。
注意每一个问题要么砍掉了一部分工作，要么改变了设计，尤其是围绕图像 token 预算的那几个。

**候选人：** 哪些模态在范围内（模态指输入的类型，比如图像、视频、音频、文本）？只有图片，还是也包括视频、音频或者文档？
**面试官：** 先从图片开始。有时间的话再聊视频。

**候选人：** 图片一般是什么分辨率？每个请求带几张图？
**面试官：** 先假设每个请求一张图，最大 1024 乘 1024 像素。多图算加分项。

**候选人：** 我们要解决的是什么任务？视觉问答、图片描述、文档 OCR，还是别的？
**面试官：** 主要是视觉问答：用户上传一张照片，用自然语言问一个关于这张照片的问题。

**候选人：** 这是交互式产品（用户在等第一个 token），还是批量补数据（没有延迟约束）？
**面试官：** 交互式。我们希望首 token 延迟在 2 秒以内。

**候选人：** 模型需要从图片里恢复多少细节？"这张图里有什么"这类任务需要的分辨率，比读小票或者图表低得多。
**面试官：** 目前是通用理解。密集文字和图表以后再考虑。

**候选人：** 预期请求量是多少？流量里主要是带图的，还是也有纯文本？
**面试官：** 假设是混合流量。大概 30% 的请求带图，其余是纯文本。

把问题陈述总结一下。**我们要设计一个服务，接收一张图片和一段文本 prompt，用视觉语言模型返回一个有依据的自然语言回答。**
输入是一张图片（最大 1024x1024）加一个文本问题；输出是流式的文本回复。首 token 延迟目标是 2 秒以内。
流量里 30% 是带图请求，70% 是纯文本。

从这里立刻能推出三个结论，早点把它们说出来，就是这道题大部分的信号。

**图像 token 预算就是整个成本故事。** 一张 1024x1024 的图片，patch 大小 16 像素，最多会产生 4096 个 token。
这些 token 落在 LLM 的 prefill 阶段（首 token 延迟的大头），也落在每一层的 KV cache 里。
一个纯文本问题可能只有 30 个 token；同一个请求带上一张高分辨率图片，prefill 的开销就是 130 倍。
下游的一切都由这笔账决定。

**分辨率是一个质量和成本之间的旋钮，不是一个默认值。** 对通用视觉问答来说，低一点的分辨率已经能恢复足够的细节，
同时把 token 数大幅压下来。有经验的做法是按任务选分辨率，而不是永远拉到最高。

**带图请求和纯文本请求差别大到值得走两条独立的基础设施路径。** 让纯文本请求绕过视觉编码器，
70% 的流量就不用为图像基础设施买单。这是一个很直接的收益，却有出人意料多的设计漏掉了它。
