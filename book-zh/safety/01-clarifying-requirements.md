# 1. 澄清需求

动手设计之前，先把两件事钉死：系统要防什么，服务谁。下面是一段典型的对话。注意每个问题要么砍掉了一块工作量，要么直接改变了设计。

**候选人：** 我们要防的是什么？有害生成、违反策略、PII 泄露，还是 prompt 注入和越狱这类操纵？

**面试官：** 都要防，但按风险分轻重。有害生成和抗越狱是首要关切。PII 泄露和 prompt 注入紧随其后，尤其这个产品用了 RAG。

**候选人：** 信任边界在哪？不可信内容只来自用户，还是检索到的文档和工具输出也算？

**面试官：** 都算。检索文档和工具结果会和用户消息一起进来，内容我们控制不了。

**候选人：** 终端用户是谁，出事的代价有多大？大规模消费级产品、内部工具，还是医疗、金融这种受监管的领域？

**面试官：** 大规模消费级。按每天几百万请求想，不是几千。没有特定监管，但品牌风险很高。

**候选人：** 安全层的延迟预算是多少？实时聊天产品能容忍的开销比异步流水线小得多。

**面试官：** p50 新增延迟要控制在 100ms 以内，对明显有害的输入必须绝对拦住。峰值吞吐是每秒几万个请求。

**候选人：** 可接受的误报率是多少？每拦错一个正常请求，就是一个绕开产品走的用户。

**面试官：** 这点我们非常在意。宁可漏掉一个边界案例，也不要错拦五个无辜用户。捕获率和良性拒绝率都要跟踪。

把问题陈述总结一下。**我们要为一个带 RAG 组件的消费级 LLM 产品设计一套分层安全系统。** 威胁面包括用户越狱、经检索内容进来的间接 prompt 注入、有害生成和 PII 泄露。系统的 p50 新增延迟必须在 100ms 以内，要扛住每秒几万个请求，尽量压低误报，并把每一次拦截决策都记下来供审计和调优。

从这里立刻能推出两个结论：

- **信任边界不止于用户。** 一个会摄入检索文档或工具输出的产品，攻击面比纯聊天界面大得多。藏在文档里的注入，比用户直接敲一句"忽略之前的指令"难抓得多。这会改变设计：结构隔离和代码侧的动作闸门变成承重墙，而不是可选项。

- **没有哪一道护栏是可以单独信任的。** 每秒几万请求、100ms 预算，在关键路径上放一个大 guard 模型，已经既太慢又太脆。防御必须分层：先跑廉价的确定性检查，再跑快速分类器，把大模型留给通过廉价层的那一小部分输入。级联不是性能技巧，它是在不吃光延迟预算的前提下，把系统做成"故障时默认关闭"的方式。
